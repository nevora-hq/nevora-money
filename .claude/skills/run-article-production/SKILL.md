# 記事制作の実行(run-local.js)

記事の生成・判定の起動経路は `サイト運営/サイト本体/scripts/autonomy/run-local.js` ただ一つである。
judge.js・cycle.js・regression.js などを直接実行しない(直接実行しても何もせずに終了する)。

## 依頼の言葉と実行するコマンド

コマンドはリポジトリのルートで実行する。**`start` と `next` は、Bash ツールの `run_in_background` を指定して実行し**、完了の通知が来るまで待つ(執筆・修正の工程は最長25分かかり、`run_in_background` を指定しない実行は10分で打ち切られるため)。`status` と `abort` はすぐ終わるので、`run_in_background` を指定せずに実行する。

| 依頼者の言葉 | 実行するコマンド |
|---|---|
| 「記事制作を実行して」 | `node "サイト運営/サイト本体/scripts/autonomy/run-local.js" start` |
| 「〇〇で記事制作を実行して」(テーマ付き) | `node "サイト運営/サイト本体/scripts/autonomy/run-local.js" start --theme "〇〇"` |
| 既存の記事を直す指示(例:「〇〇の記事の体験談を削って」) | `node "サイト運営/サイト本体/scripts/autonomy/run-local.js" start --revise "<記事のパス>" --instruction "<修正指示>"` |
| 既存の記事を直さずに判定にかける指示(例:「〇〇の記事を判定にかけて」) | `node "サイト運営/サイト本体/scripts/autonomy/run-local.js" start --revise "<記事のパス>"` |
| 「次へ」 | `node "サイト運営/サイト本体/scripts/autonomy/run-local.js" next --from <直前の停止点の番号>` |
| 「状況を見せて」 | `node "サイト運営/サイト本体/scripts/autonomy/run-local.js" status` |
| 「中止して」 | `node "サイト運営/サイト本体/scripts/autonomy/run-local.js" abort` |

- 既存の記事(`--revise`):
  - `<記事のパス>` は `サイト運営/記事データ/公開済み`・`公開待ち` のどちらかの直下にある記事ファイル。依頼者が記事をタイトルなどで示した場合は、この2つのフォルダのファイル名と frontmatter の title から探す。候補が1つに決まらなければ、候補のパスを示して依頼者に選んでもらう(推測で選ばない)。
  - `<修正指示>` には、依頼者の修正の指示を、そのメッセージの言葉のまま渡す(要約・言い換えをしない)。
  - 既存の記事を直す依頼を受けたら、実行する前に次の2点を依頼者に伝える。(1) 通過すると元の記事ファイルが置き換わる(サイトへの反映は push のあと) (2) 公開ゲートを push したあとは、判定を通っていない内容はサイトに取り込まれないため、判定を通るまで修正は公開されない。
- `--from` には、直前の停止点の報告に書かれた番号(例: `03`)をそのまま渡す。報告の「次へ進むコマンド」をそのまま使えばよい。
- 出力の最後の行 `RUN_LOCAL_RESULT:{...}` に、実行の状態(`status`・`stopSeq`・`next`・`reportFile`)がある。

## 設計期モード(お金サイトは2026-10-10の依頼者の決定により、すべて運用期。以下は設計期モードで動く場合の挙動の説明)

- ここでいう工程は、下の一覧の各行ではなく、停止点の報告1つに対応する単位である(第1層〜第5層の各層・regression などが、それぞれ1つの工程)。
- run-local.js は工程を1つ実行するたびに止まる(1回の next で実行される工程は1つだけであることは、run-local.js 側で保証されている)。**依頼者の「次へ」1回につき、next を1回だけ実行する。** 「次へ」の一言が next の指示であり、ほかの確認は要らない。「次へ」と同じ意味の指示(例:「次に進めて」「続けて」)も next の指示である。依頼者の「次へ」なしに next を実行しない。止まるたびに、停止点の報告を依頼者に見せて、指示を待つ。
- next が失敗した場合(コマンドが途中で終わった・結果が「異常」「中止」だった)も、同じ「次へ」で next をもう一度実行しない。報告して、依頼者の指示を待つ。
- 停止点の番号(`01`・`02`…)は、止まるたびに1つずつ増える。下の一覧は停止点の種類を順に並べたものであり、番号でも工程の数でもない(差し戻しがあると同じ工程が何度も現れるため、実際の番号は `RUN_LOCAL_RESULT` の `stopSeq` と報告ファイルの名前で確かめる)。
- 停止点の種類(この順に現れる):
  1. self-test 完了
  2. 記事の企画完了(執筆前)。既存の記事(`--revise`)では 2・3 の代わりに「既存記事の修正版の準備完了(判定前)」
  3. 執筆完了(判定前)
  4. 第1層〜第5層の各層の判定完了(層ごとに止まり、層ごとに別の停止点番号になる。第1層で差し戻しなら第2〜5層は実行しない。第2〜4層のいずれかで差し戻しなら第5層は実行しない)
  5. 第6層の判定完了(判定の確定)。差し戻しならここで差し戻し理由を示す。通過ならここが公開待ち配置(既存の記事では元の記事の置き換え)の直前。上限到達ならここで停止記録を置く
  6. 修正版の生成完了(再判定前) → 4 の第1層へ戻る
  7. 公開待ちへの配置完了。既存の記事では「元の記事ファイルの置き換え完了」
  8. regression・retention・aggregate・report の各完了
- 第3層の扱い(2026-10-11 依頼者の決定): 差し戻しに採用する否定は、定義どおりの回数(runs)を実行して、過半数の実行(3回なら2回以上)に出たものだけである。1回の実行でだけ出た否定と、判定が自分で「弱い」と書いた否定は採用しない。第3層を理由とする差し戻しは、1つの記事で1回だけである。1回直したあとは、第3層を理由に差し戻さない。最後の判定で第3層をもう一度実行した結果は、報告だけにする(決まりの正は `サイト運営/サイト本体/scripts/autonomy/current-rules.json` の `layer3`)。
- 停止点の報告は `docs/pipeline/autonomy/runs/<実行ID>/<番号>_<工程>.md` にもある。報告には、その工程で生成・判定されたもの(ファイル・判定条件の全文・該当テキスト・引用・差分)と、次の工程が書かれている。
- 依頼者に見せるときは、報告ファイルの全文(「この工程で起きたこと」「生成・変更されたファイル」「次の工程」の節を含む)を、書き換えずにそのまま示す(言い換え・並べ替え・要約・省略をしない)。報告ファイルのパスも示す。

## 運用期モード(2026-10-10の依頼者の決定により、すべて運用期。run-mode.jsonのmode:"operation"参照)

- 止まらずに最後まで実行するモード。工程と順序は設計期と同じ。
- 切り替えの規則は次のとおり(`scripts/autonomy/run-mode.json` の `switchRuleFullText` と同じ文。文中の「このファイル」は `run-mode.json` のこと):

> 運用期モードへの切り替えは、依頼者の明示的な指示によってのみ行う。明示的な指示に当たるのは、依頼者が運用期モードへの切り替えを実行するよう求める発言である(例:「運用期モードに切り替えて」「運用期に切り替えましょう」「運用期モードにして」)。「切り替え」という語を使っているかどうかは問わない。次のような発言は明示的な指示に当たらない: 感想・示唆(例:「そろそろ運用期でもいいかも」「切り替えたほうがいいと思う」)、質問や許可を求める形(例:「切り替えてもいい?」「切り替えられる?」)、判断をシステム側に委ねる発言(例:「切り替えるかは任せる」)。これらは例であり、例に無い発言でも、切り替えの実行を求めていると言い切れないものは明示的な指示に当たらない(迷う場合は、当たらない側に扱う)。明示的な指示に当たらない発言を受けた場合は切り替えず、現在のモードが設計期のままであることと、切り替えるには「運用期モードに切り替えて」のように指示すればよいことだけを伝える。「切り替えますか」と聞き返すことはしない(切り替えを勧める形になるため)。システム側(Claude Code を含む)が「設計が固まった」と自己判断して切り替えてはならず、自分から切り替えを勧めてもならない。依頼者に尋ねられた場合に答えてよいのは、現在のモード・切り替えの手順・未検証の事項・切り替えなかった理由(受けた発言を明示的な指示に当たらないと扱ったこと)などの事実だけである。未検証の事項を伝えるときは列挙するだけにし、切り替えの時期についての見方を添えない。意見を求められた場合も、切り替えるべきかどうかの推奨はしない。明示的な指示を受けたら、Claude Code がこのファイルを書き換える。mode を operation にし、switchedAt に Claude Code がこのファイルを書き換えた日時(ISO 8601 形式)を、switchInstructionFullText に、切り替えを求めた発言を含む依頼者のその1回のメッセージの全体(依頼者が入力した文だけ。システムが自動で付け加えた文は含めない)を、切り替えと関係の無い文も含めて、改行・空白・記号も変えずにそのまま書く(それより前のメッセージは、続けて送られたものでも含めない)。この2つが無い限り、run-local.js は運用期モードでの起動を受け付けない。運用期の起動方法(このPC上のタスクスケジューラ等)は、切り替えの前後を問わず、依頼者から設計の指示を受けたときに設計する。切り替えの書き換えのときに、起動方法の設計・設定を行わない(尋ねられた場合に、起動方法が未設計であることを伝えるのはよい)。

## やってはいけないこと

- **自分の判断で commit・push をしない。** 「Webサイト変更はcommit・push必須」の方針は、この流れには適用しない。この流れで commit・push をするのは、依頼者が commit・push を指示したとき、または `.claude/agents/publisher.md` の公開の手順を実行する者(サブエージェントを束ねる側)がその手順どおりに行うときだけである(CLAUDE.md 2026-10-03。そのときは指示された範囲だけを行う)。
- 従量課金のAPIキー(環境変数・設定ファイル)を設定しない。設定を提案もしない(run-local.js は、それらがあると何も実行しない)。
- 全体の結果が「中止」「異常」のとき、または記事制作サイクルの結果が「停止」「異常」のときは、報告して依頼者の指示を待つ。原因を調べ、報告の中で原因と直し方の案を示すのはよい。ファイルを変更して直すこと、start し直すことは、依頼者の指示を受けてから行う。
- `docs/pipeline/autonomy/halts/` の停止記録を消さない。消すかどうかは依頼者が決める。
- 判定の途中の記事ファイル(`サイト運営/実務/ライター/自動サイクル/`)を書き換えない(書き換えると、次の層で異常として止まる)。
- 公開ゲートの台帳(`scripts/autonomy/publish-ledger.json`)を手で書き換えない。記録するのは公開待ち配置の工程と、元の記事の置き換えの工程だけ。(依頼者の目視で公開する回の「台帳の代行記録」は、この流れの外で、`.claude/agents/publisher.md` の手順を実行する者が行う。)

## 結果の意味

| 項目 | 値 | 意味 |
|---|---|---|
| 記事制作サイクルの結果 | 通過 | 新規記事: 多層判定を通過し、公開待ちに publishAt を付けずに置いた。公開ゲートの台帳に内容を記録した。公開はされない。既存の記事: 多層判定を通過した修正版で元の記事ファイルを置き換え(ファイル名・date・publishAt は元のまま)、台帳に記録した。サイトへの反映は push のあと |
| | 停止 | 差し戻し5回または処理時間30分(確認待ちの時間は含めない)の上限に到達した。記事は公開工程に進めない。停止記録が残る間は、次の記事を生成しない |
| | スキップ | 前回の停止記録が残っているため、記事を生成しなかった |
| | 異常 | claude の呼び出しの失敗・判定の JSON が返らない(判定を経ていない層がある)・工程の失敗・時間上限・工程中の commit/push・判定途中の記事の書き換え・既存の記事の元のファイルが実行中に書き換えられた、のいずれか。判定は確定しない。既存の記事の元のファイルには触れない |
| 全体の結果 | 完了 | report まで進んだ |
| | 異常 | いずれかの工程で異常が起きて終えた |
| | 中止 | self-test が不合格、または依頼者の指示で終えた(abort) |

## サイトのコードに仕組みが入るまでの手順

`scripts/autonomy`(run-local.js)がまだサイトのコードに入っていない間は、次の手順で進める。

- 判定を手で行う。定義(`current-rules.json`・`docs/pipeline/JUDGE-ITEMS.md`・`.claude/agents/nevora-pipeline-verifier.md`)を読み、記事を1項目ずつ手で判定する。
- 数える所(文字数・段落の文数・図表の数・`%%出典:…%%` の有無など)は、読むだけのコマンド(grep・wc など。ファイルを書き換えない)で数える。
- 判定の結果は項目ごとに Yes / No と理由を残し、1つでも No なら直してから次へ進む(層の順序は run-local.js と同じ)。

## 起動経路の変更

- project-manager による記事制作の流れは廃止した(記事の生成・判定の起動経路を run-local.js ただ一つにするため)。
- サイトのビルドと公開キューは、多層判定を通過した内容だけを取り込む(公開ゲート)。公開ゲートを入れた時点で公開されていた記事は、基準線として台帳に載せてある(多層判定は通っていない。内容を変えると判定を通るまで公開に入らない)。
