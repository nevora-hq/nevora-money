# Web記事執筆スキル(ライター)

## frontmatter
記事Markdownの冒頭に以下を必ず含める。
```yaml
---
title: "SEOキーワードを含むタイトル"
description: "検索結果に表示される120字程度の要約"
category: "対象ジャンルのカテゴリ(例: 制作時に指定)"
tags: ["キーワード1", "キーワード2"]
affiliateLinks:
  - label: "紹介する商品・サービス名"
    url: "アフィリエイトリンクURL"
---
```
提携先が未整備の場合は `affiliateLinks` 自体を省略する(空配列やプレースホルダー文言を残さない)。`label`/`url`以外のキー名(`name`等)を使うと `/compare` ページのビルド時に値が`undefined`になりビルドエラーになるため、キー名は必ずこの2つで統一する。

## 執筆の型(記事設計イメージ)
記事全体は次の流れで組み立てる。
```
タイトル
↓
導入文(読者の悩み・検索意図への共感)
↓
この記事でわかること(💡ポイントの箇条書き)
↓
[任意] 担当マスコット登場(mascotComments: position intro)「今回は〇〇を見ていこう」
↓
本文(見出し・比較表・データ・具体例)
↓
[任意] 難所には担当マスコットの補足(mascotComments: afterHeading)
↓
重要ポイント整理
↓
まとめ(次の行動の提示)
↓
[任意] 担当マスコットの締めコメント(mascotComments: position summary)
```
1. リード文: 検索意図に即答する結論・要点を先に示す。**分析者が特定した「競合記事の弱点・不足点」を踏まえ、その記事にしかない切り口や情報を早い段階で示す。競合と同じ一般論の言い換えで終わらせない**
2. この記事でわかること: リード文の直後に、本文で答える3〜4点を箇条書き(💡ポイント)で先出しする。長い記事・複数論点がある記事で特に有効(短い記事では省略してよい)
3. 見出し(H2/H3): 想定検索キーワードを含む見出しで本論を構成する
4. 具体的な内容: データや理由を"会話的"に触れる(数値の羅列にしない)。丸数字の箇条書きを多用しすぎない。**ただし核となる具体的事実(数字・固有の条件・期間など)は各見出しに最低1つは残す。抽象論だけで終わらせない**
5. アフィリエイトリンク配置: 文脈に沿って自然に商品・サービスを紹介する箇所に配置し、広告表記(PR/広告等)を明記する
6. まとめ: 記事の要点と、次の行動(比較ページ・ランキングページ・商品ページ等への導線)を示す。**テンプレ的な汎用フレーズで終わらせず、本文の具体的内容に紐づいた結論にする**

## 段落の長さ
1段落に3文以上を詰め込まない(目安2〜3文、長くても4文まで)。話題や視点が変わる箇所(「そもそもの原因」→「対策」、「一般論」→「私の体験」など)では必ず段落(空行)を分ける。1文が長い場合も、読点の多い一文をだらだら続けず、意味の区切りで文自体を分割する。読者がスマホの狭い画面で読む前提で、圧迫感のある「文字の壁」を作らない。

## AI感を避けるルール
- 「〜と言われています」「〜というデータも」を1記事内で2回以上使わない
- 一人称・実体験ベースの語り口を優先する(「〜って気づいた」「〜してみようと思う」)
- 断定的な効果表現は避けつつ、ヘッジ表現(個人差があります等)を連発しない。1箇所にまとめる
- 数値データを羅列せず、必要な範囲に絞って触れる

## 「読まれる・上位表示される」ための必須チェック
- ヘッジ表現で具体性を薄めすぎていないか。法務上必要な最低限のヘッジは残しつつ、それ以外まで曖昧にして当たり障りのない記事にしない
- 分析者が特定した競合記事の弱点を、自社記事で実際に埋められているか
- 読み終えたときに「この記事は他と違って役に立った」と思わせる一点があるか。なければ書き直す

## 本文の装飾記法
サイト側のMarkdown処理(remark-gfm対応済み)で以下が使える。多用しすぎず、本当に強調したい1〜2箇所に絞る。
- `==強調したい語句==` → 黄色マーカーのハイライト
- `++強調したい語句++` → ブランドカラーの下線
- `**太字**` → 標準の強調(すでにブランドカラーで装飾済み)
- `~~誤り・古い情報~~` → 打ち消し線(訂正・古い情報の明示に)
- `^^気づき・感情が変わる一文^^` → 文字を大きく・青色にして目立たせる強調(「実は思い込みだった」「これは驚いた」のように、読者の認識が変わる/感情が動く一文にだけ使う。地の文の説明にはつけない)。絵文字(💦😳など)は装飾記法とは別に、地の文にそのまま書いてよい
- `%%出典の信頼性・注意点の一言注記%%` → やや小さめ・控えめな色で表示(0.88em/グレー系)。「なお、この見解は企業運営のコラム記事によるもので〜」のような、本文の主張ではなく出典の性質・留意点を添える一文にのみ使う。**景品表示法の打消し表示規制に配慮し、効果効能等の強調表示を打ち消す注記をこの記法で目立たなくする目的では使わない**(読めなくなるほど小さく・薄くしてはいけない)
- Markdownの表(`| 見出し | 見出し |` 形式)・番号なしリストがそのまま使える(表は比較・まとめ情報がある記事でのみ使用し、無理に入れない)

強調記法は1記事に対して合計3〜4箇所程度を上限とし、全部乗せにしない(ハイライトだらけの記事はかえって読みにくい)。

## 表の使用ルール
以下のような内容では積極的にMarkdown表を使う。単なる情報の羅列ではなく、読者が比較・判断しやすい列構成にする。
- 複数の商品・サービスの比較、メリット/デメリットの比較、特徴の整理、料金・スペック比較、選択基準の整理、手順・流れの整理、違いの説明

```
| 項目 | 特徴 | おすすめの人 | 注意点 |
|---|---|---|---|
```
のように、読者の意思決定に役立つ列(「おすすめの人」「注意点」等)を設定する。表・グラフとも、重要情報を画像だけに含めず、本文でも要点を文章で補足する(検索エンジン・読み上げ対応のため)。

## 図表使用の判断基準
理解を助ける効果が高い場合のみ使う。優先順位の目安は次の通り。
1. 比較・違いを説明する → Markdown表
2. 数値の変化・割合・傾向を説明する → `charts`(棒グラフ/円グラフ/統計値)
3. 手順・流れを整理する → リストまたは表
4. 文章だけで十分理解できる → 無理に図表を追加しない

## 図表とキャラクターの連携
表やグラフを配置する場合、必要に応じて担当マスコットの一言コメント(`mascotComments`の`afterHeading`)で内容を補足すると読者の理解が進む。例: 表の直前の見出しに「比較するときはこの3つの違いを見ることが大切」、表を含む見出しの後に「自分の目的に合ったものを選ぶのが一番」といった一言を添える。図表とキャラクターコメントを両方詰め込みすぎない(1つの見出しに図表+キャラクター両方は多くても1セット)。

## サムネイル画像
frontmatterの`thumbnail`(例: `/images/articles/YYYY-MM-DD_テーマ.webp`)は、ホームページ・カテゴリ・検索・ランキングの記事カードと記事ページ上部のヒーロー画像、他記事ページの「関連記事」カード、SNSシェア時のOGP画像に使われる。ライターが画像を用意する必要はない(サイト側で別途生成・設置する運用)。確定稿を渡す際、まだ画像がない場合はfrontmatterに`thumbnail`を書かなくてよい(未設定の記事は関連記事欄で本アイコンの代替表示になる)。

## 統計データ・グラフの提案
執筆中に信頼できる一次情報(政府統計・大手企業や調査会社の公表調査など)で、記事の主張を裏付ける具体的な数値が見つかった場合、frontmatterに以下の形式で`charts`を提案してよい(採用可否・最終調整は編集長が行う)。`type`は用途に応じて使い分ける。

- `stat`: 単一の割合・人数など、比較対象がない1つの数値を大きく見せる
- (typeを省略): 複数カテゴリの量を比較する棒グラフ
- `pie` または `donut`: 内訳・構成比(合計100%になる項目)を円グラフで見せる。5項目まで(6項目以上は自動的に上位4件+「その他」にまとめられる)
- `prosCons`: メリット/デメリットの比較を色分けした2カラムで見せる

```yaml
charts:
  - afterHeading: "この見出しの直後に挿入(本文の見出しテキストと完全一致させる)"
    type: "stat"   # 単一の数値
    value: "82.7"
    unit: "%"
    label: "何の割合かを説明する短い文"
    source: "調査主体名「調査タイトル」(実施時期・n数があれば併記)"
    sourceUrl: "出典URL"
  - afterHeading: "別の見出し"
    # 棒グラフ(typeを省略)。項目間の量を比較したい場合
    title: "グラフのタイトル"
    data: [{label: "男性", value: 38.5}, {label: "女性", value: 43.6}]
    unit: "%"
    source: "..."
    sourceUrl: "..."
  - afterHeading: "内訳を説明する見出し"
    type: "pie"    # 内訳・構成比(合計約100%になるデータ)
    title: "グラフのタイトル"
    unit: "%"
    data: [{label: "原因A", value: 45}, {label: "原因B", value: 30}, {label: "原因C", value: 25}]
    source: "..."
    sourceUrl: "..."
  - afterHeading: "比較したい見出し"
    type: "prosCons"
    title: "メリット・デメリット比較のタイトル(任意)"
    pros: ["メリット1", "メリット2"]
    cons: ["デメリット1", "デメリット2"]
    # prosConsは出典データではなく本文の整理なのでsource/sourceUrlは不要
```
- 出典は必ず一次情報(官公庁・調査実施企業の公式発表)のURLを明記する。まとめサイトや又聞き情報のみを出典にしない(`prosCons`は出典不要)
- 数値は概数(「約80%」等)であればそのまま概数と明記し、正確な数値であるかのように断定しない
- 調査時期・対象期間がわかる場合は`label`やその前後の本文に含める(何年の・どの期間のデータかを読者が判断できるようにする)
- グラフを置いて終わらせず、直後の本文で「このグラフから何が読み取れるか」を一言補足する(数値の再掲ではなく、読者が読み取るべきポイントの言語化)
- 1記事に詰め込みすぎず、本文の主張と直結する統計・比較に絞る(無理に全記事へ追加する必要はない)

## 文章トーン(必須)
専門的な内容でも論文・教科書・説明書のような硬い文章にしない。「専門家が一方的に説明する」のではなく「信頼できる案内役が分かりやすく話す」トーンにする。
- 難しい言葉は初回登場時に短く言い換え・説明を添える(例:「NISA(投資で得た利益が非課税になる制度)」)。2回目以降は説明を繰り返さない
- 専門用語を連続させない。専門用語の直後には平易な言い換えや具体例の文を挟む
- 一文を長くしすぎない(読点3つ以上でだらだら続けない。段落の長さのルールと合わせて意識する)
- 「〜って思ったことない?」「〜な人も多いはず」のような読者への語りかけを適度に入れる(入れすぎると軽薄になるので1見出しに1箇所程度)
- 親しみやすいトーンと、幼稚な言い回し(過剰な擬音・体言止めの多用)は別物。くだけていても情報の正確さ・信頼感は損なわない

## マスコットキャラクターの使用ルール
マスコットは単なる画像配置ではなく、読者理解を補助する案内役として使う。カテゴリごとに担当キャラクターが決まっている(`サイト本体\lib\categoryMascot.js`参照)。

| カテゴリ | 担当キャラクター |
|---|---|
| お金・家計 | ゼニまるくん |
| 投資 | フタバ |
| FX | キャンドル |
| 税金 | ソロくん |
| 保険 | マモルくん |
| 節約 | コツコツ |
| ポイ活 | オトクくん |

frontmatterに`mascotComments`(配列)を指定すると、サイト側で本文中の該当位置に吹き出し形式で自動挿入される(画像・名前・吹き出しはサイト側で組み立てるため、本文Markdown中にキャラクターの絵文字やセリフを直接書き込む必要はない)。

```yaml
mascotComments:
  - position: "intro"          # 記事冒頭、本文に入る直前(「今回は〇〇を見ていこう」等の導入)
    text: "今回は〇〇について、一緒に見ていこうね。"
  - afterHeading: "本文中の見出しテキスト"   # 難しい内容の補足・注意事項に。見出しテキストと完全一致させる
    text: "ここは少し難しいから、噛み砕くとこういうことだよ。"
  - position: "summary"        # 記事末尾、まとめの後
    text: "つまり〇〇ということ。自分に合う方法を選んでみてね。"
```
- 使用箇所は「記事冒頭の導入」「難しい内容の補足」「重要ポイントの整理」「注意事項」「まとめ」など、読者が迷いやすい・立ち止まりやすい箇所に限定する。1記事あたり2〜4箇所程度を目安にし、本文の各段落末尾など機械的に挟まない
- 本文そのものをキャラクター口調にするのは禁止。基本文章は通常の読みやすい記事形式で書き、要所でキャラクターが一言補足する構成にする
- コメントは40〜70字程度で、「〜だよ」「〜してみてね」のような親しみやすい口調にする。本文の要約ではなく、読者への一言アドバイス・気づきとして書く
- `mascotComments`を使わない場合、frontmatterに`mascotComment`(文字列1つ)を指定すると本文中盤に自動で1箇所挿入される(簡易版)。両方指定した場合は`mascotComments`が優先される

## 記号・装飾ルール
記事の読みやすさのため、記号・装飾は適度に使う。「ポイント」「注意」「まとめ」「チェック項目」「メリット/デメリット」のような見出しラベルは、太字やMarkdown小見出し(###)+絵文字1つ程度でシンプルに示す。
- 悪い例: `✨💡🌟おすすめポイント🌟💡✨`(絵文字の多用・装飾過多)
- 良い例: `💡ポイント`\n`○○を選ぶ際は、価格だけでなく成分も確認しましょう。`
- 1記事内で記号・絵文字の使い方に統一感を持たせる(同じ意味の見出しに毎回違う絵文字を使わない)
- 装飾は「重要情報を目立たせる」ためだけに使い、装飾自体を目的化しない

## 保存ルール
- 下書き段階は `サイト運営\実務\ライター\YYYY-MM-DD_テーマ_v1.md` のようにバージョンを明記して保存する
- 確定稿は編集長がfrontmatter込みで `サイト運営\記事データ\確定稿\YYYY-MM-DD_テーマ.md` に保存する
