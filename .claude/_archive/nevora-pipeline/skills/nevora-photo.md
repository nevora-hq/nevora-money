# PHOTO(本文写真) 実装手順

`.claude/skills/nevora-pipeline/SKILL.md` を先に読んだ前提。工程1・工程3が対象。

## 位置づけ(重要)

**`PHOTO`は源スペック(`_source-spec-v1.md`)には無い、本パイプライン独自の4種目のTYPEである。**
`_source-spec-v1.md`自体は変更していない(引き続き不変)。§2.2のTYPE一覧(ACC/VIS/TBLの3種、
新設禁止)に対する**本パイプライン運用上の追加**として、ここに定義する
(決定事項は`docs/pipeline/README.md`参照)。文法・ID採番・消費マーカーの規則は既存3種と
完全に同じものを流用する(新しい規則は作らない)。

## 根拠(既存実装の調査結果。詳細は`SPEC-EXTRACT.md`§4.4)

- 本文中の写真に**frontmatter経由の仕組みは無い**。標準Markdownの画像記法`![alt](path)`を
  本文へ直接書くだけ(`ACC`/`VIS`のような`afterHeading`見出しテキスト一致は存在しない)。
  したがって`PHOTO`は`TBL`と同じ性質(物理的な本文中の位置がそのまま採用される)を持ち、
  `ACC`/`VIS`が抱える見出しテキスト一致の残存リスク(`nevora-accordion.md`/`nevora-visual.md`
  参照)は無い
- ファイル命名規則: `/images/articles/{YYYY-MM-DD}_{記事名}_body{N}.webp`(N=1,2,…連番)
- 画像を自動生成するスクリプトは無い。Higgsfield等を人間/エージェントが対話的に使う
  半自動運用(`.claude\agents\サイト制作者\site-engineer.md:32-38`)。実績:
  `サイト運営\実務\ライター\2026-08-05_肌タイプ6種クラスター_画像生成プロンプト.md`
- 画像ファイルが未用意の場合、**無理に配置せず候補位置を書き残し、後から人間が反映する**
  運用が既にある(`.claude\agents\ライター\writer.md:72`)。本TYPEはこの既存運用を
  そのまま踏襲する(下記「工程3の運用」参照)

## 文法(既存3種と同じ規則。源スペック§2.2のブロック形式のまま)

```
[[PHOTO:PHOTO-01
intent: <この写真が読者に何を伝えるか。1文>
content: <どんな写真か。生成/撮影のブリーフとして使える具体性を持たせる(人物・構図・背景・トーン等)>
alt: <alt文。内容を説明する日本語文>
]]
```

- 必須フィールドは`intent`/`content`/`alt`の3つ(源スペック§2.2 R-5のまま、省略したブロックは不正)
- `caption`は無い。既存の本文写真は`<figure><figcaption>`のような可視キャプションを持たず、
  `alt`のみが付随情報である(`SPEC-EXTRACT.md`§4.3・§4.4)。VISの`caption`/`kind`/`labels`に
  相当するフィールドは追加しない(既存実装に無いものを新設しない、という§2.5の原則を踏襲)
- ID形式・採番規則(TYPEごとに01から出現順、欠番禁止)は§2.3のまま。`PHOTO-01`, `PHOTO-02`…
- 配置ルール(源スペック§4.4のまま): それが説明する本文の直後に置く。同じ内容を2箇所に置かない

### 工程1の配置ルール(既存の非公式ルールを踏襲、writer.md:68-72・SKILL.md:81)

- 1記事あたり1〜2枚が目安
- 記事冒頭(1番目の見出し)への配置は避ける(過去の差し戻し事例。writer.mdに明記)
- 複数枚配置する場合は見出しを分散させる。連続する見出しへ並べたり、まとめ・結論の
  直後に置いたりしない
- 装飾目的(空白埋め)での配置は禁止。読者の理解を助ける位置にのみ置く

## 消費マーカー(既存の`<!-- impl:ID -->`規則をそのまま使う。ただし状態フラグを付与する)

`PHOTO`は実装(=実ファイルの用意)を工程3では完了できない(下記参照)。そのため、
通常の`<!-- impl:ID -->`に**`status=pending-photo`と、人間が後で必要とする情報を
同じコメント内に埋め込む**。

```
<!-- impl:PHOTO-01 status=pending-photo path=/images/articles/{slug}_body1.webp alt="○○の様子" -->
```

- `impl:PHOTO-01`という文字列を含むため、V-03(ID実装漏れ)の既存grep
  (`impl:[A-Z]*-[0-9]*`)にそのままヒットする。**V-03のための特別扱いは不要**
  (工程4の判定表にも同じ理由を明記。`nevora-pipeline-verifier.md`参照)
- 実際の`![alt](path)`画像タグはまだ書かない(ファイルが存在しないのに参照すると
  V-10・実サイトで404になるため)。**コメントのみを残し、画像タグは人間が実ファイルを
  配置した後に別途反映する**(この「タグ反映」自体は工程1〜4の範囲外の後続作業とする)
- `path`は`{記事slug}_body{N}.webp`。Nは同記事内のPHOTO IDの連番(`PHOTO-01`→`body1`、
  `PHOTO-02`→`body2`)をそのまま使う(§4.3の命名規則のまま)

## 工程3の運用(UNRESOLVEDにしない。位置とaltの確定までを工程3の完了とする)

**`PHOTO`はVISと異なり、対応する型が無いからUNRESOLVEDにする、という運用ではない。**
既存実装が「画像ファイルが無ければ候補位置を書き残し、人間が後で反映する」という
半自動運用である以上、`PHOTO`も同じ運用を踏襲し、次を工程3の完了条件とする。

1. `[[PHOTO:ID ...]]`ブロックを、上記「消費マーカー」の`pending-photo`コメントに置換する
   (`path`は§4.3の命名規則で機械的に算出、`alt`はプレースホルダーの`alt`をそのまま転記)
2. `content`(生成・撮影のブリーフ)は本文からは削除するが、**捨てずにHANDOFF-03.mdへ
   転記する**(下記)
3. `HANDOFF-03.md`に「画像手配リスト」を必須項目として追加する(下記の様式)

### HANDOFF-03.mdの必須項目への追加(画像手配リスト)

```markdown
## 画像手配リスト(PHOTO。実ファイル未手配ぶん)
| ID | 配置位置(直前のH2/H3見出し) | 想定ファイルパス | alt | content(生成・撮影のブリーフ) |
|---|---|---|---|---|
| PHOTO-01 | (見出しテキスト) | /images/articles/{slug}_body1.webp | (alt文) | (プレースホルダーのcontentをそのまま転記) |
```

このリストが、人間(またはライター/サイト制作者による後続の「画像反映」作業)への
唯一の受け渡し手段になる。**行が1つでも残っている記事は、V-17により
`VERIFY-REPORT.md`の総合判定が「条件付き合格(写真未手配N件)」に留まり、「合格」とは
表示されない**(下記「V-17」参照。旧版のこの節では「合格しうる」としていたが、
決定事項に基づき訂正した)。パイプライン自体(工程0〜4)のやり直しは不要で、
差し戻しの扱いにはしない。

## V-10(画像の実在)との関係

`status=pending-photo`のコメントは実際の`<img>`/`![]()`ではないため、V-10
(記事内の全画像パスに対し`test -f`)の対象に含まれない。**これは意図した挙動**であり、
画像未手配のPHOTOがあってもV-10単体は不合格にならない(画像が404を起こす実タグを
本文に書いていないため)。画像の手配状況そのものはV-10ではなく、次のV-17で
`VERIFY-REPORT.md`の総合判定に反映される。

## V-17(写真の手配状況。定義の正)

源スペックのV-01〜V-15には無い、本パイプライン独自の追加検証。工程4
(`nevora-pipeline-verifier`)が実施する。

| 項目 | 内容 |
|---|---|
| 検査項目 | 写真の手配状況 |
| 判定方法 | 記事本文中の`status=pending-photo`を含む消費マーカーの件数を数える(`grep -c 'status=pending-photo'`) |
| 合否 | **この項目自体に合格/不合格は無い。件数(0以上の整数)をそのまま`VERIFY-REPORT.md`に報告する** |
| 総合判定への反映 | 0件 → 他の必須項目(V-01〜V-14・V-16・V-ACC-01・V-VIS-01。V-15はSKIP)がすべてYesなら総合判定は「合格」。1件以上 → 他がすべてYesでも総合判定は「**条件付き合格(写真未手配N件)**」であり「合格」にはしない。他に1件でもNoがあれば件数によらず「不合格」 |
| 差し戻し | 無し。V-17単独では工程2/工程3への差し戻しを発生させない(下記「未手配リストの出力」参照) |
| 未手配リストの出力 | `VERIFY-REPORT.md`に、`HANDOFF-03.md`の画像手配リストから該当行(ID・想定ファイルパス・alt・配置位置)を転記した一覧を出力する。差し戻し指示の表には含めない(差し戻しではないため) |

実施コマンド例(使い捨てスクリプトとして`docs/pipeline/work/`に置いてよい):
```bash
grep -c 'status=pending-photo' <記事ファイル>
grep -oE '<!-- impl:PHOTO-[0-9]{2} status=pending-photo[^>]*-->' <記事ファイル>
```

## 禁止事項

- 実ファイルが無い状態で`![alt](path)`を本文に直接書くこと(404の原因になる)
- `pending-photo`以外の状態フラグを自己判断で発明すること
- `caption`等、既存実装に無いフィールドを追加すること
- アスペクト比・生成ツールの選定など、`content`ブリーフを超える技術的な生成作業を
  工程3が行うこと(工程3の範囲は位置とaltの確定まで)
