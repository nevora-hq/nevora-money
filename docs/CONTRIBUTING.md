# 開発・記事編集ルール

> **会話のコンテキスト圧縮・セッション再開の直後は、作業を再開する前にこのファイルを読むこと。**

NEVORAサイトの品質改善プロジェクトで判明した構造的な問題を踏まえ、今後の作業で必ず守るルールをここにまとめる。

> **このファイルについて(2026-08-28、お金サイトへのジャンル移行時の注記)**
> 本ドキュメントは美容サイト(`nevora-beauty`)で積み上げたルールを、お金サイト(`nevora-money`)へ引き継いだものである。ルール本体はジャンルに依存しないためそのまま有効だが、以下の点に注意すること。
> - 文中に出てくる**具体例・記事名・過去の不具合事例は美容サイト時代のもの**であり、この2026-08-28時点で該当記事はリポジトリに存在しない。ルールの背景を理解するための記録として残している
> - `docs/project-state.md` / `docs/audit-report.md` / `docs/phase*-report.md` / `docs/pipeline/SPEC-EXTRACT.md` など、本文が参照している一部のドキュメントは**移行時に削除済み**。参照先が無くてもルール自体は有効
> - `SPEC-EXTRACT.md` は `nevora-spec-extractor` エージェントで作り直せる(お金サイトの実装を反映した内容が必要になった時点で実行する)

## 1. 記事の編集は必ず一次情報源側で行うこと

`サイト運営\サイト本体\content\articles` は**一次情報源ではない**。`scripts\sync-content.js` が `predev`/`prebuild` 実行時にこのディレクトリを `rmSync` で全削除し、`サイト運営\記事データ\確定稿` と `サイト運営\記事データ\公開済み` から `*.md` を再コピーする(`sync-content.js:24-29,37-49`)。

- **`content/articles` を直接編集しても、次の `next dev`/`next build` で消える。**
- **`content/articles`は2026-08-11よりgit管理外(`.gitignore`の`/content/`パターン)。** 過去にコミットされた分は`git rm --cached`で追跡から除外済み。コミット済みの中身がビルド結果に一切影響しないことを実証した上での対応(詳細は`docs/project-state.md`参照)。ローカルでは引き続き`npm run dev`/`npm run build`実行時に自動生成されるため、意識する必要はない。
- 記事の修正・加筆・削除は、必ず次のいずれかに対して行うこと。
  - 未公開・修正中の記事 → `サイト運営\記事データ\確定稿`
  - 公開済みの記事(Threads投稿後などに移動されたもの) → `サイト運営\記事データ\公開済み`
- ライター・編集長・配信者・レビューアーなど、記事に触れる全エージェント・全作業者がこのルールを守ること。

## 2. 記事専用モジュール(`lib\*Widgets.js` / `lib\*Extras.js`)の新規追加を禁止する

美容サイト時代の `サイト運営\サイト本体\lib` には、特定の1記事のためだけに書かれた専用モジュール(`lipCompareExtras.js`、`hyaluWidgets.js`、`kusumiWidgets.js` など)が14個以上存在し、`lib\posts.js` の `getPostBySlug` 末尾で `if (slug === XXX_SLUG)` という直列分岐によって適用されていた。これが以下の不具合の根本原因になっていたため、**お金サイトへの移行時に全て削除し、`renderChartHtml` は汎用chart typeのみを扱う実装に戻した**。この状態を維持すること。

- 記事ごとに目次・要約・絵文字付与ロジックが個別実装され、共通コンポーネント(`ArticleToc`、`article-summary-box` など)と重複・二重表示を起こす
- 同じ処理(`emojiForHeading` など)が複数ファイルにコピペされ、修正が漏れやすい
- 保守コストが記事数に比例して増え続ける

**今後、記事の特殊な表現・レイアウトを実現するために新しい `lib\*Widgets.js` / `lib\*Extras.js` を追加することを禁止する。**

- 新規記事の図解・比較表・診断・チェックリストなどは、frontmatterの `charts:` / `accordions:` 等の**データ駆動方式**(既存の `type` 一覧を参照)で実現すること。
- 既存の `type` で表現できない見せ方が必要になった場合は、個別モジュールを増やすのではなく、`lib\posts.js` 側の汎用レンダラーに新しい `type` を追加する形で対応を検討し、実装前にサイト制作者エージェント(または担当者)に相談すること。
- 既存14モジュールの統廃合は将来フェーズのバックログとし、現時点では触らない(壊すリスクの方が大きいため)。

## 3. 一人称体験談の書き換えルール(B5)

運営者は個人であり、顔出し・実名・性別は非開示、署名は「NEVORA編集部」である。したがって記事中の「私は〜」「筆者が〜」「実際に使ってみたところ〜」といった一人称の使用体験は、**架空の人物の体験談**であり、実在しない人物の一次体験を事実であるかのように書いていることになる。フェーズ1(2026-08-10)で、この書き換え方針についてユーザーと以下の通り合意した。ライター・レビューアー・編集長の各エージェント定義、およびフェーズ5(既存記事の一括修正)の作業は、この方針に従うこと。

一人称体験談は、必ず次の(a)(b)いずれかに書き換える。

- **(a) 仕組み・理由の説明**: 「なぜそうなるのか」を一般的なメカニズムとして説明する。
  例:「私は化粧水を洗面台の見える位置に置くようにしてから、忘れることが減りました」
  → 「化粧水を洗面台など目につく位置に置くと、視界に入ること自体が行動のきっかけになり、うっかり忘れを減らしやすくなります」
- **(b) 出典付きの一般論**: 公的機関・学会・論文・業界団体・メーカー公式など、実在し裏取り可能な出典を伴う一般的な事実として書く。

(a)(b)いずれにも書き換えられない場合(その記述が個人の体験でしか成立しない場合)は、**その記述ごと削除する。**

**禁止事項**: 出典を示せない伝聞・社会的証明の表現(「という声が多い」「多くの人が」「と言われています」「とされています」等)への言い換えは行わない。これは架空の体験談を架空の伝聞に置き換えているだけで、根拠を捏造している点は変わらないため、一人称体験談と同様に禁止する。

**禁止パターンの明文化(フェーズ5バッチ5、2026-08-11追加)**: 上記の「社会的証明の表現」には、出典で裏付けられない**頻度・多数派の断定**も含まれる。バッチ4・バッチ5で繰り返し発見されたため、明示的に禁止パターンとして列挙する。

- 禁止する表現例:「珍しくない」「珍しいことではない」「少なくない」「よくある」「よく聞かれる」「〜する人は少なくありません」、出典のない「多い」(頻度主張として使う場合)
- 理由: これらは「何割がそうか」を示す出典がないまま、暗に「大多数がそうだ」と読者に思わせる表現であり、伝聞表現の言い換え禁止と同じ問題(根拠のない社会的証明)を含む。
- 代替表現:「起こり得ます」「場合があります」「〜しやすい環境/傾向です」(ただし機序の説明を伴う場合に限る。単に頻度を言い換えただけの「傾向があります」は不可)
- この禁止パターンは、フェーズ6で予定している機械検査(バリデーションスクリプト)の検出語リストにも含めること(`docs/project-state.md` 4節フェーズ6予定を参照)。

**禁止事項の明確化(フェーズ5、2026-08-10追加)**: この禁止事項の趣旨は次の通り。

- 禁止の対象は「出典を示せない内容を『〜と言われています』『〜という声が多い』等でぼかして書くこと」である。
- **出典で裏付けられた内容は、伝聞にせず言い切ること**(「〜です」「〜します」「〜する傾向があります」)。出典があるのに伝聞表現を使うと、せっかく確保した出典の価値を自ら下げることになり、読者の信頼にもつながらない。
- 個人差・不確実性そのものを正直に示したい場合は、伝聞ではなく「傾向があります」「場合があります」「個人差があります」といった表現を使う。

フェーズ5の一人称体験談の書き換え(B5)およびフェーズ5トラック2の出典差し替え作業では、この明確化を提示前のセルフチェックに含めること。

なお、読者に問いかける修辞(例:「そんな経験、ありませんか」)は、著者自身の体験を主張するものではないため、このルールの対象外(書き換え不要)。

**禁止対象の拡張(フェーズ5バッチ2、2026-08-11追加)**: このルールの禁止対象は「一人称の体験談」に留まらず、**実在しない体験・証言の創作全般**に及ぶ。以下も一人称体験談と同様に扱い、(a)(b)いずれかへの書き換え、不可能な場合は記述ごと削除とする。

- **架空の第三者の体験談の創作を禁止**: 「友人に聞いたところ〜」「知人が使ってみて〜」のように、一人称を避けて伝聞形式にしても、実在しない人物の証言を事実であるかのように書いている点は一人称体験談と変わらない。
- **架空の専門家の発言・診断の創作を禁止**: 「税理士さんに〜と言われた」「銀行員さんによると〜」のように、専門家の発言を装う記述は、実在しない権威を借りて記事の説得力を偽装するものであり、**最も悪質な類型として扱う**。
- **「実体験に基づく」「使用体験に基づく」等、記事の裏付けとして実在しない体験の存在を主張する記述を禁止**: 本文中だけでなく、免責文・注記(例:「本記事の使用感は編集部内での個人的な使用体験に基づくもの」)内の記述も対象に含む。

これらも、伝聞表現(「〜と言われています」等)へ言い換えて逃げることは禁止事項(上記)と同じ考え方で禁止する。フェーズ5バッチ2以降の精査では、この拡張範囲を検出対象に含めてセルフチェックすること。

**禁止対象の拡張2: 主語省略の一人称体験談(2026-08-12追加)**: 「私は」「筆者が」等の一人称マーカーを使わず、主語を省略したまま過去形の行動描写を連ねる日記調の文章(例:「棚の前で30分近く迷って、結局その場では決められず、なんとなく安い方のクリームを買って帰りました」)も、実質的に一人称体験談であり禁止対象に含まれる。マーカーの有無だけで判定せず、文章全体が特定の一回性の行動・出来事を時系列で語る個人の日記のような構成になっていないかを確認すること。`scripts/verify-article.js`の項目19が候補を警告として提示するが、正規表現では確実に判定できないため、**最終判断は人間の目視によること**(2026-08-12、「ボディクリームとボディオイルの違い」記事で機械検査〔項目10〕をすり抜けていたことが発覚し追加)。


## 4. 各フェーズ着手前に、直近のコミット履歴を確認すること

このプロジェクトは複数のセッション・作業者が並行して同じコードベースに変更を加える可能性がある(実際にフェーズ1でB2の目次重複バグが、着手前に別セッション/作業者によって既に修正されていたことが判明した。`docs/phase1-report.md` 4節を参照)。

- 各フェーズ(またはフェーズ内の大きな作業単位)に着手する前に、`git log` で直近のコミット履歴を確認し、これから着手する作業対象ファイル・機能と重複または競合する変更が既に入っていないかを確認すること。
- 重複を発見した場合は、フェーズ1のB2と同様に**既存実装を優先**し(自分の変更が未着手・軽微であれば取り下げる)、その旨を完了報告に含めること。

## 5. 商品情報の検証義務(フェーズ5バッチ2、2026-08-11追加)

「くせ毛タイプ別シャンプー比較」の出典検証(トラック2)で、6製品中4製品において**存在しない商品名・公式に記載のない配合成分**がそのまま記事に掲載されていたことが判明した(架空体験談(B5)と同様、根拠のない情報をあたかも事実であるかのように記載していた点で深刻な問題)。以後、商品・製品を扱う記事では以下を徹底する。

- 記事内で言及する**商品名・ブランド運営会社・配合成分・価格**は、メーカー公式ページで実在と現行性を確認してから記載する。ブランド名だけで検索して最初に出てきた情報を無検証で使わない(表記ゆれ・旧製品名・別製品との混同に注意)。
- 公式ページで確認できない情報は記載しない。やむを得ず第三者の成分分析サイト等の情報を使う場合は「(要人手確認)」等でその旨を明示し、確度を偽らない。
- 商品はリニューアル・事業譲渡・販売終了が起こり得るため、比較記事の`sources`には**確認時期**を含める(例:「確認時期:2026年8月」)。運営会社が変わっている場合(例: TSUBAKIの資生堂→ファイントゥデイ)は現在の運営会社を記載する。
- ある製品の紹介文・データ(価格・容量・ポジショニングマップの数値等)の根拠となる配合成分が公式情報と食い違う場合、その製品を紹介枠から外すか、実際に該当成分を含む別製品に差し替えることを検討する(根拠のない製品を「枠を埋めるためだけに」残さない)。

比較系記事(タイトルに「比較」「ランキング」「おすすめ」を含む記事、または本文に具体的な商品名を列挙する記事)は特にこのルールの対象になりやすい。フェーズ5トラック2の一覧作業に「製品情報の検証」列を追加し、対象記事を横断的に確認する(`docs/project-state.md`参照)。

## 6. 記事単位の品質合格基準(フェーズ5、2026-08-11再送)

フェーズ5(既存記事の一括修正)の各バッチで、記事を確定稿へ反映する前に以下5項目でセルフチェックし、結果を1行ずつ報告に添えること。

1. **独自性**: この記事にしかない要素(編集部による成分表示の確認、独自の比較表・図解・診断)が最低1つあること。他サイトの要約・一般論だけの記事は「要増強」とマークして報告する。
2. **体験の真実性**: 実在しない体験・証言(一人称/第三者/専門家)がゼロであること。「実体験に基づく」等の虚偽の裏付け宣言もゼロであること(3節の拡張ルール参照)。
3. **出典**: 記事の中核的な主張に出典があり、URLは実在+記述の裏付けを確認済みであること。「参考として掲載(引用なし)」の水増し出典はゼロであること。
4. **YMYL対応**: 健康リスクに触れる記事は免責+受診/専門家相談の目安があること。
5. **アフィリエイトリンクがゼロであること**(全カット方針のため。2節-10参照)。

## 7. デプロイ運用:バッチ単位コミット・push(2026-08-11追加)

フェーズ5(既存記事の一括修正)のようにバッチ単位で作業を進める場合、複数バッチ分をまとめてコミット・pushせず、**バッチ単位でコミット・pushする**ことを標準とする。

- 1バッチ(記事の承認・確定稿への反映・ビルド検証)が完了するごとに、そのバッチ分をコミットする。
- コミットした上で、ユーザーの許可を得てpushする。push許可の確認は、そのバッチの完了報告に含めてよい(別途改めて確認を取り直す必要はない)。
- 理由: 未pushの変更が長期間・大量に蓄積すると、(1) 本番環境が長期間古いまま放置される、(2) 未反映の修正内容の把握が困難になる、(3) 実際にpushする際のコミット分割・検証コストが増大する、という問題が2026-08-11時点で発生した(直近コミットから約1日半・225パス分の変更が未push状態で蓄積していたことが判明)。バッチ単位でこまめにpushすることで、この蓄積を防ぐ。
- 記事以外(サイトコード修正、ドキュメント更新など)についても、意味のある単位の作業が完了した時点で同様にコミット・push確認を行う。

## 8. 一括処理は対象の妥当性を処理前に検証すること(2026-08-11追加)

フェーズ5終盤で、`updatedDate`を39記事へ機械的に一括付与した際、実際にはB5書き換え等の実質修正を経ていない記事が3件(`置き換えダイエット食品比較`・`季節の変わり目肌荒れ対策`・`毛穴ケア比較`)混入していたことが判明した。原因は、対象リストを「該当コミットで触れられたファイル」から機械的に抽出し、「実際にB5書き換え等の実質修正を行った記事」の正規リストと突き合わせなかったこと。結果として、過去の別コミット(アフィリエイト全カット・編集長基準修正等)でたまたま触れられただけの記事に、実質修正なく`updatedDate`だけが付与される事態になった(9節の禁止する「空更新」に該当)。

- **同一の値・同一の変更を複数ファイルへ機械的に適用する作業(sedループ・一括置換等)を行う前に、対象ファイルリストの生成根拠を明示し、「本当にその変更が必要な状態か」を最低限サンプル確認すること。** 「あるコミットに含まれていた」ことは「そのコミットの主目的の修正を受けた」ことを意味しない。
- 対象件数が多い場合は、全件の詳細レビューまでは不要でも、機械的な整合性チェック(例: `scripts/verify-article.js`の該当項目を全対象に実行し、想定と異なる結果が出ていないか)を一括処理の前後で行う。
- 発見した混入は、以下の順で是正する: (1) 誤って付与された値を削除し実体に合わせる (2) 台帳(`docs/project-state.md`)の記録を実態に合わせて訂正する (3) 実質修正が必要ならこのタイミングで実施する。

## 9. 検出パターンの機械側への還元(2026-08-11追加)

エージェント(reviewer・legal-checker等)が趣旨ベースで、正規表現をすり抜ける変種表現(例: 「〜と説明されています」のような婉曲的な伝聞表現、「〜人は多くありません」のような頻度断定の裏返し表現)を発見した場合、指摘して終わりにせず、その都度`サイト運営\サイト本体\scripts\verify-article.js`の該当正規表現(項目11・12等)に追加し、機械検査側を成長させること。プロンプト指示ベースの検出は再現性が保証されないため、発見したパターンは必ずコードへ還元し、次回以降は機械的に検出できる状態にする。

## 10. 固定ラベル型chart typeの選定基準(2026-08-11追加)

`prosCons`(◎メリット/△デメリット)のような固定ラベルを持つchart typeは、**内容が実際に優劣・賛否の比較である場合のみ**使用する。役割分担・分類の説明(例: 「SPFはUVB対策、PAはUVA対策」のように優劣ではなく対象が異なるだけの関係)には使わず、比較表(Markdown表)や箇条書きなど、ラベルに縛られない型を使うこと。

- 判断基準: そのchartの2つの列は「片方が優れていてもう片方が劣っている」関係か、それとも「単に役割・対象が異なるだけ」の関係か。後者であれば`prosCons`は不適切。
- 違反時の症状: 読者に「AとBのどちらが優れているか」という誤った比較軸を暗示してしまう(2026-08-11、SPF・PA記事のテスト生成で発覚。2026-08-09の受診目安/デメリット混同事例と同種のパターンが再発したため、恒久ルールとして明文化)。
- 該当する場合の対応: chart typeを比較表・箇条書き等に差し替えるか、`prosCons`のラベル文言自体を実態に即した見出し(例: 「守備範囲」「片方だけ見た場合の弱点」)に変更する。

## 11. 画像生成の役割分担(2026-08-11追加)

記事画像を生成するAIツール(Higgsfield等)は未認証のため、AIエージェントが直接画像を生成することはできない。この制約を前提に、**ユーザー画像ライブラリ優先方式**で調達する(2026-08-11、SPF・PA記事のテスト生成で確立)。

**画像調達の優先順位**:
1. **第一候補: ユーザー画像ライブラリ(`C:\Users\kokim\OneDrive\デスクトップ\画像フォルダ\各種サイト\お金サイト\ライブラリ\記事用`)からの選定。** image-selectorがまずこのフォルダを走査し、記事内容に適合する画像を探す。`CATALOG.md`(使用済み管理)と照合し、他記事で使用済みの画像は除外する。新規使用した画像は`CATALOG.md`に使用記録を追記する。
2. **第二候補: 適合画像がない場合のみ、ChatGPT用生成プロンプトを作成してユーザーに提示する。** 構図・スタイル・文字禁止・既存規格(アスペクト比3:2、概ね1536×1024px)に合わせたサイズ指定・保存ファイル名を含める。実際の画像生成はユーザーが外部ツール(ChatGPT等)で行う。ユーザーが生成した画像はライブラリに追加され、次回は上記1の候補として再走査される。

**役割分担**:
- **image-selector**: 上記1→2の優先順位でのライブラリ走査・生成プロンプト作成までを担当する。画像生成そのものは行わない。
- **image-placer**: 選定・生成された画像ファイルの変換(PNG→WebP)・配置、frontmatterの`thumbnail`更新、本文への画像挿入、`CATALOG.md`更新、ビルド確認を担当する。**WebP変換はPython(Pillow)がこの実行環境に既にインストール済みで、追加インストールなしに実行可能(2026-08-11確認)。** 元画像のアスペクト比が既存規格と異なる場合は中央クロップしてから変換する。
- この体制下で`thumbnail`が空文字の記事は「画像生成・配置待ち」として扱い、それ自体を理由に記事の内容面の合格判定(editor-in-chief等)を妨げない。画像配置完了後、`thumbnail`を含めた最終チェックを別途行う。

## 12. 記事の更新日(updatedDate)運用ルール(2026-08-11追加)

frontmatterの`updatedDate`(任意項目)は、`date`(公開日)とは別に、記事ページのヘッダー(「公開日: YYYY-MM-DD / 最終更新日: YYYY-MM-DD」)・構造化データ(`dateModified`)・`sitemap.xml`の`lastmod`に反映される(実装は`lib/posts.js`の`normalizeFrontmatter`・`lib/structuredData.js`の`buildArticleJsonLd`・`pages/sitemap.xml.js`)。

- **更新する場合**: 事実誤認の訂正/製品情報の更新/出典差し替え/セクションの追加削除/B5書き換え等、**読者にとって意味のある実質的な修正**をしたとき。
- **更新しない場合**: 誤字修正・表記ゆれの統一・サイトコード側の表示変更のみなど、本文の実質的な内容が変わらない場合。空更新(意味のない`updatedDate`の書き換え)は禁止する。
- `updatedDate`を追加・変更しても、記事一覧(新着順等)の並び順は`date`(公開日)基準のまま変わらない。

## 13. 検査基準の拡張は過去の合格判定を無効化する(2026-08-12追加)

`verify-article.js`の検査ロジック(検出パターン・スキャン対象範囲)を拡張・強化した場合、**過去にその検査で「合格」と判定された記事は、新基準でのチェックを経ていないため自動的には有効な合格とみなさない**。

- 背景: 2026-08-12、B5(項目10)・伝聞(項目11)等の検査が本文(bodyLines)のみを対象とし、`accordions`/`charts`等frontmatter内の構造化コンテンツをスキャンしていなかったため、「編集部で実際に試した」「私は〜」のような明確な虚偽体験談がaccordion内に残ったまま「修正不要」「公開可」と判定されていた記事(例: `加齢性くせ毛エイジング毛の原因`)が発覚した。この記事は7-2グループAの検品で「修正不要」と判定済みだったが、旧検査基準(構造化コンテンツ非対応)によるものであり、拡張後の基準では不合格だった。
- **対応**: 検査ロジックを拡張した際は、影響範囲(新たにスキャン対象になった構造・検出パターン)を明示した上で、既存の全記事に対して新基準での再検査を実施すること。過去の「合格」「修正不要」の記録は、それがどの検査基準の時点でのものかを合わせて記録し、基準拡張後は鵜呑みにしない。
- **配置・構成ルールの新設・変更も本節の対象とする(2026-08-13追記)**: `verify-article.js`のスキャンロジックだけでなく、CONTRIBUTING/writer/editor-in-chief等に新設した「配置ルール」(視覚要素の配置優先順位・団子の禁止等)も同様に扱う。**「次回の記事制作から適用する」という前提だけで済ませず、既存記事への遡及検証を必ず作業計画に含めること**。2026-08-13、雰囲気写真の配置優先順位ルール((d)図解のない見出し優先)を新設した際、「今後の新規記事から適用」という理解のまま直近3記事の既存画像配置を再検証せず、結果としてルール新設後もルール違反の配置(まとめ直下・診断直後等)が3記事とも残ったまま「対応済み」として報告してしまった事例が発生した。ルールを書いた時点で、既存記事(直近の対象記事に限らず全記事)への適用要否を必ず検討し、対象範囲を明示すること。
- **新規ブロッキング項目の追加時は`npm run verify:all`の全記事実行を完了報告に必須で含める(2026-08-14追記)**: `scripts/verify-article.js`へ新規のブロッキング項目を追加した場合(既存項目の判定ロジック変更を含む)、**その項目に限定した公開済み全記事(該当すれば確定稿・下書きも)への一括実行結果を、その作業の完了報告に必ず含めること**。一括実行は`サイト運営\サイト本体`で`npm run verify:all`を実行することで行う(`scripts/verify-all-articles.js`、記事ごとのoverall・違反項目番号とフォルダ別サマリを出力する)。背景: 2026-08-14、項目31(自己参照の誘導文検出)を新設した際、直近に触れた記事(美顔器・白髪ぼかし)のみを確認し、同時期に別の理由で編集していた前髪記事や、それ以外の公開済み全記事への一括確認を行わなかったため、前髪1件・他8記事(9箇所)の項目31違反が発覚まで数ターン素通りしていた。「口頭での確認」ではなく`npm run verify:all`というコマンドに紐づけることで、確認の有無を機械的に検証可能にする。
- **`lib/posts.js`のレンダリングロジック変更時は`npm run verify:rendered`の全記事実行を完了報告に必須で含める(2026-08-14追記、22節参照)**: `verify-article.js`はfrontmatter/本文Markdownソースのみを見る設計であり、実際のHTML描画結果(`lib/posts.js`のembedCharts/embedAccordions/splitHtmlBlocks等)を一切検証しない。そのため`lib/posts.js`のレンダリングロジックを変更した場合(記事の追加・削除を伴わない場合も含む)は、`npm run verify:rendered`(項目33)を実行し、不一致0件を確認した上で完了報告に含めること。

## 14. 数値修正時は記事内の全出現箇所を確認すること(2026-08-12追加)

同じ数値(年代別の日数、価格、時間等)が`charts`のdata・本文・`summaryPoints`・`description`・まとめ等、記事内の複数箇所に重複して書かれている構造は、修正漏れのリスク源になる。

## 16. 出典なし伝聞表現(項目11)が大量に残る記事への対応方針(2026-08-13追加)

`verify-article.js`項目11は、「〜と言われています/とされています」等の伝聞表現に同一文中の出典表示(丸括弧または`[リンク]`)を必須とする。Part3バッチ4〜6の総点検で、1記事あたり10〜20件以上この違反が残る記事が複数見つかった(睡眠の質を上げる寝具と寝室環境:22件、頭皮がかゆい原因:12件など)。これは記事固有の問題ではなく、「効果断定を避けるため慎重な言い回しを多用する」というサイトの執筆スタイル自体に起因する構造的パターン。

**対応方針(2026-08-13ユーザー承認)**: 文脈上重要な文のみ出典明示、それ以外は断定表現に緩和する。ただし以下の歯止めを必ず守ること。

- **出典明示側に必ず分類する文**(一般論への緩和は禁止):
  - 数値・割合・期間を含む文(例:「洗浄成分は3タイプに分かれると言われています」の3タイプ自体は一般論でよいが、「1日50〜100本」等の具体的数値を伴う主張は出典明示)
  - 団体名・制度・ガイドラインに言及する文
  - 効果・効能を主張する文(「〜に効果的と言われています」等)
- **断定表現への緩和が許容される文**: 仕組み・分類・定義レベルの一般的知識に限る(例:「髪には成長期と休止期がある」「肌は角質層で覆われている」等、複数の一次情報で広く確立された基礎知識)
- **判断に迷う文は出典明示側に倒す**(緩和を優先しない)
- **記録義務**: 記事ごとに「断定化した文の数 / 出典明示にした文の数」をバッチ完了報告に記載し、断定側に極端に偏っていないか確認を受けること
- verify-article.js自体(項目11のロジック)は変更しない。あくまで記事本文側の対応で解消する。

**線引きの明確化(2026-08-13、バッチ7-9の抜き取り検査を受けて追記)**: 「仕組み・分類・定義レベルの一般的知識」という基準は曖昧になりやすく、実際に以下3件が誤って断定表現に緩和されていた(抜き取り検査で発見・是正):
1. 「乾燥タイプは頭皮の水分・皮脂不足でバリア機能が乱れ、外部刺激を受けやすくなる」(頭皮がかゆい原因) — バリア機能の機序自体は生理学的な主張であり、出典明示に戻した
2. 「高級アルコール系の成分は刺激になりやすい」(同記事) — 成分カテゴリ×刺激性の対応づけは効果主張に該当。出典が見つからなかったため「人によって刺激を感じることがある」という個人差表現に弱めた
3. 「たんぱく質は毎食均等に摂るほうが体に使われやすい」(ダイエット中の食事管理) — 一見基礎知識に見えるが、実際はタンパク質合成の分配効果という学術トピックであり、出典明示に戻した(日本スポーツ栄養協会の一次情報を追加。研究間で見解が分かれる点も明記)

この教訓から、断定化してよい範囲を次のように絞り込む:
- **体の中で何が起きるかの機序**(バリア機能・血糖値の変動・タンパク質合成・ホルモンの働きなど)は、たとえ広く言われている内容でも出典明示側に分類する
- **成分カテゴリ×効果/刺激の対応づけ**(「〇〇系成分は△△に効く/刺激になる」等)も同様に出典明示側に分類する
- 断定化してよいのは「観察可能な事実」(例:キューティクルはうろこ状に重なっている)・「行動の帰結」(例:洗いすぎると必要な皮脂まで落ちる)・「制度的事実」(例:医療脱毛は医師法上医師のみが行える)に限る

## 17. YMYLテーマの出典は学会・公的機関を優先的に再探索すること(2026-08-13追加)

## 18. `disclaimer: none` フィールドの用途(2026-08-13追加)

一部記事のfrontmatterに `disclaimer: none` という値が入っている。これは「本記事には個別の免責注記が不要」であることを示す内部管理用のフラグであり、読者向けに表示される文言ではない(表示側の実装は`disclaimer`が未設定/`none`の場合に免責ブロックを描画しない)。about.js・privacy-policy.js側にこの値自体への言及・説明は不要(サイト全体の免責事項はprivacy-policy.js/terms.jsで一括カバーされているため)。新規記事で個別の免責注記が不要と判断した場合は `disclaimer: none` を明示的に設定し、フィールド自体を省略しない(省略と`none`明示を区別しないと、意図的に不要と判断したのか単なる書き忘れなのか後から区別できなくなるため)。

## 19. frontmatter(description等)は本文と同じ厳格さで検査すること(2026-08-13追加、サイトレベル整合性監査を受けて)

**発見**: 2026-08-13のユーザー監査で、「16時間断食」記事のdescriptionに「体験談を交えて解説します」という体験談を約束する文言が残っていた。本文の一人称体験談はB5ルールにより既に削除済みだったため、「読者への告知(description)」と「本文の実態」が矛盾していた。追加調査で同種の残存が確定稿・公開済みだけで10件、下書きにも複数件見つかった。

**見落とし原因**: 項目10(B5違反検出)は2026-08-12の改修で`extractStructuredTextBlocks`によりfrontmatterのdescription/summaryPoints/accordion等も検査対象に含めていたが、検出パターン(`RE_B5_FAKE_EXPERIENCE`等)が「実際に使ってみた」「使用体験に基づく」等、**本文の一人称体験談の言い回し**を基準に作られており、「体験談を交えて解説します」「実体験を交えて解説します」のような**meta description特有の告知・予告表現**は語形が異なるため検出パターンに一致しなかった。過去の浄化バッチは本文の体験談削除に集中しており、frontmatterの「予告文言」が本文修正と同時に更新されているかを機械的に確認する手段がなかった(目視レビューでも見落とされた)。

**恒久対応**: `scripts/verify-article.js`に`RE_B5_EXPERIENCE_PROMISE`(「体験談を交えて」「実体験を交えて」「効果を感じた/実感した」「検証してみた」等)を追加し、項目10の検出パターンに組み込んだ(2026-08-13)。また`fm.disclaimer`も`extractStructuredTextBlocks`の抽出対象に追加し、免責文内の虚偽裏付け宣言(3節参照)も項目10で機械検出されるようにした。

**教訓**: 検出パターンを設計する際は「本文でよく使われる言い回し」だけでなく、「frontmatterの各フィールドが持つ独自の文体・目的」(descriptionは読者への告知・約束、summaryPointsは箇条書きの要約、disclaimerは免責文、accordion.summaryは開閉ボタンの誘導文)ごとに、その文脈特有の言い回しを想定して検出パターンを設計すること。「本文用パターンをfrontmatterにも適用すれば足りる」という前提は誤りだった。

## 20. quadrantチャートのフォールバック表で評価記号(◎○△)を使わない(2026-08-13追加)

`type: "quadrant"`チャートのフォールバック表(JS非対応環境向けの表形式データ)は、以前は座標値を◎(高い)/○(中)/△(低い)の記号に変換して表示していたが、**◎○△は「良い/悪い」という評価の含意を持つため、軸の向き次第で誤読を招く**。

- 背景: 「ネイルサロン vs セルフネイル比較」記事のquadrantチャートで、Y軸(費用感、値が高いほど高額=悪い)においてサロンの値が高く◎がついていたため、「サロンは費用面で優れている(安い)」と誤読されるリスクがユーザー監査で指摘された。
- **対応**: `lib/posts.js`の`renderQuadrantChartHtml`を修正し、記号ではなく中立的な高低表現(「高い/中程度/低い」)をデフォルトのフォールバックとした。さらに、chartsの`data`各項目に`xNote`/`yNote`(文字列)を指定すると、そちらが自動生成の高低表現より優先され、記事の本文記述に即した具体的な文言(例:「長め(約3〜4週間)」「個人差大」)を表示できる。
- **新規記事のルール**: quadrantチャートで軸の値の大小が「良い/悪い」に単純に対応しない場合(例: 費用・時間・負担など、低いほうが良いことが多い軸)は、`xNote`/`yNote`で本文の記述と一致する具体的な文言を明示すること。単純に「高い方が良い」と読める軸(満足度等)であっても、記号ではなく言葉のほうが誤読リスクが低いため、迷ったら`xNote`/`yNote`を使う。
- **既存記事への遡及**: 記号除去そのものは`lib/posts.js`の共通レンダラー修正により全quadrantチャートに自動適用済み(記事側の追加修正は不要)。ただし`xNote`/`yNote`未指定の既存記事は「高い/中程度/低い」という一般的な表現になるため、軸の意味によっては本文の記述とニュアンスが完全に一致しない可能性がある。該当記事一覧は`docs/pipeline/quadrant-chart-audit.md`を参照し、必要に応じて`xNote`/`yNote`を追記する。

## 21. frontmatterのdate/updatedDateはYYYY-MM-DD形式で統一する(2026-08-13追加)

新規記事(2026-08-13_ネイルサロンvsセルフネイル比較)で`date: "2026-08-13T09:00:00+09:00"`のような時刻付きISO8601形式が使われ、記事ページの日付表示がISO生文字列のまま崩れて表示される不具合がユーザー監査で発覚した。既存記事の一部にも同形式が混在していた(確定稿・公開済み126記事中69記事)。

- **frontmatterの`date`/`updatedDate`は必ず`"YYYY-MM-DD"`形式(時刻を含めない)で記載すること。** 時刻情報は記事の表示・機能のどこでも使われていない。
- **表示側の恒久対策**: `サイト運営\サイト本体\lib\formatDate.js`を新設し、日付を画面表示する箇所(`pages\posts\[slug].js`の記事ヘッダー、`pages\admin\articles.js`の記事一覧)は必ずこの関数を経由して整形する。YYYY-MM-DD形式・時刻付きISO8601形式のどちらが渡されても`YYYY-MM-DD`に整形されるため、今後frontmatter側に形式の揺れが残っても表示は崩れない。

- 既存69記事のfrontmatterは表記形式の統一(値そのものの変更ではない)としてYYYY-MM-DD形式へ一括変換済み。この変換は`updatedDate`の新規追加・値の書き換えを伴わない(8節の「空更新の禁止」に抵触しないよう、`date`/`updatedDate`いずれも既存の値の表記形式のみを変えた)。

## 22. 複数記事横断コンポーネントはカテゴリ・文脈を無視した単純な日付順/配列順選定にしないこと(2026-08-13追加)

`lib/posts.js`の`getNextPost`(記事ページ「次の記事へ進む」)が、全記事を公開日順に並べただけの配列から単純にインデックス+1(末尾は先頭へ循環)で次記事を選んでいたため、カテゴリを一切考慮せず「美容サービス」記事の次に「ダイエット」記事が表示される不具合があった。SPF・PA関連記事でも同種の事象が過去に確認されており、同じ失敗パターンの再発だった(2026-08-13修正)。

- **典型的な失敗パターン**: 「複数記事から1件(または数件)を選んで表示する」コンポーネント(次の記事/前の記事、関連記事、おすすめ記事、カテゴリカードのピックアップ等)を実装する際、実装の手間を省くために「全記事配列を日付順や登録順に並べ、その並び順だけで機械的に選ぶ」実装にしてしまいやすい。一見動作しているように見える(常に何かしらの記事が表示される)ため、見た目のバグとして気づきにくく、実際にカテゴリの異なる記事が表示されて初めて発覚する。
- **対応**: このようなコンポーネントを新規実装・修正する際は、単純な日付順/配列順を採用する前に、「読者が今読んでいる記事の文脈(カテゴリ・タグ・悩みslug等)と無関係な記事が選ばれ得ないか」を必ず自問すること。優先順位のあるフォールバック(同カテゴリ→タグ一致→非表示、等)を設計し、「該当なしなら表示しない」を許容する(存在しないつながりを無理に表示しない)。
- 修正後の`getNextPost`は、同一カテゴリ内で公開日が近い記事を優先し、同一カテゴリに他の記事が無い場合のみ悩みタグ(`worry`)一致で代替、それも無ければ「次の記事へ進む」自体を非表示にする方式にした。

## 23. タイトルが約束する視覚要素・出典の実在を、レンダリング結果ベースで確認する(2026-08-13追加)

「〇〇の仕組みを図解でやさしく解説」のように公開後の白髪ぼかしハイライト記事が、パイプライン全工程(ライター・レビューアー×2・法務×2・verify×3・編集長)を通過して公開されたにもかかわらず、quadrantチャートの`data`配列を誤って`items`というキー名で書いていたため`lib/posts.js`の`renderQuadrantChartHtml`が`data`未定義で空文字列を返し、タイトルが約束する「図解」が本番で一切表示されない状態のまま公開されていた(2026-08-13発覚)。

## 24. 「図」の定義とSVG図解レンダラーの使い分け(2026-08-13追加)

新規5記事のうち3記事(前髪/家庭用美顔器/白髪ぼかしハイライト)が「1見出しに文字が詰まり、読者が離脱する」水準とユーザー評価で判定された。第一弾の対応として`steps`型・`diagnosis`型のchartを見出し直後に追加したが、ユーザーの実機確認で**不合格**と判定された。理由は「コマ間・項目間の違いが絵から読み取れない(文字を読んで初めて差が分かる)」ため、これは「図」ではなく「テキストの整形」にとどまっていたこと。

- **「図」の定義**: 概念・仕組み・変化を、**イラスト+文字の説明のセット**で見せるもの。文字だけを整形して並べたもの(番号付きリスト、チェックリスト、カード状に並んだテキスト)は図ではない
- **図に分類しないchart型**: `steps`(番号付き手順リスト)・`checklist`(チェック項目リスト)・`flowchart`/`diagnosis`(対話的なテキストUI、イラストを伴わない)。これらはタイトルに「診断」等の語を含めても図としては扱わない(`scripts/verify-article.js`項目24でこの分類を機械判定する)
- **図に分類するchart型**: `quadrant`/`faceMap`/`lineChart`(位置づけ・分布を視覚エンコードする実チャート)、および新設した`crossSection`(断面/構造図型)・`depthComparison`(深さ/到達範囲比較型)・`processContrast`(プロセス/対比型)。後者3つは`lib/posts.js`にデータ駆動のSVGレンダラーとして実装済み(色・ラベル・形状パラメータをfrontmatterのchartsから指定する、既存chart群と同じ仕組み)
- **AI画像生成は図解に使わない**: 文字が崩れる・修正が困難という理由から、概念・仕組みの図解にはAI画像生成を使わず、上記のSVGレンダラーで実装する。雰囲気写真・サムネイルは従来通りAI画像生成でよい
- **虚偽参照の禁止**: 本文中で「上の図」「下の図」「上記の図表」等の参照語を使う場合、参照先の見出しセクションに実際に図(上記のHIGH型chart)または画像が存在することを確認すること。`scripts/verify-article.js`項目26で機械チェックする(ブロッキング)。図の実装前に参照文だけを書かない
- **プロセス/対比型(`processContrast`)の設計原則(2026-08-13確定、Rev.3で最終化)**: 白髪ぼかしハイライト記事のモックアップで3回の判定を経て確定した原則。各コマはラベルを隠しても違いが分かることを設計基準とする
  - **モチーフは実物の簡略イラスト(通帳・カード・グラフ・書類等)を土台にする。抽象図形(縞・棒等)の変化だけで差を表現しない**(Rev.1/Rev.2は抽象的な縞モチーフで「ラベルを読まないと差が分からない」と判定され不合格になった)
  - **コマ間で「同じ場所にあり続ける要素」(例: 白髪)は、位置・色とも完全に固定する。**要素が消えた/移動したように見える表現は禁止。「なくなった」という誤ったメッセージになるため、変化するのは周囲の要素の色だけにする
  - **コマ数は2(Before/After)を既定とする。**3コマ目(中間コマ)を使うのは、その中間コマが「過程・動作」として明確に意味を持つ場合のみとし、単に色数を増やしただけのコマを挟まない(白髪ぼかし記事の「ハイライト追加中」コマが「色が増えただけで動作が読み取れない」と判定され、2コマ構成に確定した経緯による)
  - 意味の分からない装飾要素(データを表さないマーカー等)を置かない

## 25. 視覚要素の配置ルール(400字ルール・団子の禁止・雰囲気写真の優先順位)(2026-08-13追加)

図解3型(crossSection/depthComparison/processContrast)を新規3記事に適用したところ、ユーザー実機確認で「図解を見出し直下に置き、直下に雰囲気写真が連続する視覚要素の団子。その先の文章の壁は解消されていない」と判定された。図解の**質**は合格していたが、**配置**が誤っていたための不合格。以下を配置の大原則として確定する。

### (a) 300字ルール(ブロッキング、`scripts/verify-article.js`項目23、2026-08-13再々改訂)
改行(空行)を挟んでも実際の視覚要素(画像・チャート/アコーディオン〔見出しに紐づくもの〕・表・コールアウトボックス)に一度も当たらないまま地の文が合計300字以上連続することを禁止する。空行だけでは連続はリセットしない。
- NG例: 150字→改行→180字(計330字連続、視覚要素なし)
- OK例: 250字→視覚要素→200字
- **閾値は当初400字だったが、ユーザーの実機確認で「400字でも文章の詰まりが体感として解消されない」と判定され、2026-08-13に300字へ引き下げた**
- **見出し自体(H2/H3)はリセット条件に含めない**。図解・アコーディオンが紐づいていない見出しは、ただの太字テキストであり視覚的休憩にならないため、見出しをまたいでも連続はリセットされない(2026-08-13、家庭用美顔器記事のEMS/RF/イオン導入/超音波という4連続H3〔個々のH3見出しには図解が紐づいていない〕が、H3ごとに独立してリセットする旧実装のもとで合計1,199字の壁を形成していたのに検出をすり抜けたため厳格化した)
- **箇条書き(list)もリセット条件に含めない**。箇条書きはテキストの整形であり視覚的な間にはならないため、項目の文字も地の文としてカウントに含める(2026-08-13、白髪ぼかしハイライト記事で2項目のみの短い箇条書きを挟んだだけで385字の壁が「解消」扱いになり、実際には壁が残ったまま合格していたため厳格化した)
- **区切り線(`---`)もリセット条件に含めない**。詳細は(e)の追記を参照(2026-08-13、この除外は当初(e)にのみ追記されコード・本項の列挙には反映されていなかった。300字改訂時に本項の列挙からも「区切り線」を削除し、コード〔`verify-article.js`〕とも整合させた)
- **Markdownリンク`[表示テキスト](URL)`は、表示テキストのみをカウントし、URL・角括弧・丸括弧はカウント対象から除外する(2026-08-15、L1決裁)**。修正前は記法全体(URLの日本語スラッグ込み)をそのままカウントしており、「関連記事」等の内部リンクリストが地の文の分量を実際より水増ししていた。全記事シミュレーションで影響を検証し(のべ違反285→253件、item23違反ファイル数125→121件)、`npm run verify:all`の実行結果が完全一致することを確認してから反映した(バッチ2〔脂性肌・混合肌8記事〕での13件の元violationはこの仕様変更前後で1件も解消しておらず、アコーディオン化等の対応は仕様と無関係に必要だったことも確認済み)

### (b) 400字超の正規の解消手段は「内容の図解化」
400字を超える説明は「削る」のではなく、**その説明の内容そのものを図解に変換する**ことで解消するのを優先する。
- 優先対象: 難しい説明・科学的な機序・手順・分類・比較(文章で読むと重い内容ほど図解化の価値が高い)
- 変換に使う型: 3型(crossSection/depthComparison/processContrast)+既存chart群(表・箇条書き等)
- **chartはafterHeadingで見出しに紐づけるため、必ず見出しの直下(先頭)に挿入される。文章の「途中」を割りたい場合は、その位置にH3見出しを新設し、そこに図解を紐づけることで実現する**(2026-08-13、白髪ぼかし記事の「白髪が生えるのはなぜ」セクションで、段落の途中に新規H3「白髪が生えるまでの流れ(仕組み図)」を追加しcrossSectionを紐づけて解消した実例による)
- どの型でも表現できない場合のみ、文章の分割・要約(箇条書き化・表への要約等)で対応し、その理由を明記する(図解化を検討せず安易に分割しない)

### (c) 挿入要素の内容条件
400字ルールを満たすために挟む視覚要素は、**直前の文章の内容を視覚化・整理・要約したもの**に限る。直前の文脈と無関係な図・グラフ・写真を挟んでもルールを満たしたことにならず、むしろ違反として扱う。この一致は機械判定が困難なため、editor-in-chiefの目視必須項目とする。

### (d) 雰囲気写真(人物・情景。図解・グラフ・表以外の画像)の配置優先順位
1. 図解・グラフ・チャートが入っていない見出しの直下に配置する(視覚要素ゼロの見出しを写真で補う)
2. 該当する見出しがない(全見出しに図解等がある)場合は、文章量が多い見出しの直下を優先する
3. 同一見出し直下への視覚要素の重複配置(図解+写真等の団子)は禁止する

役割分担: **図解=見出し内の「間」(文章の壁を割る)** / **写真=見出し切り替わりの「呼吸」**。この配置決定は機械判定可能なため、`writer.md`の画像指示と`image-selector.md`の配置ロジックに組み込む。

**新設・変更したルールは、新規記事だけでなく既存記事にも遡及検証すること(13節参照)。** 2026-08-13、本節(d)を新設した直後の3記事修正で「次回の記事制作から適用する」という前提のまま既存の画像配置を再検証せず、結果としてルール新設後も違反配置(まとめ見出し直下・診断チャート直後等)が3記事とも残ったまま「対応済み」と報告してしまう事例が発生した。ルールを書いた時点で、対象とする記事の画像配置を機械的に洗い出し、違反があれば構成マップに含めること。

### (e) 視覚要素の連続配置は「違和感」の有無で判定する(2026-08-13最終改訂、非ブロッキング・`scripts/verify-article.js`項目27)
**視覚要素(chart・アコーディオン・画像・表・コールアウトボックス)の連続配置そのものは禁止しない。** 連続していても、対の関係・補完関係にあり読者に違和感なく流れるなら問題ない(例: `processContrast`で変化を見せた直後に`quadrant`で要因の位置づけを見せる、のような役割分担が明確な組み合わせ)。**問題になるのは「脈絡のない連続」による違和感のみであり、これは機械では判定できない。**

- **判定フロー(視覚配置全般の標準運用とする)**:
  1. `scripts/verify-article.js`項目27が、本文(地の文)を挟まない視覚要素の連続配置をすべて検出し、**候補リストとして出力する(非ブロッキング・機械が修正はしない)**
  2. editor-in-chiefが一次判定する。判定基準は「この連続は対・補完の関係として自然に流れるか、それとも脈絡がなく違和感があるか」。**明らかに脈絡のない連続のみ修正を提案し、判断に迷うものは『ユーザー確認』として残す**
  3. ユーザーが最終判定する。そのため、新規記事の公開前報告・既存記事の対応時のいずれも、**連続箇所リスト(見出し名+要素の並び)を必ず報告に含める**(ユーザーが該当箇所だけを実機で見て判定できる形にする)
- 個数制限(FAQ形式のaccordion連続本数の上限等)は設けない。すべて目視判定の範疇とする
- 背景: 初版は「チャート種別を問わず連続配置を例外なくブロッキング検出する」設計にしたが、この結果「見出しに紐づく複数のchart/accordionはすべて団子」という機械的な扱いになり、FAQのQ1→Q2のような自然な連続や、事前確認チェック+仕組み図解のような妥当な組み合わせまで一律に分離・受け本文の挿入を強制することになった。ユーザー判定により、「連続の可否は違和感の有無で決まり、機械は候補を挙げるだけ、人間が判定する」方式に確定した
- **区切り線(`---`)はリセット要素に含めない(2026-08-13追加)**: 視覚的な間として弱く、400字ルール(a)の「間」としても機能しないため、item23のリセット判定には使わない。見出しの手前で壁を分割したい場合は、区切り線ではなく「直前の本文を短縮する」「コールアウト・表等の実質的な視覚要素を置く」で対応する(2026-08-13、「まとめ」見出しの直前を区切り線だけで分割しようとして分割効果が無いと判明した事例による)

### (i) 装飾密度ルール(2026-08-14追加)

直近3記事の実機確認で「絵文字・`==`・`^^`・コールアウトが冒頭2〜3見出しに集中し、後半(まとめを含む)がほぼゼロになる」という装飾密度の後半失速が判明した。新記法・新CSSは追加せず、既存語彙(絵文字/`==`/`++`/`^^`/`%%`/コールアウト)の**分布**を是正することで対応する。

- **最低密度**: 本文100字以上あるH2セクションには、絵文字・`==`・`^^`・コールアウトのいずれかを最低1つ含める。この基準は記事後半・「まとめ」セクションにも同様に適用する
- **上限**: 1段落内の`==`・`++`・`^^`は合計2つまで。絵文字は1文に1つ・1段落に2つまで。1見出し内のコールアウトは2つまで
- **使い分け基準**: `==`=読者が持ち帰るべき要点そのもの/`^^`=気づき・感情の変化/絵文字=共感フック・話題転換のリズム/コールアウト=独立した注意点・ポイント
- **ノルマ埋め装飾の禁止**: 密度基準を満たすためだけに接続詞・助詞など意味のない箇所へ機械的にマーキングしない。同一フレーズへの二重装飾(`==^^同じ語句^^==`等)も禁止
- **YMYL例外**: 安全性・法規制・措置命令等の事実記述では、絵文字・`^^`のような感情装飾を使わない。事実は淡々と示し、必要な強調は`%%`注記かコールアウト(注意ボックス)のみで行う
- **AdSense観点の根拠**: 過剰な装飾(全文が色文字・絵文字だらけ)は低品質・スパム的コンテンツのシグナルになり得るため、下限だけでなく上限も必須である
- **素のblockquote(`💡`/`⚠️`/`⏱`/`🔍`のいずれのアイコンとも一致しない引用)の新規使用を禁止する**。内容に応じてNEVORAポイント・注意ボックスのどちらかに寄せる
- **項目32(装飾密度の後半失速検出、警告・非ブロッキング)**: H2見出しごとに(絵文字+`==`ペア+`^^`ペア+コールアウト数)を装飾スコアとして算出する(絵文字の定義は項目4と同じ`EMOTION_EMOJI`固定リスト、地の文・箇条書きのみが対象で見出し内・コールアウトのアイコン絵文字はカウントしない)。本文100字未満のH2はスコア対象外。スコア対象H2を文書順で前半/後半に2分し、後半平均スコアが前半平均の30%未満なら`backHalfSlowdown.flagged=true`とする。スコア0の100字以上セクションも個別に`zeroScoreSections`へ列挙する。「意味のある装飾か」は機械判定できないため、item27・item30と同じく候補提示のみでブロッキングしない

**検査項目の総数について**: `scripts/verify-article.js`の項目数・ブロッキング項目数の唯一の正はコード自体(`main()`内の`items`配列と`result: "N/A"`の有無)である。2026-08-14時点のスナップショットは全33項目(実効32: 項目7は同日ユーザー決裁により廃止・永久欠番/ブロッキング25・非ブロッキング7〔項目18・19・20・25・27・30・32〕)。項目34(crossSection leaderラベル同士の衝突検出)を同日追加。この数値は今後の項目追加で変わるため、`nevora-pipeline-verifier.md`等の他ドキュメントで数値の食い違いに気づいた場合はコードを実行して数え直し、ドキュメント側を修正する(2026-08-14、複数ファイルに書かれた項目数が同期されず「22項目」「17→25」等の食い違った数値が併存していた事故の再発防止)。

**項目7(連続プレーンテキストの上限・200字)の廃止(2026-08-14)**: 地の文連続の基準は項目23(300字ルール、本節(a)参照)に完全一本化した。200〜299字帯の地の文連続は項目23が意図的に許容している範囲であり、違反として扱わない。廃止前の安全ゲート検証で、下書き9記事中6記事に「項目7のみ検出・項目23はPass」という箇所が見つかったが、これは項目23が許容する範囲を項目7がより厳しい閾値(200字)で検出していただけであり、ユーザー決裁によりこれらは違反ではないと確定した。項目番号は履歴整合のため永久欠番として維持し、振り直しはしない(`scripts/verify-article.js`の`checkItem7`は常に`result: "Yes"`を返す無効化スタブとして残す)。詳細な経緯は`docs/project-state.md` 17.1.1節参照。

## 26. 昇格ゲート・公開後の信頼性違反対応(2026-08-14追加)

`npm run verify:all`による全154記事の初の網羅スキャンで、下書き23記事に大量のitem10/11/12違反(B5架空体験・伝聞・頻度断定)が残存していることが判明した一方、公開済み・確定稿の131記事は既存の手編纂リストベースの浄化作業(フェーズ5・シリーズ30・Part3総点検・グループB/C)だけでは発見できていなかったBLOCKER4件(公開済み2件・確定稿2件)が別途見つかった(project-state.md 15.5節参照)。これらはいずれも「機械的な全件検査を一度も通していない記事が、通したことにして扱われていた」という同型の事故であり、以下2点を恒久ルールとして明文化する。

### (a) 下書き→確定稿→公開済みの昇格条件

- **下書き→確定稿への昇格、および確定稿→公開は、`scripts/verify-article.js`の全ブロッキング項目Passを必須条件とする。** 昇格・公開を行う担当(project-manager/publisher等)の作業報告には、`node scripts/verify-article.js <対象ファイル>`(または該当記事を含む`npm run verify:all`)の実行結果を必ず含めること
- 口頭・目視だけでの「チェック済みのはず」という申告は昇格条件を満たさない。実行結果(overallとviolated itemsの一覧)を報告に添付する
- この条件は新規追加のブロッキング項目にも自動的に及ぶ(13節の遡及検証義務と合わせて、新項目追加時は下書き→確定稿の昇格待ち記事も再検査対象に含める)

### (b) 公開済み記事に信頼性系ブロッキング違反が見つかった場合の対応

- **item10(B5架空体験)・item11(伝聞)・item12(頻度断定・社会的証明)・出典不整合等、「絶対条件1(a)(b)」(虚偽・伝聞・裏付けなし断定)に直結する信頼性系のブロッキング違反が公開済み記事で発見された場合、即時修正を原則とする**
- 修正に時間を要する(裏付け調査が必要、書き換えの方向性が未確定等)場合は、**修正完了まで該当記事を非公開化し、確定稿へ差し戻す**
- **非公開化の実行(記事の公開停止)は、性質上「サイト上のコンテンツを取り下げる」という後戻り可能だが影響のある操作のため、必ずユーザー決裁を経ること**。機械検査が違反を検出したことだけをもって自動的に非公開化しない

### (d) 下書きフォルダの廃止(2026-08-19追記)

上記(a)で問題となった`サイト運営\記事データ\下書き\`(23記事)は、**2026-08-19にフォルダごと削除した**。理由は以下の通り。

- 23本すべてに公開版が存在し(公開済み21・確定稿1・リライト元記事1)、いずれも公開版のほうが大幅に長い完成版だった。下書きは公開前の初稿の残骸であり、公開版にあって下書きにない情報は多数ある一方、その逆はほぼ無かった
- 18本に未検証の一人称体験談(「私も〜」等)が残存しており、これを「使える原稿」と誤認して公開すると、アドセンス審査・ステマ規制上の問題が再発する温床だった
- 同名ファイルが2箇所に存在するため、grep検索が二重にヒットし、`sync-content.js`の対象外である下書き側を誤編集して「修正したつもりで反映されない」事故を招く構造だった
- 全23本がgit追跡済みのため、履歴から復元可能

これに伴い、(a)の「下書き→確定稿への昇格」という工程は現在存在しない。**執筆途中の原稿は`サイト運営\実務\ライター\`に置き、確定稿へ保存する時点でverify-article.jsの全ブロッキング項目Passを必須とする**、という形に読み替える。`scripts/verify-all-articles.js`の走査対象からも下書きを除外済み(公開済み・確定稿の2フォルダのみ)。

## 31. サムネイル画像のセーフゾーン規則(2026-08-16追加、UVAとUVB記事のサムネ下端切れ対応で新設)

記事のサムネイル画像(`thumbnail`)は、コンテキストによって異なるアスペクト比でクロップ表示される(記事ページのヒーロー=`16:9`・`object-fit:cover`、カード=`1:1`・`object-fit:cover`)。**重要なテキスト・要素(タイトル・キャプション・図解の本体等)は、両方のクロップに共通して残る「セーフゾーン」の内側に収めること。**

### 31-1. セーフゾーンの算出根拠

このサイトのサムネイル生成は`3:2`(例: 1536×1024px)を基準とする。`3:2`の画像を`16:9`と`1:1`それぞれに中央基準でクロップした場合に生き残る領域を算出し、その積集合をセーフゾーンとする。

- `16:9`クロップ(横幅そのまま、縦をクロップ): 縦方向の残存率 = `(3:2の縦横比)/(16:9の縦横比)` = `1.5/1.7778` ≈ `84.4%`。上下から均等に`7.8%`ずつクロップされる。→ **縦方向セーフゾーン: 上端7.8%〜下端92.2%(中央84.4%)**
- `1:1`クロップ(縦幅そのまま、横をクロップ): 横方向の残存率 = `(1:1の縦横比)/(3:2の縦横比)` = `1/1.5` ≈ `66.7%`。左右から均等に`16.7%`ずつクロップされる。→ **横方向セーフゾーン: 左端16.7%〜右端83.3%(中央66.7%)**

### 31-2. セーフゾーンの数値(基準サイズ1536×1024pxの場合)

| 方向 | セーフゾーン範囲(%) | セーフゾーン範囲(px、1536×1024基準) |
|---|---|---|
| 横(x) | 16.7%〜83.3%(中央66.7%) | 256px〜1280px(幅1024px) |
| 縦(y) | 7.8%〜92.2%(中央84.4%) | 80px〜944px(高さ864px) |

**基準サイズが異なる場合は、上記%をそのまま画像の幅・高さに乗じて計算する。** 重要なテキストブロック・タイトル・キャラクター等は、この矩形(中央66.7%×84.4%)の内側に配置する。

### 31-3. 運用ルール

- 今後のサムネイル制作・差し替え(既存記事のサムネ更新を含む)は、本規則のセーフゾーン内に重要要素が収まっているかを確認してから採用する。
- セーフゾーンからはみ出す要素がある場合、(a)その要素を画像から削る、(b)ヒーロー専用画像(`heroImage`)とカード専用画像(`thumbnail`)を分離する、のいずれかで対応する(2026-08-16、UVAとUVBの違い記事で(b)を実施した前例: `lib/posts.js`の`heroImage`フィールド、`pages/posts/[slug].js`の`post.heroImage || post.thumbnail`参照)。
- 項目35(実測レンダリング検査)のカードサムネ向けクロップ検査は、本規則導入前は「クロップ=不具合」という単純な基準が成立しなかったため検査対象外としていた(2026-08-16時点)。本規則導入後、セーフゾーンの数値を基準にした再設計(セーフゾーン内に収まらない配置を検出する等)を今後の課題とする。

**`text-shape-overlap`(テキスト×図形の重なり、2026-08-24新設、§AF)の補足**: 既存の`collision`はテキスト同士の重なりのみを対象としており、「ラベルが散布図の点や毛束の曲線の上に乗る」不具合を検出できなかった(2026-08-24、ヘアスタイル10記事の図解を実描画で目視した際に4件発見)。本カテゴリはこれを機械検出するもので、以下の設計とする。

- 検査対象の図形は、SVG内の`rect`/`circle`/`ellipse`/`polygon`/`polyline`/`path`/`line`/`image`と、記事本文内の`img`
- 許容マージンは`SHAPE_OVERLAP_TOLERANCE_PX`(既定3px、`scripts/verify-rendered-layout.js`内の定数)
- `getBoundingClientRect()`は線幅(stroke)を含まないため、strokeを持つ図形は線幅の半分だけ矩形を外側へ広げてから判定する(`inflatedShapeRect()`)。この補正が無いと、太い曲線に文字が乗っていても矩形上は1px未満しか重ならず検出漏れになる
- **`--strict`の合否に算入する(ブロッキング)。** 新設当初は既存記事への遡及影響(13節)を避けるため、環境変数`NEVORA_ITEM35_SHAPE_STRICT=1`のときだけ算入する暫定分岐を置いていたが、2026-08-25に全195記事で検出0件に到達したため分岐を廃止し、他の検出と同じ扱いにした。以後、この環境変数は存在しない

**ビルドが`text-shape-overlap`で失敗した場合の対処手順**

1. **まず原因を「偶発的なかすめ」と「設計上の配置」に切り分ける。** 実際の描画を見て判断すること(検出行の`overlap=WxHpx`だけでは判断しない)。幅768pxで該当図を描画し、文字が図形に埋もれて読みにくくなっているかを確認する
2. **偶発的なかすめ → 座標調整で解消する(原則こちら)。** 引き出し線の終点`toX`/`toY`をずらしてラベルを図形の外へ出す、`viewBox`を必要な向きへ広げる、といった座標のみの変更で対処する。文言の変更が必要だと感じた場合は、着手せず先に相談する。実例と手法は`docs/leader-label-cross-watchlist.md`の「是正のしかた」を参照
3. **設計上の配置 → `leaders[].allowOverlap: true`を付ける。** 図形とラベルが重なる配置そのものが意図的な場合に限る(例: 線が意図的にラベル領域を通る図、パネルの外へラベルを出す配置)。**偶発的に重なっているだけのものに付けてはならない。判断に迷う場合は付けず、相談すること。** 付ける際は、その図で重なりが意図的である理由を記事のfrontmatterにコメントで残す
4. 修正後は必ず`node scripts/verify-rendered-layout.js <slug>`を再実行し、当該記事が0件になったことを確認する。ラベルを移動した場合は、移動先で新たな重なりが生まれていないかをこの再実行で必ず見る(座標を動かして別の図形に食い込んだ実例がある)

引き出し線が自分のラベルの文字の上を通る現象(`text-shape-overlap`の対象外。引き出し線は除外#5)については、`docs/leader-label-cross-watchlist.md`に測定方法・判定基準(横断率50%)・経過観察リストをまとめている

## 33. 件数・集計値の報告ルール(2026-08-17追加)

**件数・集計値を報告する際は、必ず対象の列挙一覧とセットで提示し、一覧から数えた値のみを集計として記載する(集計先行・列挙後付けの禁止)。** 先に見積もり・概算・前回値の流用等で集計値を確定させ、後から裏付けの一覧を作る(または作らない)進め方を禁止する。集計は常に「まず全件を列挙 → 列挙した行数を数える → その数値を報告する」の順で導出すること。

- 2026-08-17、item36(tip/ポイント系コールアウトの見出し先頭配置検出)の対応で、検出件数を「68件」→実際は「72件」、確定43本該当を「19記事」→実際は「22記事」と、2回にわたり集計の訂正が発生した。原因はいずれも、先に近似値・前回の集計を報告し、後から詳細な列挙で答え合わせをする順序だったため、列挙漏れ(skincareTip型4件の集計対象外・確定43本の判定漏れ)に気づくのが遅れたこと。
- 実務上は、レポート内に集計値だけを書かず、必ず列挙一覧(表・箇条書き等)を先に(または同じレポート内に)示し、その一覧の行数=集計値であることが読み手にも検証可能な形にする。
