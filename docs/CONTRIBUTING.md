# 開発・記事編集ルール

> **会話のコンテキスト圧縮・セッション再開の直後は、作業を再開する前に必ず `docs/project-state.md`(このサイトには無い。読まずに進める) とこのファイルを読むこと。** `docs/project-state.md` にプロジェクト全体の進行状況(現在のフェーズ、直近の決定事項、フェーズ5の作業対象リストと進捗)がまとめられている。

NEVORAサイトの品質改善プロジェクト(フェーズ0監査 `docs/audit-report.md`(このサイトには無い。読まずに進める))で判明した構造的な問題を踏まえ、今後の作業で必ず守るルールをここにまとめる。

## 1. 記事の編集は必ず一次情報源側で行うこと

`サイト運営\サイト本体\content\articles` は**一次情報源ではない**。`scripts\sync-content.js` が `predev`/`prebuild` 実行時にこのディレクトリを `rmSync` で全削除し、`サイト運営\記事データ\公開済み` から `*.md` を再コピーする。

- **`content/articles` を直接編集しても、次の `next dev`/`next build` で消える。**
- **`content/articles`はgit管理外(`.gitignore`の`/content/`パターン)。**ローカルでは引き続き`npm run dev`/`npm run build`実行時に自動生成されるため、意識する必要はない。
- 記事の修正・加筆・削除は、必ず次のいずれかに対して行うこと。
  - 公開の予定日時を待っている記事 → `サイト運営\記事データ\公開待ち`
  - サイトに出ている記事 → `サイト運営\記事データ\公開済み`
- ライター・編集長・配信者・レビューアーなど、記事に触れる全エージェント・全作業者がこのルールを守ること。

## 2. 記事専用モジュール(`lib\*Widgets.js` / `lib\*Extras.js`)の新規追加を禁止する

`サイト運営\サイト本体\lib` には、特定の1記事のためだけに書かれた専用モジュールが既に複数存在する(このサイトには無い。読まずに進める)。`lib\posts.js` の `getPostBySlug` 末尾で `if (slug === XXX_SLUG)` という直列分岐によって適用される設計になっており、これが以下の不具合の根本原因になっている(詳細は `docs/audit-report.md`(このサイトには無い。読まずに進める) のB1・B2を参照)。

- 記事ごとに目次・要約・絵文字付与ロジックが個別実装され、共通コンポーネント(`ArticleToc`、`article-summary-box` など)と重複・二重表示を起こす
- 同じ処理(`emojiForHeading` など)が複数ファイルにコピペされ、修正が漏れやすい
- 保守コストが記事数に比例して増え続ける

**今後、記事の特殊な表現・レイアウトを実現するために新しい `lib\*Widgets.js` / `lib\*Extras.js` を追加することを禁止する。**

- 新規記事の図解・比較表・診断・チェックリストなどは、frontmatterの `charts:` / `accordions:` 等の**データ駆動方式**(既存の `type` 一覧を参照)で実現すること。
- 既存の `type` で表現できない見せ方が必要になった場合は、個別モジュールを増やすのではなく、`lib\posts.js` 側の汎用レンダラーに新しい `type` を追加する形で対応を検討し、実装前にサイト制作者エージェント(または担当者)に相談すること。
- 既存の専用モジュールの統廃合は将来フェーズのバックログとし、現時点では触らない(壊すリスクの方が大きいため)。

## 3. 一人称体験談の書き換えルール(B5)

運営者は個人であり、氏名(眞井 虹輝。/about に氏名・経歴を掲載)は公開している。記事の署名は「NEVORA編集部(運営者: 眞井 虹輝)」である。したがって記事中の「私は〜」「筆者が〜」「実際に使ってみたところ〜」といった一人称の使用体験は、運営者本人の実体験として確かめていない体験を、実名の運営者・編集部の名で**事実であるかのように書く虚偽の体験談**になり、読者の信頼を損なう。一人称体験談・架空の第三者や専門家の証言は、一般論に書き換えず削るのが現行の決まりである(writer.md の B5ルール・「文中に主体を書かない」の規則・規則32(i))。

【2026-09-17 改訂】一人称体験談・架空の第三者や専門家の証言は、一般論に書き換えず削る(writer.md 「文中に主体を書かない」の規則・規則32(i)。依頼者の指示)。以下の(a)(b)は、一般論への書き換え方針であり、現行では使わない。

- **(a) 仕組み・理由の説明**: 「なぜそうなるのか」を一般的なメカニズムとして説明する。
  例:「私は明細を見る日をカレンダーに書くようにしてから、使いすぎに気づけるようになりました」
  → 「明細を見る日をカレンダーなど目につく所に書いておくと、目に入ること自体が行動のきっかけになり、使いすぎの見落としを減らしやすくなります」
- **(b) 出典付きの一般論**: 公的機関・業界団体・金融機関や事業者の公式一次情報(料金表・約款・重要事項説明書等)など、実在し裏取り可能な出典を伴う一般的な事実として書く。

(a)(b)いずれにも書き換えられない場合(その記述が個人の体験でしか成立しない場合)は、**その記述ごと削除する。**

**禁止事項**: 出典を示せない伝聞・社会的証明の表現(「という声が多い」「多くの人が」「と言われています」「とされています」等)への言い換えは行わない。これは架空の体験談を架空の伝聞に置き換えているだけで、根拠を捏造している点は変わらないため、一人称体験談と同様に禁止する。

**禁止パターンの明文化(2026-08-11追加)**: 上記の「社会的証明の表現」には、出典で裏付けられない**頻度・多数派の断定**も含まれる。繰り返し現れるため、明示的に禁止パターンとして列挙する。

- 禁止する表現例:「珍しくない」「珍しいことではない」「少なくない」「よくある」「よく聞かれる」「〜する人は少なくありません」、出典のない「多い」(頻度主張として使う場合)
- 理由: これらは「何割がそうか」を示す出典がないまま、暗に「大多数がそうだ」と読者に思わせる表現であり、伝聞表現の言い換え禁止と同じ問題(根拠のない社会的証明)を含む。
- 代替表現:「起こり得ます」「場合があります」「〜しやすい環境/傾向です」(ただし機序の説明を伴う場合に限る。単に頻度を言い換えただけの「傾向があります」は不可)
- この禁止パターンは、フェーズ6で予定している機械検査(バリデーションスクリプト)の検出語リストにも含めること(`docs/project-state.md`(このサイトには無い。読まずに進める) 4節フェーズ6予定を参照)。

**禁止事項の明確化(2026-08-10追加)**: この禁止事項の趣旨は次の通り。

- 禁止の対象は「出典を示せない内容を『〜と言われています』『〜という声が多い』等でぼかして書くこと」である。
- **出典で裏付けられた内容は、伝聞にせず言い切ること**(「〜です」「〜します」「〜する傾向があります」)。出典があるのに伝聞表現を使うと、せっかく確保した出典の価値を自ら下げることになり、読者の信頼にもつながらない。
- 個人差・不確実性そのものを正直に示したい場合は、伝聞ではなく「傾向があります」「場合があります」「個人差があります」といった表現を使う。

フェーズ5の一人称体験談の書き換え(B5)およびフェーズ5トラック2の出典差し替え作業では、この明確化を提示前のセルフチェックに含めること。

なお、読者に問いかける修辞(例:「そんな経験、ありませんか」)は、著者自身の体験を主張するものではないため、このルールの対象外(書き換え不要)。カテゴリ担当マスコット(投資ならフヤミンちゃんなど。サイト全体のメインマスコットはコインミンちゃん)のコメント(`mascotComment`)も、キャラクターとして明示的に設計された発話であり、一人称体験談のルール(B5)の対象外。ただし断定・出典の判定(writer.md「frontmatter の文字列も判定の対象になる」)は mascotComment にも当たる。

**禁止対象の拡張(2026-08-11追加)**: このルールの禁止対象は「一人称の体験談」に留まらず、**実在しない体験・証言の創作全般**に及ぶ。以下も一人称体験談と同様に扱い、一般論に書き換えず、削る(writer.md 「文中に主体を書かない」の規則・規則32(i)。2026-09-17 依頼者の指示)。

- **架空の第三者の体験談の創作を禁止**: 「友人に聞いたところ〜」「知人が使ってみて〜」のように、一人称を避けて伝聞形式にしても、実在しない人物の証言を事実であるかのように書いている点は一人称体験談と変わらない。
- **架空の専門家の発言・診断の創作を禁止**: 「税理士さんに〜と言われた」「FPさんによると〜」「銀行の担当者いわく〜」のように、専門家の発言を装う記述は、実在しない権威を借りて記事の説得力を偽装するものであり、**最も悪質な類型として扱う**。
- **「実体験に基づく」「使用体験に基づく」等、記事の裏付けとして実在しない体験の存在を主張する記述を禁止**: 本文中だけでなく、免責文・注記(例:「本記事の使用感は編集部内での個人的な使用体験に基づくもの」)内の記述も対象に含む。

これらも、伝聞表現(「〜と言われています」等)へ言い換えて逃げることは禁止事項(上記)と同じ考え方で禁止する。精査では、この拡張範囲を検出対象に含めてセルフチェックすること。

**禁止対象の拡張2: 主語省略の一人称体験談(2026-08-12追加)**: 「私は」「筆者が」等の一人称マーカーを使わず、主語を省略したまま過去形の行動描写を連ねる日記調の文章(例:「申込画面の前で30分近く迷って、結局その場では決められず、なんとなく年会費の安い方のカードを申し込みました」)も、実質的に一人称体験談であり禁止対象に含まれる。マーカーの有無だけで判定せず、文章全体が特定の一回性の行動・出来事を時系列で語る個人の日記のような構成になっていないかを確認すること。`scripts/verify-article.js`の項目19が候補を警告として提示するが、正規表現では確実に判定できないため、**最終判断は人間の目視によること**。

## 4. 各フェーズ着手前に、直近のコミット履歴を確認すること

このプロジェクトは複数のセッション・作業者が並行して同じコードベースに変更を加える可能性がある。

- 各フェーズ(またはフェーズ内の大きな作業単位)に着手する前に、`git log` で直近のコミット履歴を確認し、これから着手する作業対象ファイル・機能と重複または競合する変更が既に入っていないかを確認すること。
- 重複を発見した場合は、**既存実装を優先**し(自分の変更が未着手・軽微であれば取り下げる)、その旨を完了報告に含めること。

## 5. 商品情報の検証義務(2026-08-11追加)

比較記事では、**存在しない商品名・公式に記載のない仕様**がそのまま記事に掲載される誤りが起こりうる(架空体験談(B5)と同様、根拠のない情報をあたかも事実であるかのように記載する点で深刻な問題)。金融商品・サービス(証券口座・投資信託・保険商品・クレジットカード・ポイントサービス・家計簿アプリ等)を扱う記事では以下を徹底する。

- 記事内で言及する**商品名・サービス名・運営会社(発行会社)・商品性(手数料・金利・利回り・還元率・補償内容・保険料・年会費・対象商品・条件)・価格**は、事業者の公式ページ(公式の料金表・手数料表・約款・重要事項説明書・目論見書等)で実在と現行性を確認してから記載する。商品名だけで検索して最初に出てきた情報を無検証で使わない(表記ゆれ・旧商品名・別商品との混同に注意)。
- 公式ページで確認できない情報は記載しない。やむを得ず第三者の比較サイト等の情報を使う場合は「(要人手確認)」等でその旨を明示し、確度を偽らない。
- 金融商品・サービスは改定・事業譲渡・取扱終了が起こり得るため、比較記事の`sources`には**確認時期**を含める(例:「確認時期:2026年8月」)。運営会社が変わっている場合(例: 合併・事業譲渡でカード・口座の発行会社やサービス名が変わっている場合)は現在の会社名で記載する。
- ある商品の紹介文・データ(手数料・還元率・ポジショニングマップの数値等)の根拠となる商品性が公式情報と食い違う場合、その商品を紹介枠から外すか、実際に該当する条件を満たす別商品に差し替えることを検討する(根拠のない商品を「枠を埋めるためだけに」残さない)。
- 手数料・金利・還元率・キャンペーンは変わりやすいため、本文か図表の`source`に「いつ時点か」(年月または年度)を書く。キャンペーンや「手数料無料」「還元率最大〇%」の条件(対象・期間・上限・エントリーの要否)は、本文で同じ大きさで書き、注記に小さく離して置かない(打消し表示のねらい)。比較・ランキングの順位に提携の有無が影響する場合はそれを明示し、順位の根拠(評価基準・時点)を冒頭付近に書く。

比較系記事(タイトルに「比較」「ランキング」「おすすめ」を含む記事、または本文に具体的な商品名を列挙する記事)は特にこのルールの対象になりやすい。

## 6. 記事単位の品質合格基準(2026-08-11再送)

フェーズ5(既存記事の一括修正)の各バッチで、記事を公開済みへ反映する前に以下5項目でセルフチェックし、結果を1行ずつ報告に添えること。

1. **独自性**: この記事にしかない要素(編集部による公式の手数料表・重要事項説明書の確認、独自の比較表・図解・診断)が最低1つあること。他サイトの要約・一般論だけの記事は「要増強」とマークして報告する。
2. **体験の真実性**: 実在しない体験・証言(一人称/第三者/専門家)がゼロであること。「実体験に基づく」等の虚偽の裏付け宣言もゼロであること(3節の拡張ルール参照)。
3. **出典**: 記事の中核的な主張に出典があり、URLは実在+記述の裏付けを確認済みであること。「参考として掲載(引用なし)」の水増し出典はゼロであること。
4. **YMYL対応(金融YMYL)**: 損失・税負担・契約トラブルに触れる記事は、免責(情報の時点・一般的な情報で個別の助言ではないこと)+専門家・公的窓口への相談の目安があること。投資・FX・外貨・保険(貯蓄型)など元本が減りうる商品を扱う記事は、リターン・メリットと同じ節に元本割れの可能性(FX などレバレッジのある取引は、預けた証拠金を超える損失が出ることがあること)・手数料・税・解約時の扱いを書いていること。リボ払い・ローンを扱う記事は、同じ節に負担増(手数料・利息・総支払額が増えること)を書いていること。個別銘柄・売買タイミングの推奨が無いこと。読者個人の税額の計算(「あなたの場合は〇円戻る」等)・読者個人の申告書の記入内容・税務書類の作成代行・個別の税務相談を行っていないこと(税理士法52条。一般的な制度や申告書の書き方の説明は禁じられていない)。読者が犯罪に関わる被害(例: 投資詐欺・SNS型投資詐欺)にいま実際にあっていて、個人では対処できない場面を扱う記事・結果に限り、窓口を、答えとして案内してよい。それ以外の悩み(制度の調べ方・手続きのやり方・商品選び・家計の見直しなど)では、窓口を答えにしない(答えのあとの補足として窓口に触れるのはよい)。diagnosis・flowchart の結果に窓口を置いてよいのは、犯罪に関わる被害がいま起きていて個人では対処できない結果に限る。窓口は名称だけを書き、電話番号とリンクは書かない(読者が名称で検索して探す。リンクや番号は変わることがあるため)。名称は確認済みのものだけを書く(未確認のものは書かない。例: 消費者ホットライン188・金融庁 金融サービス利用者相談室・金融庁「詐欺的な投資に関する相談ダイヤル」・警察相談専用電話 #9110・法テラス〔日本司法支援センター〕)。被害の取り戻し・返金を保証する書き方はしない。この例外の場面では、②の悩みや読者の設定にその状態を入れてよく、窓口は記事の中で1か所にまとめて案内する(冒頭や本文中で何度も案内しない)。無登録業者・投資詐欺・SNS型投資詐欺に触れる記事では、すでに送金した・出金できないなど被害が出ている場面は、この例外のとおり金融庁・警察・消費者ホットラインなどの窓口を答えとして案内してよい。被害が疑われる段階では、金融庁の登録業者の検索と相談窓口を、答えのあとの補足として案内する。専門家に相談する目安は見出しにせず、答えのあとの補足にだけ書く。ただし、犯罪に関わる被害がいま起きていて個人では対処できない場面の記事では、窓口へ連絡することを行動の見出し(最後の節)にしてよい。
5. **アフィリエイトリンクがゼロであること**(全カット方針のため。`docs/project-state.md`(このサイトには無い。読まずに進める) 2節-10参照)。

## 7. デプロイ運用:バッチ単位コミット・push(2026-08-11追加)

フェーズ5(既存記事の一括修正)のようにバッチ単位で作業を進める場合、複数バッチ分をまとめてコミット・pushせず、**バッチ単位でコミット・pushする**ことを標準とする。

- 1バッチ(記事の承認・公開済みへの反映・ビルド検証)が完了するごとに、そのバッチ分をコミットする。
- コミットした上で、ユーザーの許可を得てpushする。push許可の確認は、そのバッチの完了報告に含めてよい(別途改めて確認を取り直す必要はない)。
- 理由: 未pushの変更が長期間・大量に蓄積すると、(1) 本番環境が長期間古いまま放置される、(2) 未反映の修正内容の把握が困難になる、(3) 実際にpushする際のコミット分割・検証コストが増大する、という問題が起こる。バッチ単位でこまめにpushすることで、この蓄積を防ぐ。
- 記事以外(サイトコード修正、ドキュメント更新など)についても、意味のある単位の作業が完了した時点で同様にコミット・push確認を行う。

## 8. 一括処理は対象の妥当性を処理前に検証すること(2026-08-11追加)

`updatedDate`を多数の記事へ機械的に一括付与する際に、実際にはB5書き換え等の実質修正を経ていない記事が混入することがある。原因になるのは、対象リストを「該当コミットで触れられたファイル」から機械的に抽出し、「実際にB5書き換え等の実質修正を行った記事」の正規リストと突き合わせないこと。結果として、過去の別コミット(アフィリエイト全カット・編集長基準修正等)でたまたま触れられただけの記事に、実質修正なく`updatedDate`だけが付与される事態になった(9節の禁止する「空更新」に該当)。

- **同一の値・同一の変更を複数ファイルへ機械的に適用する作業(sedループ・一括置換等)を行う前に、対象ファイルリストの生成根拠を明示し、「本当にその変更が必要な状態か」を最低限サンプル確認すること。** 「あるコミットに含まれていた」ことは「そのコミットの主目的の修正を受けた」ことを意味しない。
- 対象件数が多い場合は、全件の詳細レビューまでは不要でも、機械的な整合性チェック(例: `scripts/verify-article.js`の該当項目を全対象に実行し、想定と異なる結果が出ていないか)を一括処理の前後で行う。
- 発見した混入は、以下の順で是正する: (1) 誤って付与された値を削除し実体に合わせる (2) 台帳(`docs/project-state.md`(このサイトには無い。読まずに進める))の記録を実態に合わせて訂正する (3) 実質修正が必要ならこのタイミングで実施する。

## 9. 検出パターンの機械側への還元(2026-08-11追加)

エージェント(reviewer・legal-checker等)が趣旨ベースで、正規表現をすり抜ける変種表現(例: 「〜と説明されています」のような婉曲的な伝聞表現、「〜人は多くありません」のような頻度断定の裏返し表現)を発見した場合、指摘して終わりにせず、その都度`サイト運営\サイト本体\scripts\verify-article.js`の該当正規表現(項目11・12等)に追加し、機械検査側を成長させること。プロンプト指示ベースの検出は再現性が保証されないため、発見したパターンは必ずコードへ還元し、次回以降は機械的に検出できる状態にする。

## 10. 固定ラベル型chart typeの選定基準(2026-08-11追加)

`prosCons`(◎メリット/△デメリット)のような固定ラベルを持つchart typeは、**内容が実際に優劣・賛否の比較である場合のみ**使用する。役割分担・分類の説明(例: 「つみたて投資枠と成長投資枠」「所得控除と税額控除」のように優劣ではなく役割が異なるだけの関係)には使わず、比較表(Markdown表)や箇条書きなど、ラベルに縛られない型を使うこと。

- 判断基準: そのchartの2つの列は「片方が優れていてもう片方が劣っている」関係か、それとも「単に役割・対象が異なるだけ」の関係か。後者であれば`prosCons`は不適切。
- 違反時の症状: 読者に「AとBのどちらが優れているか」という誤った比較軸を暗示してしまう。
- 該当する場合の対応: chart typeを比較表・箇条書き等に差し替えるか、`prosCons`のラベル文言自体を実態に即した見出し(例: 「守備範囲」「片方だけ見た場合の弱点」)に変更する。

**画像の生成は行わない。画像は依頼者が用意する(2026-09-12に方針として確定)。** AIエージェントは画像を生成せず、**ユーザー画像ライブラリ優先方式**で調達する。記事の生成・判定は画像なしで進む(`thumbnail`が空でも第1層は通る。公開の直前で検査される。`docs/pipeline/autonomy/DESIGN.md` §20)。

**役割分担**:
- **image-selector**: 上記1→2の優先順位でのライブラリ走査・生成プロンプト作成までを担当する。画像生成そのものは行わない。
- **image-placer**: 選定・生成された画像ファイルの変換(PNG→WebP)・配置、frontmatterの`thumbnail`更新、本文への画像挿入、`CATALOG.md`更新、ビルド確認を担当する。**WebP変換はPython(Pillow)で行う(Pillowがインストール済みの環境では、追加インストールなしに実行できる)。** 元画像のアスペクト比が既存規格と異なる場合は中央クロップしてから変換する。

## 12. 記事の更新日(updatedDate)運用ルール(2026-08-11追加)

frontmatterの`updatedDate`(任意項目)は、`date`(公開日)とは別に、記事ページのヘッダー(「公開日: YYYY-MM-DD / 最終更新日: YYYY-MM-DD」)・構造化データ(`dateModified`)・`sitemap.xml`の`lastmod`に反映される(実装は`lib/posts.js`の`normalizeFrontmatter`・`lib/structuredData.js`の`buildArticleJsonLd`・`pages/sitemap.xml.js`)。

- **更新する場合**: 事実誤認の訂正/商品・制度情報の更新(手数料・金利・還元率の改定、税制改正・制度変更の反映等)/出典差し替え/セクションの追加削除/B5書き換え等、**読者にとって意味のある実質的な修正**をしたとき。
- **更新しない場合**: 誤字修正・表記ゆれの統一・サイトコード側の表示変更のみなど、本文の実質的な内容が変わらない場合。空更新(意味のない`updatedDate`の書き換え)は禁止する。
- `updatedDate`を追加・変更しても、記事一覧(新着順等)の並び順は`date`(公開日)基準のまま変わらない。
- **制度改正・年度更新の確認(お金の記事に固有)**: 税制改正(毎年度)・NISA/iDeCoの制度変更・保険料控除の改正・金利の変動は、公開済み記事の見直し対象にする。見直して内容を直した記事は`updatedDate`を更新し、本文・図表の時点(年月または年度)も新しいものに直す(数値は14節の手順で全出現箇所を直す)。制度改正の予定(例: 税制改正大綱に載ったが、法案がまだ成立していない改正)は「予定」と書き、確定していないことを断定しない。

## 13. 検査基準の拡張は過去の合格判定を無効化する(2026-08-12追加)

`verify-article.js`の検査ロジック(検出パターン・スキャン対象範囲)を拡張・強化した場合、**過去にその検査で「合格」と判定された記事は、新基準でのチェックを経ていないため自動的には有効な合格とみなさない**。

- 背景: B5(項目10)・伝聞(項目11)等の検査が本文(bodyLines)のみを対象とし、`accordions`/`charts`等frontmatter内の構造化コンテンツをスキャンしていないと、「編集部で実際に試した」「私は〜」のような明確な虚偽体験談がaccordion内に残ったまま「修正不要」「公開可」と判定されうる。旧検査基準(構造化コンテンツ非対応)で合格した記事は、拡張後の基準では不合格になりうる。
- **対応**: 検査ロジックを拡張した際は、影響範囲(新たにスキャン対象になった構造・検出パターン)を明示した上で、既存の全記事に対して新基準での再検査を実施すること。過去の「合格」「修正不要」の記録は、それがどの検査基準の時点でのものかを合わせて記録し、基準拡張後は鵜呑みにしない。
- **配置・構成ルールの新設・変更も本節の対象とする(2026-08-13追記)**: `verify-article.js`のスキャンロジックだけでなく、CONTRIBUTING/writer/editor-in-chief等に新設した「配置ルール」(視覚要素の配置優先順位・団子の禁止等)も同様に扱う。**「次回の記事制作から適用する」という前提だけで済ませず、既存記事への遡及検証を必ず作業計画に含めること**。雰囲気写真の配置優先順位ルール((d)図解のない見出し優先)のような配置ルールを新設した際に、「今後の新規記事から適用」という理解のまま既存の画像配置を再検証しないと、ルール新設後もルール違反の配置(まとめ直下・診断直後等)が残ったまま「対応済み」として報告してしまう。ルールを書いた時点で、既存記事(直近の対象記事に限らず全記事)への適用要否を必ず検討し、対象範囲を明示すること。
- **新規ブロッキング項目の追加時は`npm run verify:all`の全記事実行を完了報告に必須で含める(2026-08-14追記)**: `scripts/verify-article.js`へ新規のブロッキング項目を追加した場合(既存項目の判定ロジック変更を含む)、**その項目に限定した公開済み全記事への一括実行結果を、その作業の完了報告に必ず含めること**。一括実行は`サイト運営\サイト本体`で`npm run verify:all`を実行することで行う(`scripts/verify-all-articles.js`、記事ごとのoverall・違反項目番号とフォルダ別サマリを出力する)。背景: 項目を新設した際に、直近に触れた記事のみを確認し、それ以外の公開済み全記事への一括確認を行わないと、違反が発覚まで素通りする。「口頭での確認」ではなく`npm run verify:all`というコマンドに紐づけることで、確認の有無を機械的に検証可能にする。
- **`lib/posts.js`のレンダリングロジック変更時は`npm run verify:rendered`の全記事実行を完了報告に必須で含める(2026-08-14追記、22節参照)**: `verify-article.js`はfrontmatter/本文Markdownソースのみを見る設計であり、実際のHTML描画結果(`lib/posts.js`のembedCharts/embedAccordions/splitHtmlBlocks等)を一切検証しない。そのため`lib/posts.js`のレンダリングロジックを変更した場合(記事の追加・削除を伴わない場合も含む)は、`npm run verify:rendered`(項目33)を実行し、不一致0件を確認した上で完了報告に含めること。

## 14. 数値修正時は記事内の全出現箇所を確認すること(2026-08-12追加)

同じ数値(金額、税率・控除額・上限額、手数料・金利・還元率、期間等)が`charts`のdata・本文・`summaryPoints`・`description`・まとめ等、記事内の複数箇所に重複して書かれている構造は、修正漏れのリスク源になる。

- 背景: `charts[].data`の数値を修正した際に、本文の箇条書き・まとめ・`summaryPoints`・`description`に残っている旧来の数値を直し忘れると、グラフと本文の数値が食い違ったまま公開される。`verify-article.js`の検査を通過していても実物確認で初めて見つかる種類の誤りである。お金の記事での同型の誤りの例(仮): つみたて投資枠の「年120万円」を本文だけ直し、図表・`summaryPoints`に旧値が残る。
- **対応(必須手順)**: 記事内の数値(金額・税率・上限額・手数料・金利・還元率・年数・%等)を修正する場合は、修正前に**その数値の文字列を記事ファイル全体でgrepし、記事内の全出現箇所を洗い出してから**まとめて修正すること。1箇所だけを直して終わらせない。
- **機械検査での補助**: `verify-article.js`項目20(非ブロッキング警告)が、`charts[].data`の数値集合と単位が一致する本文・summaryPoints・description中の近似値を突き合わせ、chartの値の範囲内にありながらどの値とも一致しない数値(修正漏れの疑いがある値)を警告として検出する。完全な意味理解はできないため、あくまで人間の目視確認を促す参考情報であり、上記の必須手順(grep確認)を代替するものではない。

## 15. 調査・集計結果は必ずファイル保存してから報告すること(2026-08-13追加)

複数記事にまたがる調査・分類・優先順位マトリクスなどの集計結果は、チャット上で報告するだけでなく、**必ず`docs/`配下にファイル保存してから報告すること**。

- 背景: 優先順位マトリクスのような集計結果をファイル保存せずチャット上でのみ報告すると、後続セッションでのコンテキスト圧縮により内容が失われる。結論だけが記録に残り、根拠となる記事リストが失われると、次のバッチ着手時に対象記事を特定できず、再調査が必要になる。
- **対応**: 複数記事・複数バッチにまたがる調査結果、優先順位マトリクス、対象記事リストなどは、作成した時点で`docs/`配下(例: `docs/pipeline/`)にMarkdownファイルとして保存する。チャット上の報告はそのファイルへの要約・ポインタとし、詳細はファイルを正とする。以後の状態確認・再開時は、まずこれらのファイルを読み込んでから作業すること。

## 16. 出典なし伝聞表現(項目11)が大量に残る記事への対応方針(2026-08-13追加)

**対応方針(2026-08-13ユーザー承認)**: 文脈上重要な文のみ出典明示、それ以外は断定表現に緩和する。ただし以下の歯止めを必ず守ること。

- **出典明示側に必ず分類する文**(一般論への緩和は禁止):
  - 数値・割合・期間を含む文(例:「投資信託の保有中の費用は数種類に分かれると言われています」の分類自体は一般論でよいが、「年0.1〜0.5%」等の具体的数値を伴う主張は出典明示。税率・控除額・上限額・手数料・金利・還元率は時点も書く)

  - 利益・損失・リスク・税負担・節税額・保障内容の評価を主張する文(「〜すると節税になると言われています」「〜は利回りが高いとされています」等)
- **断定表現への緩和が許容される文**: 仕組み・分類・定義レベルの一般的知識に限る(例:「株価は日々変動する」「クレジットカードの利用額は後日まとめて引き落とされる」等、複数の一次情報で広く確立された基礎知識)
- **判断に迷う文は出典明示側に倒す**(緩和を優先しない)
- **記録義務**: 記事ごとに「断定化した文の数 / 出典明示にした文の数」をバッチ完了報告に記載し、断定側に極端に偏っていないか確認を受けること
- verify-article.js自体(項目11のロジック)は変更しない。あくまで記事本文側の対応で解消する。

**線引きの明確化(2026-08-13追記)**: 「仕組み・分類・定義レベルの一般的知識」という基準は曖昧になりやすく、機序についての主張・商品の種類と効果の対応づけ・一見基礎知識に見えて実際は学術トピックである主張が、誤って断定表現に緩和されやすい。お金の記事では断定化してよい範囲を次のように絞り込む:

## 17. YMYLテーマの出典は公的機関・業界団体を優先的に再探索すること(2026-08-13追加)

金融機関・保険代理店・FP事務所・税理士事務所の販売・集客目的のコラムのみで出典を構成する前に、公的機関(金融庁・国税庁・財務省・日本銀行・消費者庁・総務省統計局・厚生労働省・日本年金機構・預金保険機構・J-FLEC〔金融経済教育推進機構〕・e-Gov 法令検索・国民生活センター等)や業界団体(日本証券業協会・資産運用業協会・全国銀行協会・生命保険協会・日本損害保険協会・日本クレジット協会等)が同テーマの一次情報を公開していないか、必ず明示的に検索して確認すること。「見当たらなかった」という結論を出す前に、関連する機関名+テーマで具体的に検索する。お金の記事は全記事が金融YMYLに当たる。

- 背景: 出典が民間の事業者コラム(secondary)のみになるのは、YMYL度の高いテーマで関連する公的な機関が一次情報を公開している可能性が高いにもかかわらず、事前の探索が不十分なまま「一次情報は見当たらない」と判断してしまうため。
- **対応**: 事業者のコラムのみが出典候補になった場合、着手前に「[テーマ] 国税庁 タックスアンサー」「[テーマ] 金融庁」「[テーマ] site:go.jp」「[テーマ] 協会 統計」等で明示的に検索し、該当する一次情報の有無を確認する。見つかった場合は中核的な主張(制度の対象・税率・控除額・上限額・制度の要件・相談の目安等)の出典をそちらに差し替え/追加し、事業者のコラムは補助的な位置づけに格下げする。本当に見つからない場合のみ、既存の事業者出典で維持してよい。
- 事業者のコラムを使ってよいのは、その事業者しか公開していない自社の値(自社の手数料・自社調査の件数等)に限る。制度の解釈・税の取り扱い・リスクの評価の言い切りには使わない。手数料・金利・還元率は、同じ事業者の料金表・約款(一次情報)を優先する。販売目的のコラムを出典にしないのは、販売者の評価が中立でないためである。
- 税率・控除額・上限額・制度の要件は「いつ時点か」(年月または年度)を出典とあわせて書く。知るぽると(金融広報中央委員会)は2024年8月にJ-FLECへ移管され現在はアーカイブサイトのため、新規の出典はJ-FLECを優先し、知るぽるとの統計を使うときはアーカイブであることと調査年を書く。

## 18. `disclaimer: none` フィールドの用途(2026-08-13追加)

一部記事のfrontmatterに `disclaimer: none` という値が入っている。これは「本記事には個別の免責注記が不要」であることを示す内部管理用のフラグであり、読者向けに表示される文言ではない(表示側の実装は`disclaimer`が未設定/`none`の場合に免責ブロックを描画しない)。about.js・privacy-policy.js側にこの値自体への言及・説明は不要(サイト全体の免責事項はprivacy-policy.js/terms.jsで一括カバーされているため)。新規記事で個別の免責注記が不要と判断した場合は `disclaimer: none` を明示的に設定し、フィールド自体を省略しない(省略と`none`明示を区別しないと、意図的に不要と判断したのか単なる書き忘れなのか後から区別できなくなるため)。

## 19. frontmatter(description等)は本文と同じ厳格さで検査すること(2026-08-13追加)

**問題の型**: descriptionに「体験談を交えて解説します」という体験談を約束する文言が残ると、本文の一人称体験談はB5ルールにより削除済みでも、「読者への告知(description)」と「本文の実態」が矛盾する。

**見落とし原因**: 項目10(B5違反検出)は`extractStructuredTextBlocks`によりfrontmatterのdescription/summaryPoints/accordion等も検査対象に含めるが、検出パターン(`RE_B5_FAKE_EXPERIENCE`等)が「実際に使ってみた」「使用体験に基づく」等、**本文の一人称体験談の言い回し**を基準に作られており、「体験談を交えて解説します」「実体験を交えて解説します」のような**meta description特有の告知・予告表現**は語形が異なるため、検出パターンに一致しない。本文の体験談を削除するだけでは、frontmatterの「予告文言」が本文修正と同時に更新されているかを機械的に確認する手段がなく、目視レビューでも見落とされやすい。

**恒久対応**: `scripts/verify-article.js`に`RE_B5_EXPERIENCE_PROMISE`(「体験談を交えて」「実体験を交えて」「効果を感じた/実感した」「検証してみた」等)を項目10の検出パターンに含める。また`fm.disclaimer`も`extractStructuredTextBlocks`の抽出対象に含め、免責文内の虚偽裏付け宣言(3節参照)も項目10で機械検出する。

**教訓**: 検出パターンを設計する際は「本文でよく使われる言い回し」だけでなく、「frontmatterの各フィールドが持つ独自の文体・目的」(descriptionは読者への告知・約束、summaryPointsは箇条書きの要約、disclaimerは免責文、accordion.summaryは開閉ボタンの誘導文)ごとに、その文脈特有の言い回しを想定して検出パターンを設計すること。「本文用パターンをfrontmatterにも適用すれば足りる」という前提は誤りだった。

## 20. quadrantチャートのフォールバック表で評価記号(◎○△)を使わない(2026-08-13追加)

`type: "quadrant"`チャートのフォールバック表(JS非対応環境向けの表形式データ)は、以前は座標値を◎(高い)/○(中)/△(低い)の記号に変換して表示していたが、**◎○△は「良い/悪い」という評価の含意を持つため、軸の向き次第で誤読を招く**。

- 背景: Y軸(費用感、値が高いほど高額=悪い)において一方の選択肢の値が高く◎がつくと、「その選択肢は費用面で優れている(安い)」と誤読されるリスクがある。お金の記事では、年会費・信託報酬・保険料・手数料の軸が同じ向き(値が高いほど読者の負担が大きい)になる。
- **対応**: `lib/posts.js`の`renderQuadrantChartHtml`を修正し、記号ではなく中立的な高低表現(「高い/中程度/低い」)をデフォルトのフォールバックとした。さらに、chartsの`data`各項目に`xNote`/`yNote`(文字列)を指定すると、そちらが自動生成の高低表現より優先され、記事の本文記述に即した具体的な文言(例:「高め(年1万円台)」「条件により変動」)を表示できる。
- **新規記事のルール**: quadrantチャートで軸の値の大小が「良い/悪い」に単純に対応しない場合(例: 費用・手数料・時間・負担など、低いほうが良いことが多い軸)は、`xNote`/`yNote`で本文の記述と一致する具体的な文言を明示すること。単純に「高い方が良い」と読める軸(満足度等)であっても、記号ではなく言葉のほうが誤読リスクが低いため、迷ったら`xNote`/`yNote`を使う。
- **既存記事への遡及**: 記号除去そのものは`lib/posts.js`の共通レンダラー修正により全quadrantチャートに自動適用済み(記事側の追加修正は不要)。ただし`xNote`/`yNote`未指定の既存記事は「高い/中程度/低い」という一般的な表現になるため、軸の意味によっては本文の記述とニュアンスが完全に一致しない可能性がある。該当記事一覧は`docs/pipeline/quadrant-chart-audit.md`を参照し、必要に応じて`xNote`/`yNote`を追記する。

## 21. frontmatterのdate/updatedDateはYYYY-MM-DD形式で統一する(2026-08-13追加)

`date: "2026-08-13T09:00:00+09:00"`のような時刻付きISO8601形式が使われると、記事ページの日付表示がISO生文字列のまま崩れて表示される。

- **frontmatterの`date`/`updatedDate`は必ず`"YYYY-MM-DD"`形式(時刻を含めない)で記載すること。** 時刻情報は記事の表示・機能のどこでも使われていない。
- **表示側の恒久対策**: `サイト運営\サイト本体\lib\formatDate.js`を新設し、日付を画面表示する箇所(`pages\posts\[slug].js`の記事ヘッダー、`pages\admin\articles.js`の記事一覧)は必ずこの関数を経由して整形する。YYYY-MM-DD形式・時刻付きISO8601形式のどちらが渡されても`YYYY-MM-DD`に整形されるため、今後frontmatter側に形式の揺れが残っても表示は崩れない。
- 一方、`lib\structuredData.js`の`buildArticleJsonLd`(`datePublished`/`dateModified`)と`pages\sitemap.xml.js`の`lastmod`は、schema.org・sitemapの仕様上ISO8601形式(日付のみも許容)がそのまま正しい値になるため、`formatDate`を経由させる必要はない(frontmatterがYYYY-MM-DD形式に統一されていれば、そのまま出力しても仕様に適合する)。
- frontmatterの`date`/`updatedDate`の表記形式だけをYYYY-MM-DD形式へ統一する変更は、値そのものの変更ではなく、`updatedDate`の新規追加・値の書き換えを伴わない(8節の「空更新の禁止」に抵触しないよう、既存の値の表記形式のみを変える)。

## 22. 複数記事横断コンポーネントはカテゴリ・文脈を無視した単純な日付順/配列順選定にしないこと(2026-08-13追加)

`lib/posts.js`の`getNextPost`(記事ページ「次の記事へ進む」)が、全記事を公開日順に並べただけの配列から単純にインデックス+1(末尾は先頭へ循環)で次記事を選んでいたため、カテゴリを一切考慮せずカテゴリの異なる記事が次に表示される不具合があった(このサイトに当てはめれば「保険」の記事の次に「FX」の記事が出るような状態)。

- **典型的な失敗パターン**: 「複数記事から1件(または数件)を選んで表示する」コンポーネント(次の記事/前の記事、関連記事、おすすめ記事、カテゴリカードのピックアップ等)を実装する際、実装の手間を省くために「全記事配列を日付順や登録順に並べ、その並び順だけで機械的に選ぶ」実装にしてしまいやすい。一見動作しているように見える(常に何かしらの記事が表示される)ため、見た目のバグとして気づきにくく、実際にカテゴリの異なる記事が表示されて初めて発覚する。
- **対応**: このようなコンポーネントを新規実装・修正する際は、単純な日付順/配列順を採用する前に、「読者が今読んでいる記事の文脈(カテゴリ・タグ・悩みslug等)と無関係な記事が選ばれ得ないか」を必ず自問すること。優先順位のあるフォールバック(同カテゴリ→タグ一致→非表示、等)を設計し、「該当なしなら表示しない」を許容する(存在しないつながりを無理に表示しない)。
- 修正後の`getNextPost`は、同一カテゴリ内で公開日が近い記事を優先し、同一カテゴリに他の記事が無い場合のみ悩みタグ(`worry`)一致で代替、それも無ければ「次の記事へ進む」自体を非表示にする方式にした。

## 23. タイトルが約束する視覚要素・出典の実在を、レンダリング結果ベースで確認する(2026-08-13追加)

「〇〇の仕組みを図解でやさしく解説」のようにタイトルが図解を約束していても、quadrantチャートの`data`配列を誤って`items`というキー名で書くと`lib/posts.js`の`renderQuadrantChartHtml`が`data`未定義で空文字列を返し、タイトルが約束する「図解」が本番で一切表示されない状態のまま、パイプライン全工程を通過して公開されうる。

- **根本原因**: frontmatterのYAMLスキーマはコード側の`chart.data`という前提に暗黙で依存しており、キー名を`items`と書き間違えても構文エラーにはならず(単に未使用のフィールドが増えるだけ)、`verify-article.js`の項目15(quadrantのnote/source欠落チェック)もキー名の誤りまでは検出できなかった。パイプラインの全工程が「frontmatterに書かれた内容が正しく実装のキー名と一致していること」を前提にしており、実際のレンダリング結果(本番HTML)を誰も確認していなかった。
- **対応**: `scripts/verify-article.js`に項目21(タイトル約束語の実体照合)を追加した。タイトルに「図解」「グラフ」「チェックリスト」「表」等の語がある場合、対応するchart型が`data`/`items`配列を実際に1件以上持っているかを機械チェックする(ブロッキング)。あわせて項目22(検証済み出典1件以上)も追加したが、のちに廃止した(永久欠番。スクリプトは常に Yes を返すスタブ。nevora-pipeline-verifier.md が正)。
- ただし項目21は語句マッチによる簡易チェックであり、「意味的に図解の内容が本文の主張と対応しているか」までは検証できない。**新規記事の公開前は必ず本番(またはローカルビルド)のレンダリング結果を目視確認し、frontmatterに書いた内容が実際に画面に表示されているかを確認すること**(編集長のチェック項目にも追記済み、`.claude/agents/editor-in-chief.md`参照)。

## 24. 「図」の定義とSVG図解レンダラーの使い分け(2026-08-13追加)

「1見出しに文字が詰まり、読者が離脱する」状態への第一弾の対応として`steps`型・`diagnosis`型のchartを見出し直後に追加するだけでは、**不合格**になる。理由は「コマ間・項目間の違いが絵から読み取れない(文字を読んで初めて差が分かる)」ため、これは「図」ではなく「テキストの整形」にとどまること。

- **「図」の定義**: 概念・仕組み・変化を、**イラスト+文字の説明のセット**で見せるもの。文字だけを整形して並べたもの(番号付きリスト、チェックリスト、カード状に並んだテキスト)は図ではない
- **図に分類しないchart型**: `checklist`(チェック項目リスト)・`flowchart`/`diagnosis`(対話的なテキストUI、イラストを伴わない)。これらはタイトルに「診断」等の語を含めても図としては扱わない。`steps`(番号付き手順)と`compareScroll`(横スライドの比較)は、手順・比較を見せる主役の図解として置いてよく、図に数える(依頼者の決定 2026-09-24。writer.md 規則28(b)と、規則28の表の「図」の欄が正)。`scripts/verify-article.js`項目24は steps を LOW、compareScroll を NEUTRAL として判定するが、参考情報であり要件にしない。図の必須・本数は writer.md 規則28(g)
- **図に分類するchart型**(型ごとの「図」の欄が○かどうかは writer.md 規則28の表が正。以下は例): `quadrant`/`faceMap`/`lineChart`(位置づけ・分布を視覚エンコードする実チャート)、および新設した`crossSection`(断面/構造図型)・`depthComparison`(深さ/到達範囲比較型)・`processContrast`(プロセス/対比型)。後者3つは`lib/posts.js`にデータ駆動のSVGレンダラーとして実装済み(色・ラベル・形状パラメータをfrontmatterのchartsから指定する、既存chart群と同じ仕組み)
- **AI画像生成は図解に使わない**: 文字が崩れる・修正が困難という理由から、概念・仕組みの図解にはAI画像生成を使わず、上記のSVGレンダラーで実装する。雰囲気写真・サムネイルは生成AIで作ってよいが、AIエージェントは画像を生成せず、依頼者が用意する(2026-09-12 に確定。11節)
- **虚偽参照の禁止**: 本文中で「上の図」「下の図」「上記の図表」等の参照語を使う場合、参照先の見出しセクションに実際に図(writer.md 規則28の表の「図」の欄が○の型のchart)または画像が存在することを確認すること。`scripts/verify-article.js`項目26で機械チェックする(ブロッキング)。図の実装前に参照文だけを書かない
- **プロセス/対比型(`processContrast`)の設計原則(2026-08-13確定、Rev.3で最終化)**: モックアップで3回の判定を経て確定した原則。各コマはラベルを隠しても違いが分かることを設計基準とする
  - **モチーフは実物の簡略イラスト(お金の記事なら通帳・明細・財布・カード・カレンダー・書類・スマホ等)を土台にする。抽象図形(縞・棒等)の変化だけで差を表現しない**(抽象的な縞モチーフは「ラベルを読まないと差が分からない」ため不合格になる)
  - **コマ間で「同じ場所にあり続ける要素」(例: 明細の中で毎月残り続ける固定費の行)は、位置・色とも完全に固定する。**要素が消えた/移動したように見える表現は禁止。「なくなった」という誤ったメッセージになるため、変化するのは周囲の要素の色だけにする
  - **コマ数は2(Before/After)を既定とする。**3コマ目(中間コマ)を使うのは、その中間コマが「過程・動作」として明確に意味を持つ場合のみとし、単に色数を増やしただけのコマを挟まない(中間コマが「色が増えただけで動作が読み取れない」ものになりやすいため)
  - 意味の分からない装飾要素(データを表さないマーカー等)を置かない

## 25. 視覚要素の配置ルール(400字ルール・団子の禁止・雰囲気写真の優先順位)(2026-08-13追加)

図解3型(crossSection/depthComparison/processContrast)の図解を見出し直下に置き、直下に雰囲気写真が連続する視覚要素の団子にすると、その先の文章の壁は解消されない。図解の**質**が合格でも、**配置**が誤っていれば不合格になる。以下を配置の大原則として確定する。

### (a) 400字ルール(ブロッキング、`scripts/verify-article.js`項目23。2026-08-13再々改訂、閾値は2026-09-12に400字へ戻した)
改行(空行)を挟んでも実際の視覚要素(画像・チャート/アコーディオン〔見出しに紐づくもの〕・表・コールアウトボックス)に一度も当たらないまま地の文が合計400字以上連続することを禁止する。空行だけでは連続はリセットしない。数え始めるのは最初の見出しからで、導入(最初の見出しより前)は対象にしない。字数は出典の印 `%%出典:…%%` を除いて数える(2026-10-07。writer.md 400字ルールが正)。なお、この規則は新規執筆のときだけ適用し、差し戻し後の修正には適用しない(writer.md 400字ルール。機械は両者を区別できないため、修正版で項目23が No のときは writer.md「依頼者の目視で公開する経路」で扱う)。
- NG例: 250字→改行→180字(計430字連続、視覚要素なし)
- OK例: 250字→視覚要素→200字
- 境界: **ちょうど400字も違反**(400字以上が禁止。実装は `runChars >= CONTINUOUS_TEXT_MAX_CHARS`)
- **閾値は400字**(`verify-article.js` の `CONTINUOUS_TEXT_MAX_CHARS`)。変更の経緯と理由は `docs/pipeline/autonomy/DESIGN.md` に記載する
- **見出し自体(H2/H3)はリセット条件に含めない**。図解・アコーディオンが紐づいていない見出しは、ただの太字テキストであり視覚的休憩にならないため、見出しをまたいでも連続はリセットされない(図解が紐づいていないH3見出しが続くと、H3ごとに独立してリセットする実装では合計が長い壁になっても検出をすり抜けるため厳格化した)
- **箇条書き(list)もリセット条件に含めない**。箇条書きはテキストの整形であり視覚的な間にはならないため、項目の文字も地の文としてカウントに含める(短い箇条書きを挟んだだけで壁が「解消」扱いになり、実際には壁が残ったまま合格してしまうため厳格化した)
- **区切り線(`---`)もリセット条件に含めない**。詳細は(e)の追記を参照
- **Markdownリンク`[表示テキスト](URL)`は、表示テキストのみをカウントし、URL・角括弧・丸括弧はカウント対象から除外する(2026-08-15、L1決裁)**。修正前は記法全体(URLの日本語スラッグ込み)をそのままカウントしており、「関連記事」等の内部リンクリストが地の文の分量を実際より水増ししていた

### (b) 400字超の解消手段は「視覚要素の位置で切る」と「内容の図解化」(この順。writer.md「400字ルール」の対処が正)
400字を超える説明は、(1)まず視覚要素(図表・枠・表・画像)の位置で切り(直前の段落に `afterParagraph` で置いてもよい。図解を置くためだけの見出しは立てない)、(2)次に**その説明の内容そのものを図解に変換する**ことで解消する。説明を短くして回避しない。アコーディオンは対処に使わない。
- 優先対象: 難しい説明・仕組み(制度の構造・税の計算の段階・お金の流れ)・手順・分類・比較(文章で読むと重い内容ほど図解化の価値が高い)
- 変換に使う型: 3型(crossSection/depthComparison/processContrast)+既存chart群(表・箇条書き等)
- **chartはafterHeadingで見出しに紐づけ、`afterParagraph: n` を書くと、その見出しのあとの段落 n 個の後ろに入る(書かない場合は見出しの直下)。文章の「途中」を割りたい場合は、その位置の直前の段落に `afterParagraph` で図解を紐づける。図解を置くためだけの見出しを立てない**(段落の数え方は `.claude/agents/writer.md` の規則32(a)、400字ルールの対処は writer.md の「400字ルール」)
- 要約・短縮で回避しない(writer.md 400字ルールの『当たったときの対処』)

### (c) 挿入要素の内容条件
400字ルールを満たすために挟む視覚要素は、**直前の文章の内容を視覚化・整理したもの**に限る。ただし、枠(💡⚠️)・accordion・図の中の文は、地の文と同じ文にしない(`.claude/agents/writer.md` の規則32(b))。直前の文脈と無関係な図・グラフ・写真を挟んでもルールを満たしたことにならず、むしろ違反として扱う。この一致は機械判定が困難なため、editor-in-chiefの目視必須項目とする。

### (d) 雰囲気写真(人物・情景。図解・グラフ・表以外の画像)の配置優先順位
1. 図解・グラフ・チャートが入っていない見出しの直下に配置する(視覚要素ゼロの見出しを写真で補う)
2. 該当する見出しがない(全見出しに図解等がある)場合は、文章量が多い見出しの直下を優先する
3. 図解チャートの直後に写真を続けて置く配置(図解+写真の団子)は、writer.md「本文内画像の配置優先順位」3が正(図解以外の視覚要素の連続は、(e)の「違和感」の有無で判断する)

役割分担: **図解=見出し内の「間」(文章の壁を割る)** / **写真=見出し切り替わりの「呼吸」**。この配置決定は機械判定可能なため、`writer.md`の画像指示と`image-selector.md`の配置ロジックに組み込む。

**新設・変更したルールは、新規記事だけでなく既存記事にも遡及検証すること(13節参照)。** 「次回の記事制作から適用する」という前提のまま既存の画像配置を再検証しないと、ルール新設後も違反配置(まとめ見出し直下・診断チャート直後等)が残ったまま「対応済み」と報告してしまう。ルールを書いた時点で、対象とする記事の画像配置を機械的に洗い出し、違反があれば構成マップに含めること。

### (e) 視覚要素の連続配置は「違和感」の有無で判定する(2026-08-13最終改訂、非ブロッキング・`scripts/verify-article.js`項目27)
**視覚要素(chart・アコーディオン・画像・表・コールアウトボックス)の連続配置そのものは禁止しない。** 連続していても、対の関係・補完関係にあり読者に違和感なく流れるなら問題ない(例: `processContrast`で変化を見せた直後に`quadrant`で要因の位置づけを見せる、のような役割分担が明確な組み合わせ)。**問題になるのは「脈絡のない連続」による違和感のみであり、これは機械では判定できない。**

- **判定フロー(視覚配置全般の標準運用とする)**:
  1. `scripts/verify-article.js`項目27が、本文(地の文)を挟まない視覚要素の連続配置をすべて検出し、**候補リストとして出力する(非ブロッキング・機械が修正はしない)**
  2. editor-in-chiefが一次判定する。判定基準は「この連続は対・補完の関係として自然に流れるか、それとも脈絡がなく違和感があるか」。**明らかに脈絡のない連続のみ修正を提案し、判断に迷うものは『ユーザー確認』として残す**
  3. ユーザーが最終判定する。そのため、新規記事の公開前報告・既存記事の対応時のいずれも、**連続箇所リスト(見出し名+要素の並び)を必ず報告に含める**(ユーザーが該当箇所だけを実機で見て判定できる形にする)
- 個数制限(FAQ形式のaccordion連続本数の上限等)は設けない。すべて目視判定の範疇とする
- 背景: 初版は「チャート種別を問わず連続配置を例外なくブロッキング検出する」設計にしたが、この結果「見出しに紐づく複数のchart/accordionはすべて団子」という機械的な扱いになり、FAQのQ1→Q2のような自然な連続や、事前確認チェック+仕組み図解のような妥当な組み合わせまで一律に分離・受け本文の挿入を強制することになった。ユーザー判定により、「連続の可否は違和感の有無で決まり、機械は候補を挙げるだけ、人間が判定する」方式に確定した
- **区切り線(`---`)はリセット要素に含めない(2026-08-13追加)**: 視覚的な間として弱く、400字ルール(a)の「間」としても機能しないため、item23のリセット判定には使わない。見出しの手前で壁を分割したい場合は、区切り線ではなく「コールアウト・表等の実質的な視覚要素を置く」で対応する

### (f) アコーディオンに置くもの(2026-08-13追加)
- **仕組み(制度の構造・計算の段階)・比較・手順**: 図解化を優先する((b)の従来方針のまま)
- 図解に向かない補足・深掘り(本文の主張を読むのに要らないもの)だけをアコーディオンに格納する。本文の説明は移さない(writer.md 規則32(b))

### (g) 図の整理原則(2026-08-13追加。「1見出しに図解は原則1つまで」は撤回)
図は読者理解の補助であり、必要なら多く使ってよい。ただし同一見出し・近接範囲に図・視覚要素が複数必要になる場合は、縦に羅列するのではなく、以下の統合・収納形式で整理できないかを必ず検討すること。
- **横スクロール形式**: 同種の図が複数あるとき1ユニットにまとめる(例: 方式別の仕組み図4枚をスワイプで見る)
- **フローチャート化**: 複数の図で説明しようとしている流れを1枚の分岐図・工程図に統合する
- **アコーディオン格納**: 主要な図1つを本文に出し、補足的な詳細図はアコーディオン内に収める

検討の結果「縦に並べるのが最適」と判断した場合は、その理由を構成マップに明記する。**横スクロールユニット・アコーディオン内部は、(e)視覚要素の連続配置の判定における「1つの視覚要素」として扱う**(ユニット内部の図同士の連続は団子とみなさない)。

**横スクロール形式は`compareScroll`(chart type、2026-08-13実装)で実現する。** 既存`compareCards`(固定4項目: 原因/見た目/かゆみ・痛み/部位)を一般化し、`fields: [{key, label}]`で記事ごとに比較項目を定義できるようにしたもの(お金の記事での例: NISA・iDeCo・課税口座を「非課税の範囲/引き出し/上限額/向く人」で、カード3種を「年会費/還元率/付帯保険」で比べる)。CSSは`compareCards`と同じ`.chart-compare-cards-*`系を流用する。item24 の判定(スクリプトの分類)では NEUTRAL 扱い(`compareCards`と同じ)で HIGH に含めないが、書き手の規則では主役の図解として置いてよい図に数える(writer.md 規則28(b)・表の「図」の欄○。依頼者の決定 2026-09-24)。item24 は参考情報である。横スライドの本数は writer.md 規則28(g)。

**注意: `type`を指定せずchartsに項目を追加すると、フォールバックでrenderBarChartHtml()が呼ばれ、dataが無い場合は何も描画されず空文字列を返す(サイレント失敗)。** アコーディオン(summary/content形式)を追加する場合は必ず`accordions:`配列に書くこと。`charts:`配列に誤って書いた場合、`scripts/verify-article.js`項目28がブロッキングで検出する(サイレント失敗で本番まで長期間気づかれにくいため新設)。

### (h) crossSection図解のleader/ラベル自己検査+自己参照文の禁止(2026-08-14追加)

crossSection図では、①あるleaderの起点が実在しない座標を指す、②ラベルがviewBox右端からはみ出て実機で見切れる、③本文に「(詳しくは上のアコーディオンから読めます)」のような自己参照の誘導文が入る、という不具合が起こりうる。原因はいずれも「執筆エージェントの指示書に該当ルールが存在しない」ことであり、`writer.md`(2-1〜2-4相当のセルフチェック)・`editor-in-chief.md`(対応する目視確認項目)に追記のうえ、以下3項目を機械検査として新設した。

- **項目29(leaderの指示先実体チェック、ブロッキング)**: crossSection型の`leaders[].fromX/fromY`(図形側の起点。`toX/toY`はラベル側の終点で図形から離れているのが正常)が、`parts`のいずれかの図形の描画範囲(±15単位の許容マージン)内にあるかを検査する。範囲外なら「空を指す引き出し線」として差し戻す
- **項目30(SVGラベルの推定占有幅チェック、警告・非ブロッキング)**: 実機幅を保守的に325px、全角1文字をfont-size×(viewBoxWidth/325)の概算幅として、anchor方向の残り余白と比較する。誤検知があり得るため警告のみでブロッキングしない

**追記(2026-08-14)**: 上記の機械検査新設後も、`leaders[]`のラベルフィールドとして廃止済みの`label`(単一文字列)を使ってしまい、`renderCrossSectionDiagramHtml`が参照する`labelMain`/`labelSub`のいずれとも一致しないため**ラベルが常に空文字で描画される**(指示線・ドットだけが見え、タイプ名が一切表示されない)という不具合が起こりうる。項目29(leader実体チェック)・項目30(ラベル幅チェック)はいずれもfrontmatterの座標・文字数のみを検査しており、レンダラー側のフィールド名不一致(＝レンダリング結果が空文字になること)は検出できなかった。

## 26. 昇格ゲート・公開後の信頼性違反対応(2026-08-14追加)

機械的な全件検査(`npm run verify:all`)を一度も通していない記事を、通したことにして扱うと、大量のitem10/11/12違反(B5架空体験・伝聞・頻度断定)や、手編纂リストベースの浄化作業だけでは発見できないBLOCKERが残る。以下2点を恒久ルールとして明文化する。

### (a) 作成中→公開待ち→公開済みの昇格条件

- **作成中→公開待ちへの昇格、および公開待ち→公開済み(公開)は、`scripts/verify-article.js`の全ブロッキング項目Passを必須条件とする。** 昇格・公開を行う担当(スキル run-article-production の流れ・publisher等)の作業報告には、`node scripts/verify-article.js <対象ファイル>`(または該当記事を含む`npm run verify:all`)の実行結果を必ず含めること
- 口頭・目視だけでの「チェック済みのはず」という申告は昇格条件を満たさない。実行結果(overallとviolated itemsの一覧)を報告に添付する
- この条件は新規追加のブロッキング項目にも自動的に及ぶ(13節の遡及検証義務と合わせて、新項目追加時は作成中・公開待ちの記事も再検査対象に含める)

### (b) 公開済み記事に信頼性系ブロッキング違反が見つかった場合の対応

- **item10(B5架空体験)・item11(伝聞)・item12(頻度断定・社会的証明)・出典不整合等、「絶対条件1(a)(b)」(虚偽・伝聞・裏付けなし断定)に直結する信頼性系のブロッキング違反が公開済み記事で発見された場合、即時修正を原則とする**
- 修正に時間を要する(裏付け調査が必要、書き換えの方向性が未確定等)場合は、**修正完了まで該当記事を非公開化し、`サイト運営\記事データ\非公開アーカイブ\`へ移す**
- **非公開化の実行(記事の公開停止)は、性質上「サイト上のコンテンツを取り下げる」という後戻り可能だが影響のある操作のため、必ずユーザー決裁を経ること**。機械検査が違反を検出したことだけをもって自動的に非公開化しない

### (d) 下書きフォルダの廃止(2026-08-19追記)

上記(a)で問題となった`サイト運営\記事データ\下書き\`は、**廃止している(フォルダごと削除する)**。理由は以下の通り。

- 下書きは公開前の初稿の残骸になりやすく、公開版のほうが大幅に長い完成版で、公開版にあって下書きにない情報が多い
- 未検証の一人称体験談(「私も〜」等)が残存した下書きを「使える原稿」と誤認して公開すると、アドセンス審査・ステマ規制上の問題が再発する温床になる
- 同名ファイルが2箇所に存在すると、grep検索が二重にヒットし、`sync-content.js`の対象外である下書き側を誤編集して「修正したつもりで反映されない」事故を招く構造になる
- git追跡済みのファイルは、履歴から復元可能

これに伴い、(a)の「下書きからの昇格」という工程は現在存在しない(2026-10-12に、記事の置き場を作成中・公開待ち・公開済みの3種類にそろえた)。**執筆途中の原稿は`サイト運営\記事データ\作成中\`に置き、公開待ちへ置く時点でverify-article.jsの全ブロッキング項目Passを必須とする**、という形に読み替える。`scripts/verify-all-articles.js`の走査対象からも下書きを除外済み(公開済みの2フォルダのみ)。

### (c) 対象エージェント定義への反映

上記(a)(b)の要旨は、以下のエージェント定義にも追記済み(2026-08-14): `.claude/agents/publisher.md`(公開・昇格実行時の必須確認事項として)、`.claude/skills/run-article-production/SKILL.md`(今の記事制作の流れ。2026-08-14当時の追記先だった `project-manager` は2026-09-11に廃止)。

## 28. 項目33(宣言vs実描画の突き合わせ)と`npm run verify:rendered`(2026-08-14新設)

`lib/posts.js`の`splitHtmlBlocks`には、「⏱30秒でわかる/🔍結論だけ知りたい人へ/🎯まとめカードの3種の単一divボックス直後の見出しへのchart/accordion挿入がサイレント失敗する」種類の不具合が起こりうる。`afterHeading`のテキスト自体は本文の見出しと完全一致していても起こり、`scripts/verify-article.js`(frontmatterと本文Markdownソースのみを見る、`lib/posts.js`のレンダリングロジックを一切import・改修しない設計)の既存項目はこの種の失敗を検出できない。

**設計上の判断**: `verify-article.js`は1記事あたり高速に判定するため意図的に`lib/posts.js`をimportしない設計(同ファイル冒頭コメント参照)であり、この制約自体は今後も維持する。そのため項目33は`verify-article.js`の項目群には統合せず、実際のNext.jsビルドパイプラインを通した後の結果を見る独立スクリプト`scripts/verify-declared-vs-rendered.js`(`npm run verify:rendered`)として実装した。

- **仕組み**: `lib/posts.js`の`embedCharts`/`embedAccordions`に、環境変数`NEVORA_VERIFY_RENDER_MATCH`が設定されている時だけ動作する診断ログ(`[UNMATCHED_CHART]`/`[UNMATCHED_ACCORDION]`)を追加した。`npm run verify:rendered`はこの環境変数を立てて`next build`を実行し、宣言されたchart/accordionのうち実際には本文に挿入されなかったものを集計する。1件でもあればexit 1。
- **実行タイミング**: 全記事を都度チェックする性質のコマンド(1記事単位では実行できない)であるため、`lib/posts.js`のレンダリングロジック(embedCharts・embedAccordions・splitHtmlBlocks・各chart/accordionレンダラー)を変更した場合にのみ実行する。通常の記事執筆・文章修正(`lib/posts.js`に変更が無い場合)では不要。詳細な運用条件は`.claude/agents/nevora-pipeline-verifier.md`「33. 宣言vs実描画の突き合わせ」節を参照。
- **`[EMPTY_CHART]`(2026-08-25追加)**: `embedCharts`は「`afterHeading`が本文の見出しと一致したか」で挿入済み(`used[i]`)を判定しており、**レンダラーが空文字を返したかどうかは見ていなかった**。各chartレンダラーは必須フィールド(`items`/`data`/`layers`等)が配列でない場合に`return ""`する設計のため、**キー名を1語取り違えるだけで図が丸ごと消えたままビルドが通る**。例えば`type: "steps"`の項目キーを`items`ではなく`steps`と書くと図が表示されず、本文からその図への参照が無ければ読者にも執筆側にも気づかれない。対策として、`renderChartHtml`の戻り値が空文字のときに`[EMPTY_CHART]`診断行を出し、項目33で集計してブロッキングする。**チャート型を問わず「必須キー欠落による空描画」を一括で捕捉する**。
- **教訓**: `[UNMATCHED_CHART]`(挿入されなかった)と`[EMPTY_CHART]`(挿入されたが中身が空)は**別の失敗クラス**である。前者だけを見る検査は後者を素通りさせる。新しい検査を足すときは「この検査が通っても壊れている状態はどれか」を必ず一度書き出すこと

- **レンダラー修正と項目23/24/32**: verify-article.jsの項目23/24/32はfrontmatter/本文Markdownソースのみを検査対象とし`lib/posts.js`を一切importしないため、`lib/posts.js`のバグ修正の前後でこれら項目の判定結果に変化は無い(アーキテクチャ上、そもそも影響を受けない)。

## 30. push停止条件・項目35の検査範囲に関する恒久ルール(2026-08-16追加)

- **30-1. push停止条件の解釈に迷った場合は、pushせず停止してユーザー確認を仰ぐ。** 「新規検出が多数の場合はpushしない」のような閾値付き停止条件が指示された際、「多数」「軽微」等の量的表現の解釈に迷う境界事例(例: 対象記事自体は0件だが、検査範囲拡張で無関係な既存記事に多数の新規検出が出た場合)では、自己判断で「対象外だからpushしてよい」と解釈して進めるのではなく、一度停止してユーザーに解釈を確認する。依頼者が不在の回は、停止して確認を待たず、その記事・項目だけを保留にして残りを進め、保留の理由を報告に書く(プロジェクト直下の `CLAUDE.md` の「依頼者が不在の回」のとおり)。
- **30-2. 項目35(実測レンダリング検査)の検査対象は、記事ページ(`/posts/[slug]`)の`.article-body`内SVGテキストに限定せず、悩みページ(`/worry/[slug]`)等の他ページタイプ、および図解ウィジェットが生成するHTML(div/ul等)テキスト要素も含めて検討する。** 項目35が記事ページ(`/posts/[slug]`)しか検査対象にしていないと、悩みページ(`/worry/[slug]`)の`lib/worryContent.js`由来のカードにのみ存在する表示不具合を見逃す。記事ページ以外のページタイプへの項目35の適用範囲拡大は、今後の課題として本ルールに記録する。

- **30-3. 表示不具合の原因調査では、まずデータ/コンポーネントの「定義場所」ではなく実際にページへ描画している「使用場所」(import元を逆に辿る、または実際のDOM/画像を直接見る)から追う。** 定義側のgrep一致だけを起点にすると無関係な箇所の調査で空振りしやすく、実際の画像ファイルを直接確認(`Read`ツールでwebpを開く)して初めて`.article-hero-image`の`object-fit:cover`クロップのような真因(サムネ画像そのものへの焼き込みテキスト)にたどり着けることがある。文言のgrep一致だけで原因箇所を断定せず、疑わしい表示要素を直接目視確認する手順を優先する。
- **30-4. ユーザーに実機確認を依頼する際は、対象を本番URLのフルパスで特定する。** 「〇〇の記事」のような曖昧な指定では、記事ページ・悩みページ(`/worry/[slug]`)・カテゴリページ等どのページを指すか調査側で誤解しうる(30-2の悩みページとの混同の一因)。依頼・報告の双方で`https://nevora-money.vercel.app/posts/xxx`のような完全なURLを明記する。
- **30-5. 引用は逐語のみとし、要約を引用形式(「」やコードブロック)で提示しない。** 一次資料・二次資料からの引用は、実際に取得したテキストをそのまま貼るか、取得できていない場合は「逐語不能」と明記する。二次サイト経由の情報を一次資料からの逐語引用であるかのように提示する誤りを防ぐため、要約と逐語を明確に区別する。

## 31. サムネイル画像のセーフゾーン規則(2026-08-16追加)

記事のサムネイル画像(`thumbnail`)は、コンテキストによって異なるアスペクト比でクロップ表示される(記事ページのヒーロー=`16:9`・`object-fit:cover`、カード=`1:1`・`object-fit:cover`)。**重要なテキスト・要素(タイトル・キャプション・図解の本体等)は、両方のクロップに共通して残る「セーフゾーン」の内側に収めること。**

### 31-1. セーフゾーンの算出根拠

このサイトのサムネイル生成は`3:2`(例: 1536×1024px)を基準とする。`3:2`の画像を`16:9`と`1:1`それぞれに中央基準でクロップした場合に生き残る領域を算出し、その積集合をセーフゾーンとする。

- `16:9`クロップ(横幅そのまま、縦をクロップ): 縦方向の残存率 = `(3:2の縦横比)/(16:9の縦横比)` = `1.5/1.7778` ≈ `84.4%`。上下から均等に`7.8%`ずつクロップされる。→ **縦方向セーフゾーン: 上端7.8%〜下端92.2%(中央84.4%)**
- `1:1`クロップ(縦幅そのまま、横をクロップ): 横方向の残存率 = `(1:1の縦横比)/(3:2の縦横比)` = `1/1.5` ≈ `66.7%`。左右から均等に`16.7%`ずつクロップされる。→ **横方向セーフゾーン: 左端16.7%〜右端83.3%(中央66.7%)**

### 31-2. セーフゾーンの数値(基準サイズ1536×1024pxの場合)

| 方向 | セーフゾーン範囲(%) | セーフゾーン範囲(px、1536×1024基準) |
|---|---|---|
| 横(x) | 16.7%〜83.3%(中央66.7%) | 256px〜1280px(幅1024px) |
| 縦(y) | 7.8%〜92.2%(中央84.4%) | 80px〜944px(高さ864px) |

**基準サイズが異なる場合は、上記%をそのまま画像の幅・高さに乗じて計算する。** 重要なテキストブロック・タイトル・キャラクター等は、この矩形(中央66.7%×84.4%)の内側に配置する。

### 31-3. 運用ルール

- 今後のサムネイル制作・差し替え(既存記事のサムネ更新を含む)は、本規則のセーフゾーン内に重要要素が収まっているかを確認してから採用する。
- セーフゾーンからはみ出す要素がある場合、(a)その要素を画像から削る、(b)ヒーロー専用画像(`heroImage`)とカード専用画像(`thumbnail`)を分離する、のいずれかで対応する(`lib/posts.js`の`heroImage`フィールド、`pages/posts/[slug].js`の`post.heroImage || post.thumbnail`参照)。
- 項目35(実測レンダリング検査)のカードサムネ向けクロップ検査は、「クロップ=不具合」という単純な基準が成立しないため検査対象外とする。本規則(セーフゾーン)を基準に、セーフゾーンの数値を基準にした再設計(セーフゾーン内に収まらない配置を検出する等)を今後の課題とする。

**`text-shape-overlap`(テキスト×図形の重なり、2026-08-24新設、§AF)の補足**: 既存の`collision`はテキスト同士の重なりのみを対象としており、「ラベルが散布図の点や曲線の上に乗る」不具合を検出できなかった。本カテゴリはこれを機械検出するもので、以下の設計とする。

- 検査対象の図形は、SVG内の`rect`/`circle`/`ellipse`/`polygon`/`polyline`/`path`/`line`/`image`と、記事本文内の`img`
- 許容マージンは`SHAPE_OVERLAP_TOLERANCE_PX`(既定3px、`scripts/verify-rendered-layout.js`内の定数)
- `getBoundingClientRect()`は線幅(stroke)を含まないため、strokeを持つ図形は線幅の半分だけ矩形を外側へ広げてから判定する(`inflatedShapeRect()`)。この補正が無いと、太い曲線に文字が乗っていても矩形上は1px未満しか重ならず検出漏れになる
- **`--strict`の合否に算入する(ブロッキング)。** 環境変数`NEVORA_ITEM35_SHAPE_STRICT=1`のときだけ算入する暫定分岐は置かず、他の検出と同じ扱いにする。この環境変数は存在しない

**ビルドが`text-shape-overlap`で失敗した場合の対処手順**

1. **まず原因を「偶発的なかすめ」と「設計上の配置」に切り分ける。** 実際の描画を見て判断すること(検出行の`overlap=WxHpx`だけでは判断しない)。幅768pxで該当図を描画し、文字が図形に埋もれて読みにくくなっているかを確認する
2. **偶発的なかすめ → 座標調整で解消する(原則こちら)。** 引き出し線の終点`toX`/`toY`をずらしてラベルを図形の外へ出す、`viewBox`を必要な向きへ広げる、といった座標のみの変更で対処する。文言の変更が必要だと感じた場合は、着手せず先に相談する。実例と手法は`サイト運営/サイト本体/docs/leader-label-cross-watchlist.md`の「是正のしかた」を参照
3. **設計上の配置 → `leaders[].allowOverlap: true`を付ける。** 図形とラベルが重なる配置そのものが意図的な場合に限る(例: 線が意図的にラベル領域を通る図、パネルの外へラベルを出す配置)。**偶発的に重なっているだけのものに付けてはならない。判断に迷う場合は付けず、相談すること。** 付ける際は、その図で重なりが意図的である理由を記事のfrontmatterにコメントで残す
4. 修正後は必ず`node scripts/verify-rendered-layout.js <slug>`を再実行し、当該記事が0件になったことを確認する。ラベルを移動した場合は、移動先で新たな重なりが生まれていないかをこの再実行で必ず見る(座標を動かして別の図形に食い込んだ実例がある)

引き出し線が自分のラベルの文字の上を通る現象(`text-shape-overlap`の対象外。引き出し線は除外#5)については、`サイト運営/サイト本体/docs/leader-label-cross-watchlist.md`に測定方法・判定基準(横断率50%)・経過観察リストをまとめている

## 33. 件数・集計値の報告ルール(2026-08-17追加)

**件数・集計値を報告する際は、必ず対象の列挙一覧とセットで提示し、一覧から数えた値のみを集計として記載する(集計先行・列挙後付けの禁止)。** 先に見積もり・概算・前回値の流用等で集計値を確定させ、後から裏付けの一覧を作る(または作らない)進め方を禁止する。集計は常に「まず全件を列挙 → 列挙した行数を数える → その数値を報告する」の順で導出すること。

- 先に近似値・前回の集計を報告し、後から詳細な列挙で答え合わせをする順序だと、列挙漏れ(集計対象外の型・判定漏れ)に気づくのが遅れ、集計の訂正が繰り返し発生する。
- 実務上は、レポート内に集計値だけを書かず、必ず列挙一覧(表・箇条書き等)を先に(または同じレポート内に)示し、その一覧の行数=集計値であることが読み手にも検証可能な形にする。

## 39. next.config.jsの`output`設定変更は項目35の検査基盤に影響する(2026-09-27追加)

`サイト運営/サイト本体/scripts/verify-rendered-layout.js`(項目35、実測レンダリング検査)は検査用サーバーの起動方法を`next.config.js`の`output`設定に依存する(`output: "export"`なら`out/`を`serve`で静的配信、そうでなければ`next start`)。

- `output: "export"`を導入したのにこの依存を見落とし、`verify-rendered-layout.js`側が`next start`を呼び続けると、`item35-weekly`ワークフローが全バッチ「"next start" does not work with "output: export" configuration」で落ち、「全カテゴリ0件なのに失敗」という誤解を招く報告になる
- **`next.config.js`の`output`設定(`export`の追加・削除)を変更する場合は、必ず`scripts/verify-rendered-layout.js`の起動方式(`next start` / `serve out/`)が整合しているかを確認し、`node scripts/verify-rendered-layout.js --strict <slug 1件>`をローカルで完走させてから push すること**
- `item35-weekly.yml`の集計には「実行エラー: N件」(起動失敗・ページ取得失敗等の基盤エラー件数)を含めており、検出0件と基盤エラーによる失敗を区別できるようにしてある。Issue本文がこの件数を含めて0件でない場合は、レイアウト検出ではなく検査基盤側の不具合を先に疑うこと

## 40. 台帳(publish-ledger.json)への`requester-visual-check`追記は`scripts/ledger-add-visual-check.js`経由に限る(2026-09-28追加)

- **理由**: 多層判定(`run-local.js`の第1〜6層・self-test)を経ずに、依頼者の目視確認を最終判定として台帳(`scripts/autonomy/publish-ledger.json`)へ`kind: "requester-visual-check"`のエントリを直接追記する運用で、その追記をその場ごとのアドホックなスクリプトで行うと、(a) 追記前に項目35(実測レンダリング検査)を通す確認が保証されない、(b) 承認者・実行日時が記録に残らない、という2つの弱点がある。企画からの全面書き直しが既存記事の項目35対応(座標調整済み図解・短いラベル・heroImage分離)を継承せず、かつpush前にitem35を確認する手順が無いと、実測レンダリング検査で検出が出る。
- **恒久ルール**: 台帳へ`requester-visual-check`種別のエントリを追記する手段は、`node scripts/ledger-add-visual-check.js --slug <slug> [--slug <slug> ...] --reason "<理由>" --commit <コミットハッシュ>`(`サイト運営/サイト本体`がカレントディレクトリ)に限る。このスクリプト以外の方法(台帳ファイルの直接編集・アドホックなワンオフスクリプト)で`requester-visual-check`エントリを追記しない。
- このスクリプトは、対象slugすべてに対し`verify-rendered-layout.js --strict`を内部で実行し、1件でも検出があれば台帳に一切書き込まずに終了する(fail-fast)。承認者(`git config user.name`)・実行日時・理由・対象コミットを必ずエントリに記録する。
- 台帳への書き込みという操作の性質上、このスクリプトの**実行**はAIエージェントではなく依頼者本人が行う(AIエージェントによる台帳の直接書き込みは「ログ・監査記録の改ざん」にあたるため)。エージェントは、修正・検証・スクリプトの用意までを行い、実行コマンドを提示するに留める。
