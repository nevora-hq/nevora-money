## 0. 実行環境(2026-09-11 追加の前提。v5 と同等の強制力を持つ)

- すべての工程(記事の企画・執筆・第1層〜第6層の判定・差し戻し・自動集計・暴走防止・保持削除)は、**このPC上の VS Code 内の Claude Code で実行する**
- 認証は **Claude Code のサブスクリプション認証のみ**。従量課金のAPIキー・認証トークン・クラウド事業者経由の課金は、いかなる工程でも使わない
- GitHub Actions その他の外部実行サービスに、Claude CLI・Anthropic API を呼ぶ処理を置かない(GitHub Actions に残るのは `publish-queue.yml`〔公開キュー〕と `item35-weekly.yml`〔レンダリング検査〕だけで、どちらも Claude・API を使わない)
- 従量課金が発生しうる経路が1箇所でも残っている状態は、設計として未完了とみなす
- 起動は依頼者の指示による(「記事制作を実行して」)。無人の定期起動はしない。「関与ゼロ」は、依頼者が最初に指示したあとは完了まで人が介入しないという意味である(運用期)

## 2. プロンプト改修指示(差分) → U1・U2 に対応

### 2-1. `.claude/agents/writer.md` — 「各見出しに入れる要素(必須・機械検査あり)」を新設 → U1

`# B5ルール` の直前に挿入。要旨:

- 地の文が100字以上ある各H2セクションに、A(具体的な場面)・B(数量・頻度)・C(読者の行動)のうち2種以上を入れる
- 記事全体で、Cを含むセクションが最低1つ必要
- **順序・配置・文体・構成パターンは規定しない。**要素がどこにどの順で現れてもよく、記事ごとに分布が変わってよい
- Aは読者の状況または一般的な場面で満たす。著者の体験談で満たしてはならない(B5ルール = 保護対象P3を壊さないための制約)

この要件が新設である理由は、writer.md の「最重要方針3(具体例・具体的な場面を各見出しに入れる)」が指示としては存在しながら検査されておらず、H2セクションの多くが2種未満になりうること(S1)。

### 2-2. `.claude/agents/writer.md` — 「説明を図表へ逃がさない(必須)」を新設 → U2

- 視覚要素のルール(H2ごと視覚要素・400字ルール・chart2件以上・装飾6箇所以上)を満たすために、本文で説明すべき内容をfrontmatterのchart・accordionのテキストへ移してはならない
- chart・accordionは、本文で説明した内容を整理・要約・対比するものとして置く
- 400字ルールに当たったとき、本文を削って字数を下げる形で回避しない

根拠: 本文Markdownのみでは2000字未満の記事になりうるが、frontmatterの図表テキストを含めれば量は足りうる(S2)。

### 2-3. `.claude/agents/writer.md` — 生成メタ情報の出力を必須化 → U1(第4層の入力を作る)

記事本文とセットで `meta.md`(想定読者・構成とその選定理由・タイトルの約束と回収位置)と `sources.md`(出典URLと**原文の引用**)を残す。第4層はこの2つを入力に取る。無いと設計妥当性と事実性を判定できない。

構成の選定理由には「読者は結論を先に知りたいから結論を先に書いた」のような、どの記事にも書ける一般論を書かない。

## 4. 機械判定の判定条件の定義(§4-3 要素充足方式) → U1

定義の本体は `scripts/autonomy/current-rules.json` の `layer1.elementRequirement` にある。ここには判定方法の要旨だけを記す(条件を2箇所に書かないため)。

```
範囲: 記事本文の各H2セクションのうち、地の文が100字以上のもの
      (見出しが「出典|参考文献|関連記事|あわせて読みたい」に一致するもの、
       最初のH2より前のリード部分は対象外)
要素: A. 具体的な場面 / B. 数量・頻度 / C. 読者の行動
必要数: 2種以上
記事全体: Cを含むセクションが1つ以上
```

**判定方法**: 地の文を文単位に分割し、要素ごとの正規表現で照合する。A・Cは著者を主語とする文(`私は`/`筆者が`/`編集部で`)を除外する(保護対象P3のB5ルールを壊さないため)。Bは西暦の年と箇条書きの序数を除外する。

**必要数の可変性**: セクション長によらず一律2種とした。自動改修サイクルの調整対象に含める。

**例外**: 上記の範囲外(リード・出典セクション・100字未満)。リードは共感フックで読者をつかむ役割であり、読者の行動を示す位置ではないため。

**要素定義の較正**: 既存記事に対して実行し、0種と判定されたセクションを実物で確認したうえで検出パターンを調整する。「〜程度にとどめましょう」「〜タイプに替える」「3タイプ」「2×2」といった、実際には要素が存在するのに検出できていない表現を取りこぼさないようにする。**必要数(2種)は変えない。**

| | 較正前 | 較正後 |
|---|---|---|

既存記事はこの要件を知らずに書かれたものであり、通過率が低いことは「要件が外れている」ことを意味しない。新規記事は要件を渡された上で書かれる。

## 5. 判定項目ごとの入力定義表(§4-5-b) → U1・I1

**この表は「判定プロセスへ渡すデータ」の定義である。記事本文に何を書くかとは無関係である。**

| 判定したいこと | 層 | 判定プロセスへの入力 | 理由 |
|---|---|---|---|
| 要素の有無・数、既存34項目、出典の形式 | 第1層 | 記事本文Markdown + frontmatter構造データ + sources | 照合対象が機械的に定まる |
| 行動可能性・ターゲット一貫性・約束の回収・具体性・意図の伝達 | 第2層 | **読者提示テキストのみ** | 実際の読者と同じ条件にする必要があるため |
| タスク出力が不合格条件に該当するか | 第2層(合否判定側) | **読者提示テキスト + タスク出力**(生成メタ情報は渡さない) | 不合格条件「記事の主張の言い換えにしかならない」「引用箇所を指定できない」は、実行結果と記事本文を突き合わせないと判定できないため。2026-09-10訂正: 記事本文も渡さない設計では不合格条件そのものが判定不能になる。遮断すべきは生成メタ情報であって記事本文ではない |
| 引用を伴う否定が成立するか | 第3層 | **読者提示テキストのみ** | 読者が読める材料だけで否定が成立するかを見るため |
| 構成選定理由の固有性・宣言と実体の一致 | 第4層 | 記事本文 + 生成メタ情報 | メタ情報がなければ判定対象が存在しないため |
| 事実性(数値・出典・要確認候補) | 第4層 | 記事本文 + 収集データ(原文) + 機械検査が挙げた候補 | 照合対象がなければ判定できないため |
| 既合格記事との相対比較 | 第5層 | 判定対象と比較対象の読者提示テキスト(どちらが判定対象かは伏せる) | 単体で「良いか」を問うと甘くなるため |
| 層間の不一致の裁定 | 第6層 | 各層の判定結果と根拠のみ | 記事を読み直すと他層と同じ判定をやり直すため |

**全層共通**: 過去の判定ログは渡さない。差し戻し回数・経過時間・コストは渡さない(判定側が生産効率に関心を持たないようにするため)。

**「入力を渡さない」を一律の方針にしていない。** 第4層は入力を絞らないことが正しい。

## 6. 多層判定システムの仕様(§4-5) → U1・I1

| 層 | 役割 | 判定形式 | 別プロセス |
|---|---|---|---|
| 第1層 | 機械判定(既存34項目 + 要素充足 + 要確認候補の抽出) | 有無・数 | — |
| 第2層 | 読者シミュレーション(タスク実行 → 機械チェック → 合否判定) | タスクの実行可否 | 要 |
| 第3層 | 敵対的検証(落とす側に固定) | 引用を伴う否定の成否 | 要 |
| 第4層 | 設計妥当性 + 事実性照合 | 整合/不整合 | 要 |
| 第5層 | 既合格記事との比較 | 劣後したか | 要 |
| 第6層 | 層間の裁定 | 通過/差し戻し | — |

### 実装上の要点

- **別プロセス**: 判定は、記事の生成とは別の `claude` CLI のプロセスで行う(認証はサブスクリプションのみ。§0)。生成側はエージェント定義を読む必要があるため、リポジトリを作業場所にして動かす。判定側は、CLAUDE.md・auto-memory・hooks を読み込まない状態で起動する(§16)。判定の JSON が返らなかった層は、通過にも差し戻しにもしない(§17)
- **第2層の2段構成**: タスクを実行するプロセスと、その出力の合否を判定するプロセスを分けた。実行者に自分の出力の合否を判定させると自己申告になるため。**合否判定側にも記事本文(読者提示テキスト)を渡す**。遮断するのは生成メタ情報であって記事本文ではない(不合格条件「記事の主張の言い換えにしかならない」「引用箇所を指定できない」は、本文と突き合わせないと判定できない)。本文を渡すことで判定が好意的に戻る懸念に対しては、指示文で「記事の良し悪しを評価してはならない。見るのは実行結果と記事本文の対応関係だけである」「実行結果に書かれていないことを記事本文から読み取って補ってはならない」と明示する。加えて、機械で判定できるもの(項目が3つあるか、引用が本文に実在するか、項目が『〜を理解する』のような内面の状態だけを述べていないか)は機械で判定する
- **第3層の引用検証は機械で行う**: 提示された引用が読者提示テキストに実在するかを文字列照合する。実在しない引用(捏造引用)を伴う批判は否定として採用しない。引用を伴わない抽象的な批判も採用しない。過検出を防ぐため
- **第5層はA/Bをランダムに入れ替える**: どちらが判定対象かを判定プロセスに伏せる
- **第6層**: 初期設定は全層一致で通過。重みは全層1.0。運用ログから層ごとの信頼度が判明した段階で自動調整する
- **判定は二値**。点数化しない
- **実行順**: 第1層 →(第2・3・4層。順に1層ずつ)→ 第5層 → 第6層。第1層で落ちた記事を第2層以降に流さない。第2〜4層のいずれかが差し戻しなら第5層を実行しない

## 7. ログ設計とスキーマ(§6-2 自己完結) → I2

保存先: `docs/pipeline/autonomy/logs/{slug}__{ISO時刻}__r{差し戻し回数}.json`

```
{
  schema, articleFile, articleTitle, articleCategory,
  judgedAt, startedAt, reworkCountBefore, reworkCountAfter, elapsedMinutesTotal,
  finalVerdict: "pass" | "rework" | "halted",
  haltReasonFullText,                     // 上限到達時、条件の全文と到達した値
  layers: [
    { layer, verdict, costUsd, durationMs,
      findings: [ { firedConditionFullText,       // 判定条件の全文(要件名ではない)
                    scopeFullText,
                    elementDefinitionsFullText,   // 要素の定義の全文
                    heading, detectedKinds,
                    offendingTextFull } ],        // 該当テキストの全文
      perTask: { <task>: { taskFullText, failConditionFullText,
                           taskOutputFull, failed, failedBy, reasonFullText } },
      acceptedClaims / rejectedClaims,            // 第3層: 引用と理由の全文
      taskExecutionOutputFull, outputFull,        // 各層の出力全文
      verdictRuleFullText }
  ],
  costUsd, durationMs,
  articleFullTextAtJudgment,              // 判定時点の記事全文
  readerViewAtJudgment                    // 判定時点の読者提示テキスト
}
```

**外部を指す参照を持たない。** ルールファイル名・ルールの生成日時・項目番号だけの参照は書かない。発火した判定条件はその全文を書き写す。既存34項目の違反は、項目番号だけでなく項目名も併記する。

記事全文を持つのは、差し戻しごとに記事がどう修正されたかを、他のどこも参照せずに追えるようにするため。

## 8. 保持・削除の設計(§6-3) → I2

- 保持期間: 180日
- 期間を過ぎたログは本体を削除し、`docs/pipeline/autonomy/archive/` に集計要約を残す
- **集計要約も自己完結させる**: 発火した判定条件の全文・該当テキストの抜粋・タスクの全文・不合格条件の全文を含める。要件名・項目番号・層番号だけの要約は作らない
- **削除処理そのものを記録する**: `archive/deletions.jsonl` に、削除日時・保持条件の全文・削除件数・削除対象の識別情報・残した要約の内容を追記する。集計の母数が変わった理由を追えるようにするため
- 法的・検証上の理由で削除できないログ: 現時点で該当なし(PHASE 1 で確認済み)

## 9. 自動改修サイクルの仕様(§6-5・6-6) → I2

### 9-1. 起動単位(§6-7)

**記事20本ごと。** 期間ベースでは生成ペースの変動で母数が不安定になるため、本数で固定する。20本とした根拠は `current-rules.json` の `cycle.rationale` に全文がある(層ごとの発火率を比較するのに必要な最小規模。最も発火率の低い検査を下限の目安に置くと20本で期待発火数が約1.8件となり、「2サイクル連続で発火ゼロ」を死蔵の判定に使える)。

### 9-2. 自動集計

- 通過率・停止率・1記事あたり判定回数・コスト
- 層ごと: 実行数・差し戻し数・発火率・**単独検出率**(その層だけが差し戻しにした割合)・1検出あたりコスト
- 層どうしの一致率
- **判定条件ごとの発火数**(条件の全文をキーにする。項目番号や層番号ではないため、ルールが更新されても過去の集計と突き合わせられる)
- 一度も発火していない条件・層
- 常に発火する条件
- **過検出の推定**: 差し戻された次の判定で、記事本文がほとんど変わらない(変更率2%以下)まま同じ層が通過に転じた場合
- **見逃しの推定**: 一度通過した記事が後の再判定で差し戻しになった場合。再判定は、記事制作の実行(`run-local.js`)のたびに regression の工程で、通過済みの記事から1本を選んで行う(2026-09-11改訂)。回帰判定のログは `isRegression: true` を持ち、新規記事の通過率の母数からは外す。第4層の事実性照合で差し戻しになった場合は、公開済みの記事に誤情報が残っている可能性があるため `docs/pipeline/autonomy/regressions/` に区別して記録する
- **停止発生率**(上限到達でサイクルが止まった割合)

### 9-3. 自動調整

対象は判定側だけ(要素定義・必要数・判定条件・層の重みづけ・層の増減・実行タスクの文面・入力定義)。

- **層の重みを上げる**: 単独検出率が50%以上の層。他層が拾えない問題を検出している証拠のため
- **廃止候補として記録**: 20回以上実行して一度も差し戻しを出していない層
- **検出定義の見直しとして記録**: 過検出と推定された差し戻しが3件以上ある条件。**必要数は変えず、検出パターンの定義を見直す**
- **上流原因として記録**: 発火率が90%以上の条件。ほぼ全件で発火する条件は、判定側が緩すぎるのではなく、生成側がその要件を満たせていないことを示す。**判定側では調整しない**

生成プロンプトは自動調整の対象外とする。生成側に原因があると判明した場合は、その事実を記録して可視化する(§6-4「止まることは要件が外れている証拠であり、可視化されているほうが望ましい」)。

### 9-4. 暴走防止(§6-6)

検出条件:

1. 通過率が3サイクル連続で上昇した
2. 2サイクル連続で一度も差し戻しを出していない層がある
3. 1回の自動調整で緩められる上限(必要数は1段階まで、数値閾値は現行値の20%まで)を超える調整が算出された
4. 通過率を下げる役割を持つ第3層(敵対的検証)が廃止候補に挙がった

検出時の動作:

- **自動調整を停止する**(`autoTuning.stopped = true`)。現行ルールをその時点で固定する
- 記事生成と判定は、固定された現行ルールで継続する
- 停止した事実と、停止の原因となった集計結果を記録する
- **自動で緩める方向にも、自動で厳しくする方向にも戻さない。** 旧バージョンが存在しない以上、過去バージョンへの復帰は取れない。停止して現状を保つのが、誰も見ていない状態での最も安全な動作である
- 一度停止したら自動では再開しない

### 9-5. ルールは常に1つ(§6-1) → I3

- 実行領域に置く判定ルール定義は `scripts/autonomy/current-rules.json` ただ一つ
- 改修時はこのファイルを上書きする。旧版を残さない
- バージョン番号を持たない
- `editor-in-chief.md`・`final-review-scoring/SKILL.md`・`writer.md` には判定条件を書かない(仕上げの観点と執筆の指示だけを残す)

診断で見つかった二重定義(90点上限 vs 80〜99点公開可)は、点数という中間値を置いたことが原因だった。判定を二値にし、判定を行う場所を1箇所に集約することで、同じ食い違いが起きる余地をなくした。

## 10. コスト設計(§4-5-g) → 実測値

**従量課金は使わない(§0)。** claude CLI はサブスクリプション認証で動くため、判定・生成の呼び出しに料金の請求は発生しない。代わりに、サブスクリプションの使用量(利用上限)を消費する。

判定1巡あたりの目安(sonnet、記事1本1巡。層ごとの換算値と所要は実走で記録する):

| 層 | CLI が出す API 換算値(請求ではない) | 所要 |
|---|---|---|
| 第1層 |  |  |
| 第2層(実行 + 合否判定の2回) |  |  |
| 第3層 |  |  |
| 第4層 |  |  |
| 第5層 |  |  |
| **1巡合計** |  |  |

- 換算値は、サブスクリプションの使用量の相対的な大きさの目安として記録する(判定ログの `costUsd` も同じ値)。請求額ではない
- 1巡で claude を最大5回呼ぶ(第2層2回・第3〜5層各1回)。これに企画・執筆・修正の呼び出しが加わる
- 上限: 1記事あたり差し戻し5回 / 処理時間60分(依頼者の確認待ちの時間は含めない)。**いずれかに達したら停止**(2026-10-11 依頼者の決定: 差し戻しは1つの記事で合計5回、第3層はそのうち1回まで。§64)
- 処理時間の上限は 2026-09-12 に30分から60分へ変えた(依頼者の決裁)。第2〜5層は1回あたり数分かかり、企画・執筆(執筆の工程は上限25分)を含めると、差し戻しが1回あるだけで30分に達しやすいため。差し戻しの回数の上限は5回
- 全体の処理時間の上限は90分のまま(1本に60分使うと、回帰判定・集計・報告に残るのは30分)
- 前段フィルタ: 第1層で落ちた記事は第2層以降を実行しない(claude を呼ばずに差し戻す)
- 打ち切り: 第2〜4層のいずれかが差し戻しなら第5層を実行しない
- 使用量に対して検出の少ない層は §9-3 の自動集計(1検出あたりの換算値)で見直す

**上限到達時の動作**: その記事の処理を停止し、公開工程へ進めない。**同時に記事制作サイクル全体を停止し、次の記事の生成を開始しない。** 停止の記録が `docs/pipeline/autonomy/halts/` に残っている間、`run-local.js` は新しい記事を作らない(self-test のあと regression へ進む)。「保留」という状態は作らない。時間切れ・回数切れが暗黙の合格になる経路は存在しない。

## 11. 設計期の確認項目リスト(§7)

`node scripts/autonomy/report.js` が `docs/pipeline/autonomy/REPORT.md` に出力する。

1. 判定が通過/差し戻しになった根拠 — どの層の、どの判定条件が、どのテキストで発火したか(条件は全文、該当テキストも全文)
2. 層ごとの発火状況(実行数・差し戻し数・発火率・単独検出数)と、層間で判定が食い違った記事の一覧
3. 各層の実行タスクとその出力全文
4. 通過率と差し戻し理由の分布の推移(サイクルごと)、および発火した判定条件の全文と発火数
5. 自動調整の差分 — 何をどう変えたか、適用しなかった提案とその理由
6. 自動調整が停止した場合、その原因となった集計結果
7. 層ごとのコストと検出量の対比(1検出あたりコスト)
8. 過検出と推定された差し戻し、見逃しと推定された通過、上限到達で停止した記事

**設計期に確認すべき点**(挙動が正しいかを目視で見る対象):

- 第3層が採用した否定が、実際に読者にとって問題か。引用が本文に実在しているか
- 第2層のタスク出力が、読者として妥当な内容か(タスクを実行せず評価を返していないか)
- 第4層が、生成メタ情報の選定理由を一般論と正しく判別しているか
- 第1層の要素充足が、実際には要素があるセクションを落としていないか(過検出)
- 処理時間の上限(60分)に当たる頻度。当たり続ける場合、判定条件が外れている可能性がある
- 公開待ちに置かれた記事に `publishAt` が付いていないこと(公開されていないこと)

## 12. 誤読検出の実施結果(§8)

成果物(`current-rules.json`、`writer.md` の追加部分)を、この設計を書いた文脈を持たない別プロセスに渡し、**実行させず解釈だけを述べさせる**。

### 誤読の指摘と修正の記録

| 指摘 | 修正 |
|---|---|
| 「記事本文」が二重の意味で使われる(公開されるもの全般 / H2の地の文のみ) | `_terms` に「地の文」を定義して分ける。要素充足の `conditionText`・`scopeText`・writer.md は「地の文」に統一する |
| 自動改修・ログ削除・報告の実行主体が不明で、報告先が人間と読まれる | `_actors` に判定・生成・集計・削除の実行主体を明示する。上限到達時の `report` は、人が読む前提の報告ではなく次のサイクルを止めるための記録とする |
| 第4層の実行タスクが項目番号で外部参照している(判定プロセスは項目番号を知らない) | taskText から番号を外し、候補の内容(商品名の実在未確認・主語省略の体験談の疑い・図表と本文の数値の不一致)で記述する |
| `promotedItems` の名称が「第1層でブロッキング化された」と読める | `machineFlaggedCandidates` とし、「第1層はこの3項目について合否を決めない(候補を渡すだけである)」を条件文に明記する |
| 「渡さない」が記事本文への制限と読める | `_scopeWarning`: 「入力に含めない」は判定プロセスへ渡すデータの話で、記事本文に何を書くかへの制限ではない。記事本文は作成者の意図が読者に伝わるように書く |

別プロセスに解釈だけを述べさせると、本文要件と入力制限の区別は付き、意図の隠蔽や構成の画一化は明示的に否定されていると読まれる。残りうる条件付きリスク(「一文だけを前後の否定文から切り離して読むと誤読されうる」)に対し、layer2・layer3 の `inputRationale` は否定を文頭に置き、要素充足の `conditionText` には「要素がどこにどの順で現れるかは問わない」を含める。

### 検出できなかったが記録しておく事項

記事本文の構成を固定する要素として、`writer.md` の既存ルール(まとめは単一H2 + 箇条書き + 次の一歩の一文)が残っている。これは過去の不具合(まとめの二重表示)への対処として存在するもので、保護対象を壊さないため変更しない。

## 13. 設計期モードと運用期モード(2026-09-11 追加)

v5 §1-3 は、設計期(挙動を目視で確認する)と運用期(関与ゼロ)を分けている。`run-local.js` はこの2つをモードとして持つ。設定は `scripts/autonomy/run-mode.json`。

| モード | 動作 | 状態 |
|---|---|---|
| 設計期(design) | 工程を1つ実行するたびに止まり、停止点の報告(その工程で生成・判定されたもの、判定条件の全文、該当テキスト、引用、差分)を出して、依頼者の「次へ」を待つ。1回の起動で実行する工程は1つだけで、依頼者の指示なしに次の工程へ進まない | お金サイトの現在は運用期のため今は使わない(設計期モードという仕組み自体は残り、`run-mode.json` の `mode` を依頼者の指示で `design` にすれば使える) |
| 運用期(operation) | 止まらずに最後まで実行する | **お金サイトの現在の期**(2026-10-10 に依頼者の指示で切り替え済み。切替日時と指示の原文は `run-mode.json` に記録する)。切り替えは依頼者の明示的な指示があったときだけ行う |

- 2つのモードは、**同じ工程を同じ順序で実行する**(工程の実装は `run-steps.js` ただ一つ)。違うのは、工程と工程の間で止まるかどうかだけである。モードごとに別の実装を持つと、実行経路が2つになる(§15)
- 停止点: self-test 完了 / 企画完了(執筆前) / 執筆完了(判定前) / 第1〜5層の各層の判定完了 / 第6層の判定完了(差し戻し理由の提示・公開待ち配置の直前・上限到達の停止を兼ねる) / 修正版の生成完了(再判定前) / 公開待ちへの配置完了 / regression・retention・aggregate・report の各完了。既存記事の修正版(§18)では、企画・執筆の代わりに「既存記事の修正版の準備完了」、公開待ちへの配置の代わりに「元の記事ファイルの置き換え完了」
- 第6層の停止点は、差し戻しならその差し戻し理由(執筆側へ渡す内容の全文)を、通過なら公開待ちの置き先を示す。どちらも、その時点ではまだ何も実行していない(次へで修正または配置を行う)
- 公開待ちへの配置の完了は、依頼の停止点の一覧には無いが、1回の指示で2つの工程(配置と regression)を実行しないために止まる
- **切り替えは依頼者の指示によってのみ行う。** システム側が「設計が固まった」と自己判断して切り替えることを禁止する。`run-mode.json` の `mode` を `operation` にしても、切り替えた日時(`switchedAt`)と依頼者の指示の原文(`switchInstructionFullText`)が無ければ、`run-local.js` は起動を受け付けない
- お金サイトの切り替え(2026-10-10): 依頼者が「運用期・設計期などありません。すべて運用期です。」と指示した。`run-mode.json` の `mode` は `operation` で、`switchedAt` と `switchInstructionFullText` にこの日時と原文を書く(キーの構造は変えない)。システム側の自己判断で切り替えたものではない
- 運用期の起動方法(このPC上のタスクスケジューラ等)は、切り替えの前後を問わず、依頼者から設計の指示を受けたときに設計する(切り替えの書き換えのときに、あわせて設計・設定はしない)。切り替え規則の全文は `run-mode.json` の `switchRuleFullText` にあり、スキル `run-article-production` に一字一句同じ文を載せている(テストで一致を確かめる)
- 処理時間(30分の上限)は、工程の実行に要した時間だけを積み上げる。設計期に依頼者が確認している時間は含めない(含めると、確認しているだけで上限に達するため)。`current-rules.json` の `limits.onLimitReached.conditionText` も「その記事の処理時間(企画・執筆・判定・修正の各工程を実行していた時間の合計。設計期モードで依頼者の指示を待っていた時間は含めない)」に改めた(2026-09-11)

## 14. 公開ゲート(2026-09-11 追加)

記事がサイトに出る入口は2つある。どちらにも、同じ照合を置いた(`scripts/autonomy/publish-gate.js`)。

| 入口 | 照合 | 通過記録が無い場合 |
|---|---|---|
| 公開キュー(`queue-release.js`。GitHub Actions の publish-queue.yml から30分おき) | 公開待ち → 公開済みへ移す前 | 移さず公開待ちに残す(ログに理由を出す。30分おきの失敗扱いは Issue のコメントを積み上げるため、失敗扱いにはしない) |
| サイトのビルド(`sync-content.js`。next build / next dev の前) | 公開済みをサイトへ取り込む前 | 取り込まない。台帳が無い場合はビルドを失敗させる(空のサイトを公開せず、直前の公開を残すため) |

- 照合するのは「内容の指紋」: 記事ファイルから、公開日・画像・表示位置の指定(`date`・`publishAt`・`updatedDate`・`thumbnail`・`heroImage`・`popular`・`featured`)、HTML コメント、画像だけの行を除いた残りの SHA-256。文章・見出し・図表・折りたたみ・要約・出典・タイトルのどれかが1文字でも変われば値が変わる。画像の追加や公開日の割り当てでは変わらない(queue-release.js が行う公開日の書き換えでも変わらない)
- 台帳(`scripts/autonomy/publish-ledger.json`)に記録するのは、`run-local.js` の公開待ち配置の工程と、既存記事の修正版で元の記事を置き換える工程(`replace`)だけ。多層判定を通過した直後の内容を記録する。配置の前に、判定を通過した時点の内容から書き換えられていないことを確かめる
- 照合は Node の標準モジュールだけで行う(公開キューのジョブは依存パッケージを入れない。Claude・API は使わない)
- 公開済みへファイルを置く操作そのもの(エージェントの書き込み・手作業)は技術的に止められない。止めているのは、判定を通っていない内容が「公開済みへ移される」経路(公開キュー)と「サイトに取り込まれる」経路(ビルド)である
- **基準線**: 公開ゲートを入れた時点で公開済みにあった記事は、`kind: baseline` として台帳に載せる。**これらは多層判定を通っていない。** 内容を変えると記録が当てはまらなくなり、判定を通るまで公開に入らない。公開待ちにあった判定前の記事は基準線に入れない。基準線の記事は、§18 の経路で判定にかける対象とする
- 台帳が既にあるときは基準線を作り直さない(作り直すと、その時点で置かれていた判定前の記事まで通してしまうため)

### 14-1. 飛ばした記事の記録(2026-09-12 追加)

ビルドも公開キューも止めない代わりに、**飛ばした事実は必ず残す**。運用期は誰も見ていないため、黙って飛ばすと、記事がサイトに出ていないことに気づけない。

- 記録先: `docs/pipeline/autonomy/publish-skips/<入口>__<理由>__<記事のファイル名>__<指紋の先頭12文字>.json`。判定ログと同じ保持・削除の対象(§8。`retention.js` が保持期間を過ぎた記録を `archive/` へ写して本体を消す)
- 記録の中身(自己完結。他のファイルを参照しなくても分かる): 記事のファイル名とパス / 入口(ビルド・公開キュー)とその説明 / 理由(**通過記録なし**=台帳にこのファイル名の記録が1件も無い、**指紋不一致**=同じファイル名の記録はあるが指紋が違う) / 照合に使った条件の全文(指紋の求め方を含む) / 照合した値そのもの(記事の指紋と、台帳にある同じファイル名の指紋) / 台帳の場所と記録件数 / 日時 / この記事がどうなるか / 重複の扱い
- **同じ入口・同じ記事・同じ内容・同じ理由の記録は書き足さない。** 30分おきに動く公開キューや、ビルドのたびに記録が増え続けないため。記録の日時は、その組み合わせで最初に飛ばした時刻である。内容が変われば指紋が変わるため、別の記録として残る
- 記録の全文は標準出力にも出す。Vercel のビルドや GitHub Actions のランナーで書いたファイルは、その実行が終わると消えるため
- **公開キュー(Actions)で書いた記録は commit しないと残らない。** `publish-queue.yml` の commit の対象に `docs/pipeline/autonomy/publish-skips` を加え、公開が0本でも記録が増えていれば commit するようにした(保護対象 P5 に触れる変更。記録が書き足されないため、commit が30分おきに増えることはない)
- **Vercel のビルドで書いた記録は残らない**(Vercel からは commit できない)。残るのは Vercel のビルドログ(標準出力)だけである。手元でのビルド・同期(`npm run build` / `npm run dev` / `npm run sync-content`)で書いた記録は残る
- そのため、**同じ照合を公開キューのジョブ(GitHub Actions)でも行う**(2026-09-12 追加)。`publish-queue.yml` に、公開の処理とは別の工程として `node scripts/autonomy/publish-gate.js --audit` を置いた
  - 対象は**サイトのビルドが取り込む2つのフォルダ(公開済み)の全記事**(`publish-gate.js` の `AUDIT_DIR_NAMES`)。照合して、通過記録の無い記事の記録だけを書く。**記事の移動・削除・公開の判断は一切しない**(公開の処理は queue-release.js が行う)
  - 2026-09-12 追加: **公開済みも対象に含める**。公開済みを外すと、公開待ちから移したあとに書き換えられた記事が点検から外れる(サイトのビルドは公開済みも取り込むため、サイトには出続ける)。対象フォルダが `sync-content.js` の取り込み元と同じであることはテストで確かめる
  - 記録の形式・重複の扱い・保持期間は、ビルドや公開キューが書く記録と同じ。入口(`source`)は **`site-articles-audit`**(サイトに出る記事を点検する工程)で、どの工程が書いたかが記録から分かる。既存の入口(`sync-content`・`queue-release`)と同じく、工程1つを表す小文字ハイフン区切りの名前である
  - この名前は**対象のフォルダ名を含めない**。対象は「サイトに出る記事」という条件で決まり、そのフォルダが増減しても名前は変えない(2026-09-12 に改名した)。どのフォルダの記事かは記録の `filePathFullText` に入っている
  - これにより、指紋不一致(判定を通ったあとに記事が書き換えられた)が、運用期でも30分おきに検出され、記録として残る
  - この点検が見ないもの: 公開待ちフォルダ(公開キューの処理そのものが照合する)と、サイトに出ない非公開アーカイブ

## 16. 判定側の文脈遮断

判定側の claude は、次の方法で起動する(`judge.js` の `judgeInvocation()`。起動方法はここだけに定義する)。

| 項目 | 設定 | 理由 |
|---|---|---|
| 起動オプション | `--safe-mode` | CLAUDE.md・skills・plugins・hooks・MCP・カスタムエージェント等を読み込まない。認証は通常どおり(サブスクリプション認証のまま使える) |
| ツール | `--tools ""`(1つも持たせない) | 判定は入力のテキストだけで行う。ファイルを読むツールがあると、CLAUDE.md や記事データを自分で読みに行ける |
| 作業場所 | リポジトリ外の空のフォルダ(`os.tmpdir()/nevora-judge-isolated`) | `--safe-mode` でも、リポジトリ内で起動すると git status(ファイル名)がシステムプロンプトに入る。リポジトリ内に作業場所を置く設定は例外で止める |

- 従来の起動方法では、ユーザーの CLAUDE.md・リポジトリの CLAUDE.md・記憶の索引(MEMORY.md)・hooks の出力が判定プロセスに入り、hooks も実行される。上の起動方法では、どれも入らず、hooks も実行されない(目印入りの CLAUDE.md と hooks を置いたフォルダ・サイト本体・空のフォルダの3か所で比べて確かめる。モデルの応じ方に左右されない確かめとして、同じプロンプトの入力トークン数を、目印を仕込む前と後で比べる。従来の起動方法では増え、上の起動方法では増えない。judge.js の `callClaude` そのものでも確かめる。VERIFICATION.md)
- 判定側に渡る文脈の量は、大きく減る(使用量の面でも有利)
- `--safe-mode` は Claude Code の起動オプションである。将来 CLI から無くなった場合は、未知のオプションとして claude の起動が失敗し(`error: unknown option`、終了コード1)、判定を経ていない層として異常で止まる(§17)。通過にはならない
- 生成側(企画・執筆・修正)は、エージェント定義と CLAUDE.md を読む必要があるため、従来どおりリポジトリを作業場所にして起動する

## 17. 判定の JSON が返らなかった場合

judge.js は、判定の JSON を取り出せない場合に空の答えとして扱わない(空の答えは第3〜5層で「否定なし・不合格なし」=通過になってしまうため。claude の呼び出しが失敗した場合も同じ)。

- 第2層(実行側・合否判定側)・第3〜5層で、claude の呼び出しが失敗した、JSON を取り出せない、JSON が決められた形でない場合は、その層の判定を `error`(通過でも差し戻しでもない)とし、理由を記録する
- 形として確かめるのは、欠けていると「不合格ではない」=通過と読まれてしまう項目である(第2層の合否の5項目が真偽値・第3層の claims が配列・第4層の各タスクの failed が真偽値・第5層の better が A/B/equal)。第2層の実行側は、機械照合に使う action(配列)と promiseQuote(文字列)を確かめる
- 第6層は、`error` の層があれば判定を確定しない。その記録は判定ログの場所(`logs/`。集計・回帰判定・保持期間の処理が読む)には書かず、`judge-errors/` に書く(集計に「判定できなかった」を混ぜないため)
- run-local.js の経路では、`error` の層が出た時点でその工程を異常にして止める(判定ログも書かない)。回帰判定では、判定を確定できなかった記事を見逃しの検出に数えず、regression の工程を異常にする
- 判定の中身(各層の判定条件・通過/差し戻しの基準)は変えていない。変えたのは「判定できなかったときの扱い」だけである
- モデルが判定の JSON に末尾のカンマを入れると、JSON として読めずに `error` になる。通過にはならないが、工程は異常で止まる(誤って止まる)
- **JSON を取り出せなかった場合は、同じ入力で同じ層をもう一度だけ実行する**(2026-09-12 依頼者の決裁)。2回目も取り出せなければ `error` にして工程を止める。やり直しは1回までで、それ以上は繰り返さない
  - **読み取りそのものは緩めない。** 末尾のカンマなどを通す変更(通りやすくする方向の変更)はしない
  - やり直すのは「JSON を取り出せなかった」場合だけである。claude の呼び出しが失敗した場合(呼び出しの失敗)と、JSON は取り出せたが決められた形でない場合(判定の中身の問題)は、やり直さずに `error` にする
  - やり直したことは層の記録に残す(`parseRetry`: やり直しの規則の全文・1回目の出力の全文・2回目で読めたか)。費用と所要時間は2回の合計にする

## 18. 既存記事の修正版を判定にかける経路

公開ゲート(§14)により、基準線の記事を1文字でも直すと、判定を通るまでサイトに取り込まれない。既存記事を直す(アフィリエイトリンクの追加・誤字の修正・架空の体験談の削除など)ための、判定を通る経路を設けた。起動経路は `run-local.js` ただ一つのままである。

- 起動: `run-local.js start --revise <記事パス> [--instruction "<修正指示>"]`。対象は `記事データ/公開済み`・`公開待ち` の直下の記事だけ。`--theme` と一緒には使えない
- 工程: self-test → **修正版の準備** → 第1〜6層(新規記事と同じ。差し戻しなら修正 → 第1層へ)→ 通過なら **元の記事ファイルの置き換え** → regression → retention → aggregate → report
- 依頼者の判断(2026-09-11)による仕様:

| 決めたこと | 仕様 |
|---|---|
| 修正の担い手 | 依頼者の修正指示(そのままの言葉)を writer に渡して直させる。指示が無ければ本文は1文字も変えず、判定だけ行う |
| 第4層の入力 | 既存記事には生成メタ情報・収集データが無いため、修正版の準備の工程で writer に作らせる(記事本文は変えない。出典は WebFetch で確かめたものだけ) |
| 通過後の置き場所 | 元のファイルを、ファイル名(URL)を変えずに置き換え、公開ゲートの台帳に記録する。サイトへの反映は依頼者の push の指示のあと |
| 公開待ちの記事の publishAt | そのまま残す(push のあと、予定の時刻に公開キューが公開する) |

- 守り: 修正版の準備の工程で元の記事が変わったら異常 / 修正指示が無いのに本文が変わったら異常 / 生成メタ情報・収集データが無ければ異常 / 置き換えの前に、判定を通過した内容から書き換わっていないこと、起動したあとで元の記事が書き換えられていないこと(書き換えを消さないため)、date・publishAt が元の記事と同じことを確かめ、どれかが違えば置き換えない / 上限到達・異常のときは元の記事に触れない / 第5層の比較相手から、修正前の元の記事を除く
- 変更前の内容の複製を、作業フォルダ(`記事データ/作成中/<記事フォルダ>/original.md`)に残す。追跡済みのファイルは git の履歴にも残る
- 修正版の準備の時間は、記事の処理時間(30分の上限)に数える

## 19. 地の文の連続文字数の上限(項目23)を400字に戻す

- 現在は多層判定の第2〜5層が内容そのものを判定する。**形式で内容を代替する必要がない**

## 20. サムネイルが無くても公開される(依頼者の決定: 記事は画像なしで公開してよい)

### 変更前の状態と、その問題

`verify-article.js` の項目16(frontmatter必須項目)が `thumbnail` の空をブロッキングで No にしていた(2026-08-11 追加)。第1層はこのスクリプトをそのまま呼ぶため、**画像を用意できない環境では、記事の中身の判定に一度も進めない**。差し戻しを繰り返しても画像は増えないため、上限(差し戻し5回・60分)に達して止まる経路になっていた。

### 変更後

**要件は緩めない。検査の場所を、記事の中身の判定(第1層)から公開の直前へ移す。**

| 場所 | 何をするか |
|---|---|
| `verify-article.js` 項目16 | `thumbnail` を見ない(title・description・category・date・summaryPoints はそのまま必須) |
| `scripts/queue.js`(公開予定の割り当て) | `thumbnail` を見ない。サムネイルが空でも `publishAt` を付ける |
| `scripts/queue-release.js`(公開済みへの移動) | サムネイルが無くても移す(依頼者の決定: 記事は画像なしで公開してよい)。`queue-release.js` に、サムネイルを確かめる処理は無い |
| 判定を通過して公開待ちにある記事 | `thumbnail` が空でも**正常な状態**。`publishAt` は付き、そのまま公開される。画像は公開のあとでも足せる |

### 指紋が変わらないようにしてある理由

`thumbnail` を後から埋めると記事ファイルは変わるが、**公開ゲートの指紋の計算からは `thumbnail` を除いてある**(`VOLATILE_KEYS`)。除いていないと、判定を通った記事が画像を入れた瞬間に指紋不一致で止まる。除くのは `thumbnail` という項目そのものだけで、記事の文章・図表のテキストは1文字も除かない。この理由は `publish-gate.js` の `FINGERPRINT_RULE`(記録に入る条件文)に明記した。

`VOLATILE_KEYS` には `date`・`publishAt`・`updatedDate`・`heroImage`・`popular`・`featured` も入っている(公開ゲートを作った時点からの設計)。**これらを今回減らしていない。** 減らすと台帳にあるすべての記事の指紋が変わり、公開済みの全記事が公開ゲートで止まるため。

## 21. 判定側を直したときのやり直し(retry)

停止点で待っている実行に対して、**記事ではなく判定側(判定条件・機械判定のコード・指示文)を直したあと、同じ記事で判定をもう一度実行する**操作。

**指定した判定工程から始め、第6層(判定の確定)まで続けて実行する**(2026-09-12 に拡張)。直した層より後の判定は、古い前提で作られているためである。

```
node "サイト運営/サイト本体/scripts/autonomy/run-local.js" retry --at <停止点の番号> --reason "<判定側の何を直したか>" [--through <工程>]
```

| 決めたこと | 内容 |
|---|---|
| どこからやり直すか | `--at` に**これまでの判定の停止点の番号**を指定する(現在の停止点でなくてよい)。そこから第6層まで続けて実行する |
| どこまで実行するか | 既定は第6層まで。`--through` を付けると**その工程で止める**(2026-09-12 追加)。直した層の効果だけを見て、後続は「次へ」で1つずつ進めたい場合に使う。工程IDでも層の番号でも指定できる(`--through layer2` / `--through 2`)。やり直す工程より前の工程は指定できない |
| 途中で止まらない | 設計期でも、やり直しの途中では工程ごとに止まらない(記事の内容は変わらず、判定側の是正の効果を確かめる操作のため)。各層の結果は通常どおり `results/` に残す |
| 前の結果を残す | 前の工程の結果ファイルは上書きしない。新しい番号の結果として書く(例: `04_layer1.json` は残し、`08_layer1.json` を作る) |
| 差し戻しの回数 | **増やさない。** 差し戻しは記事側の問題で記事を直させる操作、やり直しは判定側を直したことによる再実行であり、別のものだから |
| やり直しの記録 | `runs/<実行ID>/retries/<やり直した停止点>_<工程>__<新しい停止点>.json` に自己完結の形で書く。やり直した理由の全文・やり直しの規則の全文・前の結果・前後の差し戻し回数・記事の SHA-256 に加えて、**どの工程からどの工程まで実行したか**(`executedFromStepId`・`executedThroughStepId`・`executedStops`・`executedFullText`)を含む |
| 差し戻し回数の戻し方 | やり直す工程が最初に動いたときの差し戻し回数に戻してから実行する(`results/` の `statePatch.judgment.round`)。戻さないと、第1層からやり直したときに第6層が回数を1つ増やしてしまう(第1層は `state.round` を判定に写すため) |
| 理由の必須 | `--reason` が無いと受け付けない(何を直したから再実行するのかが残らないため) |
| やり直せる工程 | 判定の工程だけ(`selfTest`・`layer1`〜`layer6`)。記事を作る工程(企画・執筆・修正)はやり直せない(同じ記事でやり直す操作のため) |
| 処理時間 | 実際にかかった分を加算する(時間は実際に消費しているため) |

## 24. 項目23 が記録する数値の意味

同じ記事(`articleSha256` が同一)でも、上限を変えると**記録される数値が上限に応じて変わってしまう**問題があった。

### 理由(実装のどこがそうだったか)

`checkItem23` は本文を1行ずつ読み、視覚要素に当たらない限り `runChars` に字数を足していく。旧実装は `runChars >= 上限` になった**その行で違反を記録し、`flaggedForCurrentRun = true` にして、その連続についてはそれ以上記録しなかった**。つまり記録される `charCount` は「その連続の実際の長さ」ではなく「**上限に達した行までの累計**」だった。上限が小さいほど早い行で到達するため数値も小さくなる。`endLine` も同じ理由で、連続の終わりではなく到達した行を指していた。

### 直した内容

**記録する数値を「連続の実際の長さ」に揃えた**(条件文の「地の文の連続文字数」という言葉と一致させた)。

- 連続が途切れた時点(視覚要素に当たった時点・本文の終わり)で、その連続の全体を記録に確定する(`flush()`)
- `charCount` = 連続の実際の長さ / `endLine` = 連続の終わりの行。**上限の値を変えても変わらない**
- 上限に達した時点の情報は捨てず、`reachedLimitAtLine`・`reachedLimitAtChars` に別に残す
- 判定条件の全文(`note`)にこの区別を明記した。判定ログの数値と条件文の意味がずれた状態を残さない

## 25. アコーディオン(折りたたみ)は、読者が開かない前提で判定に渡す

### 直した理由

第2層(読者シミュレーション)・第3層(敵対的検証)・第5層(比較判定)は、**実際の読者と同じ条件で読む**ことが要件である(v5 §4-5-b)。しかし `reader-view.js` は、アコーディオンの中身を**開いた状態で全文含め**、見出しの行にだけ「【折りたたみ】」の印を付けていた。閉じの印が無く、中身と本文の境界は空行だけだった。

このため、**折りたたみを開かない読者の経路が入力に存在しなかった**。本文からアコーディオンへ退避しただけの説明が「読者に届いている」ものとして判定され、「退避しても読者に示す情報量は減っていない」という執筆側の主張を、読者の条件で検証できない状態だった。

### 決めたこと

| 決めたこと | 内容 |
|---|---|
| 読者役の立場 | **開かない読者**とする。記事は折りたたみを開かなくても成立していなければならないため、落とす側の立場と一致させる |
| 中身(`content`) | 読者提示テキストから**除外する** |
| 見出し(`summary`) | **`【折りたたみ:見出し文】` の形で残す。** 折りたたまれた内容がそこにあること自体は、読者にも見えるため |
| 除外した分量の記録 | 規則の全文・件数・除外した字数(空白を除く)・除外した全文を `collapsedExclusion` にまとめ、**第2〜5層の結果**(`readerViewCollapsedExclusion`)と**判定ログ**(`readerViewCollapsedExclusionAtJudgment`)の両方に自己完結の形で残す。判定の入力から外しただけで、記事からは失われていないことを、記録だけで追えるようにする |
| 確認の手段 | `node scripts/autonomy/reader-view.js <記事> --exclusion` で、除外した中身の記録だけを出せる |

**この変更で判定条件は緩めていない。** 読者が見られないものを「見た」ことにしていた入力条件を、実態に合わせただけである。第2層の約束の回収(引用が本文にあるかの機械照合)も、この読者提示テキストに対して行うため、**折りたたみの中身からの引用は「本文に無い」と扱われる**ようになる。

## 26. 読者提示テキストに、図表のどのキーを入れるか

### 原則

**読者が画面で見るものは入力に入れる。見ないものは入れない。**

判断の根拠は記事データではなく、**サイト側の描画実装**(`lib/posts.js`・`lib/*Widgets.js`)である。「そのキーの値が `escapeHtmlText` を通って画面のテキストになるか」で決める。

### 直した理由

`stat` 型の図表(大きな数字で見せるタイル)の `value` が `NON_TEXT_KEYS` に入っていたため、**数値そのものが読者提示テキストから落ちていた**。

```
記事データ:  type: "stat" / value: "<数値>" / unit: "<単位>" / label: "<ラベル>"
読者提示(旧): <単位>
             <ラベル>
読者提示(新): <数値><単位> <ラベル>
```

### 突き合わせ

図表の型の全部の値について、読者提示テキストに現れるかを1件ずつ突き合わせる。

| 直した点 | 内容 |
|---|---|
| `value` を入れるようにした | `NON_TEXT_KEYS` から外し、`stat` 型は `value + unit + label` を1行に組み立てる |
| `tradeoffCurve` の横軸を入れるようにした | `points[].temp` は画面に目盛りのテキストとして出る(縦の値 `hold`・`damage` は折れ線の高さになるだけで、テキストとしては出ない) |
| `key`・`resolution`・`tool` を入れないようにした | いずれも内部の識別子で、読者が見るのは対になる日本語のラベルの方。**読者が見ないものが入力に入っていた**ため取り除いた |

入れないままにしたものと、その根拠:

| キー | 型 | 根拠 |
|---|---|---|
| `depth` / `from` / `to` | depthComparison | `depthToY()` で描画位置に変換されるだけ。読者が見るのは `label` |
| `cx` / `cy` / `rx` / `ry` / `strokeWidth` | crossSection | SVG の座標・線幅 |
| `sebum` | calendarBand | 帯の色を決めるだけ(数値の大小で帯の色が変わる)。数値は画面に出ない |
| `hold` / `damage` | tradeoffCurve | 折れ線の高さ。テキストとしては点の `<title>`(ホバー)にしか出ない |
| `maxScore` | diagnosis | 判定の内部の閾値 |
| `motif` | processContrast | イラストのモチーフ名 |

### 歯止め

テストで、**pool の全記事の全図表について、読者が見る値が1件も落ちていないこと**を確かめる。落としてよいキーは根拠つきで列挙する。新しい型・新しいキーが増えたときに、読者が見る値を黙って落とさないためである。

## 27. 引用から記事の位置への逆引き

### 直した理由

第3層の差し戻し文は否定を「**本文の次の箇所**が…」と書くが、否定の引用元は本文だけとは限らない。引用元は次のように分かれる。

| 分類 | 件数 |
|---|---|
| 本文にそのままある |  |
| frontmatter の表示テキスト(図表の注記・チェックリストの項目・要点) |  |
| 本文にあるが、装飾記法(`==`)を外さないと一致しない |  |
| **記事のどこにも無い**(読者提示テキストの組み立て結果 `【折りたたみ:…】`) |  |

原因は2つある。**第3層の指示文が「根拠は必ず本文から引用して示すこと」と書きながら、渡している入力は読者提示テキストだったこと**と、**読者提示テキストから記事の位置への逆引きが無かったこと**である。執筆側は、本文から探せない引用の直し場所が分からない。

### 決めたこと

| 決めたこと | 内容 |
|---|---|
| 位置の対応表 | `reader-view.js` が、読者提示テキストの各行が記事のどこから来たかを持つ(`lines[].origin`)。本文は**記事ファイルの行番号**、frontmatter は**キーのパス**(`charts[3].note`・`summaryPoints[0]`)、折りたたみの見出しは**アコーディオンの番号と「中身は読者に見えない」こと**、組み立てた見出し行は**合成**と記録する |
| 逆引き | `makeLocator(detailed)` が引用から位置を探す。照合は装飾記法(`==` `^^` `++` 等)を外し、空白・句読点・括弧を無視して行う(機械照合と同じ正規化)。1行に収まる一致を優先し、収まらない場合だけ行をまたぐ範囲として示す |
| 差し戻し文 | 第3層・第2層の指摘に `位置: 本文 行107` `位置: frontmatter charts[2].note` のように位置を書く |
| 位置を出せない引用 | **差し戻し文に入れない。** 執筆側が直す場所を示せないため。判定ログに `unlocatableClaims`(位置不明)として、規則の全文つきで記録する |
| 指示文 | 第3層の「本文から引用」を「**読者提示テキスト**(読者が画面で実際に読めるテキスト)から引用」に直した。入力と言い方を一致させる |
| 言い回し | 「読者の役に立たない根拠として成立している」(意味が逆に読める)を「**読者が読める材料だけでは、次の箇所は読者の役に立つ根拠として成立していない**」に直した |

**読者提示テキストの中身は変えていない。** 記事の全件で、この変更の前後の出力が1文字も違わないことを確かめる(判定の入力条件は動かしていない)。

## 31. 工程が完了しなかったときは、作業ツリーに成果物を残さない

### 直した理由

工程が時間上限で強制終了されて実行が「異常」で終わったとき、記事ファイルが**完全に書き換わった状態**で残ることがある。`run-steps.js` が `res.ok` が false のときに作業ツリーの状態を確かめずに異常を返すと、「工程は完了していない」と記録されながら、判定を1つも経ていない記事だけが作業ツリーに残る。

| どこで行うか | **`run-local.js`(親)で行う。** 工程は子プロセスごと強制終了されるため、子(`run-steps.js`)に後始末をさせられない |
| 対象 | 記事を作る工程(`plan` / `write` / `revisePrepare` / `fix`)が書き換えうる4ファイル(企画書・記事・生成メタ情報・収集データ) |
| 複製 | 工程の開始前に内容と SHA-256 を控える。**「無かった」ことも控える**(工程が新しく作ったファイルは、失敗したら消す必要があるため) |
| 失敗したとき | 書きかけの成果物を `runs/<実行ID>/attempts/<停止点>_<工程>__<日時>/` へ**退避してから**、開始前の内容に戻す。捨てない |
| 確認 | 復元後の SHA-256 が開始前と一致することを確かめ、停止点の報告と停止記録の両方に書く |
| 自己完結 | 退避先に `退避の記録.json` を置く。規則の全文・実行ID・停止点・工程・異常の全文・各ファイルの SHA-256(開始前/工程の後/復元後)を含む |

## 32. 停止記録の条件文を、停止の理由ごとに書き分ける

### 直した理由

`writeHaltRecord` が、停止の理由にかかわらず `limits.onLimitReached.conditionText`(「差し戻し回数が5回に達する、または処理時間が60分に達した場合」)を書くと、CLI のタイムアウトのようにこの条件とは無関係な停止でも同じ条件文が書かれる。**記録だけを見た人が、起きていないことを起きたと読む状態**になる。

### 決めたこと

停止の理由の種類を6つに分け、`current-rules.json` の `limits.haltConditions` に種類ごとの条件文・理由・禁止事項を置く。
`writeHaltRecord` は `reasonKind` を受け取り、その種類の条件文を書く。種類が渡されなければ、上限の条件文を書かずに「種類が指定されていない」と書く。

| 種類 | いつ |
|---|---|
| 差し戻し回数の上限 | 第6層で差し戻し回数が上限に達した |
| 処理時間の上限 | 第6層で処理時間が上限に達した / 工程の開始前に上限に達していた(§33) |
| 工程の時間上限 | 工程が時間上限で強制終了された |
| CLIの失敗 | claude の呼び出しが失敗した、または成果物が作られなかった |
| 出典の不一致 | 収集データに無い出典が frontmatter に足された(§34) |
| 依頼者の中止 | `abort` で実行を終えた |

**依頼者の中止だけは停止記録のファイルを置かない。** 停止記録が残っていると次の記事の生成が止まる作りのため、
判定条件の異常ではない `abort` で止めてしまうのは筋が通らない。条件文は実行の記録(`state`)に残す。

## 33. 処理時間の上限の定義を1箇所にし、工程の開始前にも評価する

### 直した理由

上限が2箇所にあると食い違う(停止条件 `current-rules.json` の `maxMinutesPerArticle` は**60分**、工程の実行側 `run-local.js` の `TOTAL_BUDGET_MS` は**90分**)。停止条件の評価が判定の直後(第6層)だけだと、上限に近い時点で始めた修正の工程がさらに動き、上限を超えた記事に、さらに工程を実行することになる。

### 決めたこと

- **定義は `maxMinutesPerArticle` ただ1つ。** 実行全体の上限も工程ごとの上限も、そこから導出する
  - 実行全体 = `maxMinutesPerArticle × 1.5`(記事の処理時間に数えない工程〔self-test・regression・retention・aggregate・report〕の分)
  - 工程ごと = `maxMinutesPerArticle ÷ 除数`(÷2.4=25分 記事を作る工程 / ÷3=20分 第4層 / ÷4=15分 第2・3・5層 / ÷6=10分 aggregate / ÷12=5分 機械判定・裁定・配置など / ÷2=30分 regression)
  - 導出の式は `limits.derivedCaps.conditionText` に全文で書く。**コードに上限の数値を書かない**
- **記事の処理時間に数える工程は、開始前にも停止条件を評価する。** 達していれば工程を開始せず、停止記録を置いて実行を終える
- **上限の値そのものは変えない**(60分・修正工程25分のまま)。上限に当たること自体を、値を緩めて避けない

## 34. 差し戻し対応で足した出典を、収集データと照合する

### 直した理由

差し戻しの指摘(「法律名や条文番号が一切示されていない」など)に応じて執筆側が**収集データに無い一次資料**(行政の通知など)を自分で取りに行き、frontmatter の `sources` にだけ足すと、第4層(事実性)は**収集データの原文**と突き合わせて判定するため、正しい資料であっても「原文で裏付けられない断定」として落ちる。

### 決めたこと

| 決めたこと | 内容 |
|---|---|
| 規則 | 差し戻し後の修正で出典を新しく足す場合も、(1)WebFetch で本文を取得して確かめ、(2)原文の引用を収集データに記録し、(3)そのうえで frontmatter に書く |
| 照合 | 修正の工程の完了時に、**開始前の記事と修正後の記事の `sources` を比べ、新しく足された URL** が収集データに現れるかを機械で照合する。1つでも現れなければ工程を異常で止める |
| 対象外 | 修正の開始前から frontmatter にあった出典。既存記事の修正版では、元の記事に未記録の出典が残っていることがあり、この工程では直しようがない(記録だけ残す) |
| 解消できない場合 | 出典を取得できず指摘を解消できないときは、**断定を弱める・範囲を限定する形で書き直す**。未解消のまま出さない。断定を強める方向では解消しない |

## 35. 指示文同士の矛盾を解き、④を機械で検出する

### 診断

差し戻し文の冒頭「**指摘のない箇所は変更しないこと**」は、`writer.md` の是正(まとめ固定の解除・反復の抑制・コールアウトに言い換えを入れない)を打ち消す。④(まとめが `summaryPoints` の複製)と⑥(同じ注意点の反復)が解消しないのはこのためである。**執筆側は指示どおりに動いており、指示同士が矛盾していた。**

### 決めたこと

- 差し戻し文の冒頭を「指摘のない箇所は、`writer.md` に書かれた規則(この定義の全体)を満たすために必要な変更を除き、変更しないこと。**規則に反している箇所は、指摘が無くても直すこと(任意ではない)**。規則を満たすために行った変更は、生成メタ情報に『規則対応』という見出しを作り、指摘への対応の一覧とは**別の一覧**として列挙すること」に改めた
- ④は機械で検出できるため、**第1層に項目38 を足した**
- ⑥は今回ルールを作らない。矛盾の解消で差し戻し時にも規則が効くようになるため、次の判定で再度実測する

### 項目38(本文の箇条書きと summaryPoints のほぼ同文)

| 決めたこと | 内容 |
|---|---|
| 対象 | 本文の**すべての**箇条書き(まとめに限らない)と、frontmatter の `summaryPoints` の各項目 |
| 判定 | 文字bigramのDice係数が **0.80以上**の組が1つでもあれば違反(ブロッキング) |
| 正規化 | 装飾記法(`==` `^^` `++` `%%`)・リンク記法・空白・句読点・括弧を落とす。正規化後10文字未満の箇条書きは対象外 |
| 閾値の根拠 | ほぼ同文(語尾と語順だけが違う)・一部重複(同じ話題に情報が足されている)・別内容のそれぞれが取る Dice 係数の帯を比べ、0.80 はほぼ同文だけを検出し、一部重複(まとめが本文の要点をもう一度示す通常の書き方)を違反にしない値とした |

## 36. 判定を経ていない修正版を、新しい実行で判定にかける

### 直した理由

異常終了などで、**判定を経ていない修正版だけが作業フォルダに残る**ことがある。この記事を判定にかける入口が必要である。

- `start`(新規)は企画から作り直すため、この記事は捨てられる
- `start --revise` は**記事データの3フォルダ(公開済み・公開待ち)の直下**しか受け付けない。この記事はまだ公開されておらず、置き換える元の記事も無い
- `next` / `retry` は、終了した実行には使えない

### 決めたこと: `start --continue <作業フォルダの article.md>`

| 決めたこと | 内容 |
|---|---|
| 対象 | 記事の作業フォルダ(`記事データ/作成中/<記事フォルダ>/`)の**直下**にある `article.md` だけ。生成メタ情報と収集データが揃っていなければ受け付けない(第4層の入力のため) |
| 工程 | self-test → **引き継ぎ(`continuePrepare`)** → 第1層。**企画・執筆は行わない。claude を呼ばない**(ファイルの複製と記録だけ) |
| 記録 | 旧実行の実行ID・複製した時点の SHA-256・引き継ぐ理由を、停止点の報告と実行の記録に**自己完結の形で**残す |
| 書き換えの検出 | 起動時に控えた SHA-256 と、引き継ぐ時点の SHA-256 が違えば引き継がない(書き換え後の内容は判定を経ていないため) |
| 時間・回数 | 新しい実行のものとして**0から数える** |
| 終わり方 | 判定を通過したら**新規記事と同じ経路**(公開待ちへの配置)。置き換える元の記事が無いため |
| やらないこと | 判定を経ていない記事を記事データのフォルダへ置いてから `--revise` で拾う経路は作らない(**公開ゲートの外にあるべき記事を、ゲートの内側のフォルダへ持ち込むことになる**) |

### あわせて: 停止記録を「対処済み」にする入口

停止記録が残っている間は、self-test の次が `regression` になり**記事の生成が行われない**(設計どおり)。
停止記録が残っているままだと、新しい実行を始めても記事が飛ばされる。

`resolve-halt --record <停止記録のパス> --reason "<停止の原因に何をしたか>"` を設けた。

- **削除しない。** `halts/対処済み/` へ移し、同じ場所に `__対処の記録.json`(規則の全文・元の停止の理由と種類・対処の内容・移動前の SHA-256)を置く
- 停止が起きた事実は記録として残り、`listHaltRecords`(直下の `.json` だけを見る)からは外れる
- **対処の内容(`--reason`)が無ければ受け付けない。** 対処しないまま記録だけ消して先へ進む経路を作らないため

## 38. 「この記事で分かること」(summaryPoints)を、読者が得るものに揃える

### 直した理由

記事の冒頭の固定枠「この記事で分かること」に、読者と無関係な法令上の分類や行政機関の注意喚起の回数などが並ぶことがある。**読者が本文より先に見る枠に、読者と無関係な統計・制度の説明が並ぶ**という、本改修の出発点だった症状が、この枠の中で再発する。

### 診断

| 見たもの | 分かったこと |
|---|---|

**第3層の否定は「その記述が正確か・根拠として成立しているか」の観点**であり、
「読者が得るものになっているか」の観点では、**どの層も見ていなかった**(第1層の項目38 は「まとめとの重複」だけを見る)。
上流は「定義が誤っている」のではなく「**定義が存在しない**」状態で、既存記事の模倣で内容が決まっていた。

### 決めたこと(上流: writer.md に定義を新設)

| 決めたこと | 内容 |
|---|---|
| 何を書くか | 「読者がこの記事を読み終えたときに、**判断できること・できるようになること**」。記事の要約ではなく、読者が手にするものを読者の側から書く |
| 禁止 | **事実の提示だけで終わる項目**。統計・件数・年・機関名・法令名・商品や制度の分類などの事実は根拠であり、読者が得るものではない。**事実を書くこと自体は禁じない**が、その事実を読者が何に使えるのかを同じ項目の中に書く(2026-09-18 に取り消し。現行は writer.md 規則5: 統計・件数・年・機関名・法令名・括弧書きの補足を書かず、読者が何を見分けられる・判断できるようになるのかだけを書く) |
| 形 | frontmatter の `targetReader` が抱く疑問に対する**答えの形**。文の主語として「あなた」を明示する必要はない |
| 除外 | 「〜を知る」「〜を理解する」で終わる項目(何を判断できるようになるのかが分からない) |
| 根拠 | 同じ項目に添えてよい。**答えを先に書き、根拠は括弧等で後ろ**に置く(2026-09-18 に取り消し。現行は writer.md 規則5: 統計・件数・年・機関名・法令名・括弧書きの補足を書かず、根拠は本文と記事末の「出典」欄で示す) |
| 本文との関係 | 本文での根拠の置き方(主張の直後)は**別の規則**。この規則は summaryPoints に根拠を書くことを禁じない(2026-09-18 に取り消し。現行は writer.md 規則5: summaryPoints には根拠を書かない) |

### 決めたこと(判定: 第2層にタスクを1つ足す)

| 決めたこと | 内容 |
|---|---|
| 定義の場所 | `current-rules.json` の `layer2.preReadTask`(key = `summaryValue`) |
| 入力 | 記事のタイトル / `targetReader` / `summaryPoints` の項目**だけ**。**記事本文は渡さない** |
| 入力をこうする理由 | 読者はこの枠を本文より先に見る。本文を渡すと、本文から補って「得られるもの」を述べられてしまい、枠だけを見た読者の条件にならない |
| 実行 | 第2層の中で**別の呼び出し**にする(既存の5タスクは記事全体を渡す従来どおりの呼び出し) |
| 不合格 | (1)読者役が得られるものを述べられない(**機械で判定**) (2)項目が事実の提示だけで終わる (3)述べた内容がタイトルの疑問とも targetReader の疑問とも対応しない |
| 判定しないこと | 答えと根拠の**順序・文体**(執筆側の規則)、項目と**本文の整合**(第3層と第1層の項目38が見る) |
| 位置 | 不合格の項目の番号を合否判定側に返させ、**項目の数の範囲内の番号だけ**を `frontmatter summaryPoints[番号]` にする(範囲外は捨てる)。差し戻し文には「位置:」として出る |
| 実行しない場合 | `summaryPoints` が無い記事、呼び出し元から入力が渡らなかった場合。**黙って通さず、実行しなかったことと理由を結果に残す** |
| 呼び出しの失敗 | 判定を通過させず、第2層全体を異常にする |

### ルールを足した理由(症状の数だけルールを作らない原則との関係)

**診断で「どの層も見ていない」ことを確認した症状**であり、かつ**本改修の出発点の症状そのもの**であるため足した。
第3層が同じ箇所を別の観点で指摘しうるが、観点が異なる(正確性 ≠ 読者が得るもの)ため重複しないと判断した。

## 39. プレビューに、その記事の状態を出す

### 直した理由

プレビューの画面だけでは、**判定を経ていない新規記事を「既存記事を修正したもの」と誤認しうる**。
描画は本番と同じであるため、画面だけでは「これが何か」(新規か修正版か・判定を通過しているか・どの停止点のものか)が分からない。

### 決めたこと

| 決めたこと | 内容 |
|---|---|
| 出す場所 | 記事ページの冒頭(サムネイルの直前)。**作業場所のコピーにだけ**差し込む |
| 触らないもの | サイト本体の `pages/`・`components/`。本番の描画には影響しない |
| 出す内容 | 記事の場所 / 実行ID(進行中か終わった記録か) / 種類(新規・既存記事の修正版・引き継ぎ) / 判定の状態 / 停止点 / サムネイル未設定 / 「見えても公開・判定通過ではない」 |
| **判定の状態の出し方** | 記録にある判定は「判定を始めた時点の記事」に対するもの。いまのファイルの SHA-256 がそれと違えば、**「いま表示している内容は、判定を1つも経ていない」**と出す |
| 差し込めない場合 | 記事ページの目印が見つからなければ、**黙って飛ばさず**に理由を記録に残し、プレビューの表示自体は続ける |

## 40. 公開日の扱い(確認のみ)

frontmatter の `date` は「公開日」として表示されるため、公開時に実際の公開日へ書き換えているかを確認する。

| 工程 | `date` の扱い |
|---|---|
| `npm run queue`(公開予定の割り当て) | **公開予定日に書き換える**。ファイル名の日付プレフィックスも変える |
| `queue-release.js`(実際の公開) | **実際に公開した日に書き換える**。ファイル名の日付プレフィックスも変える |
| `publish-queue.yml` | 全ステップに `TZ: Asia/Tokyo` があり、UTC ずれも起きない |

公開済み記事のファイル名の日付と `date` は一致する。**判断事項に積む必要はない**。
判定に日数がかかった記事が古い日付で公開されることはない。

## 37. 設計期のローカルプレビュー(公開はしない)

### 直した理由

停止点での目視が、記事の Markdown の生データしか見られないと、
**読者が実際に見る画面**(折りたたみが閉じた状態・図表の描画・装飾の分布)を確かめられない。
一方で、確認のために記事を公開経路(`content/articles`・記事データ)へ置くと、判定を経ていない記事がサイトのビルドに取り込まれうる。

### 決めたこと

| 決めたこと | 内容 |
|---|---|
| 入口 | `run-local.js preview [--article <記事のパス>]... [--port <番号>]` / `preview --stop` |
| 対象 | `--article`(複数可)。指定が無ければ進行中の実行の記事 |
| 作業場所 | **リポジトリの外**(`%TEMP%/nevora-preview/workspace`)。中に作ろうとしたら例外で止める |
| 描画 | 本番と同じコンポーネント。`pages`・`components`・`lib`・`styles` を**複製**し、`public`・`node_modules` は**リンク** |
| 記事の置き場所 | 作業場所の `content/articles` を実体とし、**対象の記事だけ**を置く |
| 公開の経路 | **一切書き込まない**(サイト本体の `content/articles`・記事データの3フォルダ・公開ゲートの台帳・公開キュー) |
| 停止点の報告 | 記事のある工程の報告に、プレビューの URL(動いていれば)または開き方を書く |

**プレビューは公開ではない。** プレビューで見えることは、判定を通過したことにも、公開されたことにもならない。
規則の全文は `current-rules.json` の `limits.preview`。

### なぜ複製とリンクを使い分けるか

描画に使うコードをリンク(junction)にすると next のローダーが当たらない。

- Turbopack(`next dev` の既定): `Symlink [project]/pages is invalid, it points out of the filesystem root` で**起動そのものを拒否する**
- webpack: 作業場所の外の実体パスに解決するためローダーの対象から外れ、`Module parse failed: Unexpected token (22:4)` で JSX を変換できない

このため描画に使うコードは複製し、`next dev` は `--webpack` で起動する。
画像と `node_modules` はローダーが処理しないためリンクのままにする。

## 41. 第4層に、出典の権威性の照合を足す

### 直した理由

第4層の事実性照合が、法的評価の断定(例: 「あるサービスが**法令上の業務規制には当たりません**」)を、民間の解説記事(`type: "secondary"`)**1件だけ**の裏付けで**合格**にしてしまうことがある。収集データの解釈メモが「この通知は、その業態の営業そのものが違法かどうかについては何も述べていない」「その部分を書く場合は、出典の整理にとどめ、この通知を根拠として示さないこと」と記録していても、断定が通る。

事実性の照合が「**原文と一致するか**」だけを見ると、一致はしているが**裏付けの資格がない出典**を通してしまう。
法的評価・税務上の評価・リスクの評価は、解説記事が正しく整理していても、それ自体は法令・行政の判断ではないため、読者に対する断定の根拠にならない。

### 決めたこと

| 決めたこと | 内容 |
|---|---|
| 定義の場所 | `current-rules.json` の `layer4.authorityCheck`。不合格条件は `layer4.tasks[factual].failConditionText` に足した |
| 裏付けありとする条件 | 法令・税法・約款の解釈、制度・業規制への該当、利益・損失・リスク・税負担の評価の断定は、**`type` が `primary` の出典**(法令・行政の通知・公的機関の発表・査読論文等)の原文で裏付けられている場合だけ |
| 不合格 | `secondary` の出典だけで裏付けられた断定、どの出典でも裏付けられない断定。該当箇所と**その出典の `type`** を判定ログに残す |
| 対象外 | 法令・税法・約款の解釈、制度・業規制への該当、利益・損失・リスク・税負担の評価に関係しない断定(業態の説明・手順の説明・読者への呼びかけ)。`type` を問わない |
| 原文が当てはめを述べていない場合 | 裏付けられているとは扱わない(一般的な基準だけを述べ、この記事の対象への当てはめを述べていない原文を含む) |

### 断定の候補を機械で出し、意味の判定は第4層に渡す

断定かどうかは**文末の形**で機械的に決まるが、それが法的評価・税務上の評価・リスクの評価かどうかは**文の意味**を読まないと決まらない。
機械は候補を出すところまでを担い、意味の判定は第4層の判定プロセス(AI)が行う。抽出の規則は `layer4.authorityCheck.candidateExtraction`。

1. 本文の行のうち、見出し行・表の行・画像の行・HTMLコメントを除く(引用ブロックと箇条書きは含める)
2. 装飾記法(`== ++ ~~ ^^ %%`)とリンク記法を外し、「。」で文に分ける
3. 文末が断定の形(`assertionEndings`: です。/ ます。/ ません。/ である。/ に当たります。 ほか13種)で終わる文を採る
4. 限定・推量の標識(`hedgeMarkers`: 可能性 / 場合があ / ことが多 / がち / とされて / 一般に ほか25種)を含む文は候補から外す

**4 で外すのは、限定表現が「根拠の範囲に留めた記述」であり、この照合が問題にしている『根拠を超えた断定』ではないため**である(第3層の立場〔§42〕と同じ考え方)。
行番号は **frontmatter の行数を足した記事ファイルの行番号**で示す(執筆側が探せるようにするため)。

### 出典の `type` をどこから採るか

収集データ(`sources.md`)には「`- type: primary(公的機関)`」の形で、frontmatter には `sources[].type` として、
**同じ出典の種別が両方に記録される**。二重にあるため、どちらを使うかを決めておかないと、片方だけを直したときに判定が変わる。

- **収集データの記録を先に使う**(そこが原文と一緒に記録されている場所であり、第4層が照合に使う入力そのもののため)
- 収集データに記録が無ければ frontmatter の `sources[].type` を使う
- どちらにも無い出典は `primary` として扱わない(裏付けの資格を確かめられないため)

### 機械の安全網

判定プロセスが**裏付け不足の断定を挙げながら `failed` を `false` にした**出力は、機械で不合格に直す
(`authorityOverride` に理由を残す)。不合格条件がそう定めている以上、判定プロセスの申告だけに委ねない。

## 42. 第3層の立場を明示し、規則との衝突を第6層で外す

### 直した理由

第3層の指示文が「落とす側に立て」とだけ書き、**何を欠陥とみなすかの方向**を書かないと、2つの症状が出る。

| 症状 | 内容 |
|---|---|
| **「もっと言い切れ」方向の否定** | 限定表現(「〇〇になる**可能性がある**」「**目安になり**」「**場合があります**」「**ことが多く**…**なりがち**です」)への否定。法的評価の断定は、言い切ると虚偽のリスクに直結する |
| **執筆規則が求める注記への否定** | 図表の注記「実測した〇〇の度合いを示すものではありません」を「図表を自ら無効化している」として否定する。この注記は writer.md の「根拠を示せない座標には『測定値・採点ではありません』と明記する」規定に従って書かれたもの |

**虚偽・誤情報を最優先で落とすという v5 の方向と、この層の動きが逆を向く。**
注記への否定を差し戻し文に渡すと、執筆側は **writer.md の規則と差し戻し文のどちらかに必ず違反する**状態になる。

### 決めたこと(指示文: 否定の対象と対象外を書く)

| 区分 | 内容 |
|---|---|
| **否定の対象** | (1)根拠を超えた断定(出典が示す範囲より強く言い切っている) (2)根拠が無い主張 (3)読者が実行できない指示・回収されない約束 (4)論理の飛躍・矛盾 |
| **否定の対象外** | (1)根拠の範囲に留めるための限定表現(「〜の場合」「〜ことがあります」「一般に」)。**曖昧であること自体は欠陥ではない**。限定が根拠と対応していれば正しい記述である (2)writer.md が求める注記(図表が測定値でないことの明示・効果を保証しない旨・参考情報の明示) |
| **方向の禁止** | 「もっと言い切るべきだ」という方向の否定を出さない。言い切りが必要だと考える場合は「**根拠を提示すれば言い切れる。現状の根拠では言い切れない**」という形で、根拠の不足として書く |

定義の場所は `current-rules.json` の `layer3.scope`(指示文本体 `layer3.instructionText` にも同じ内容を書いた)。

### 決めたこと(第6層: 規則との衝突を機械で外す)

指示文を直すだけでは**実行ごとのばらつきが残る**ため、裁定の層に機械の照合を1つ置く(`layer6.ruleConflictExclusion`)。

| 決めたこと | 内容 |
|---|---|
| 除外の条件 | 次の**2つをともに満たす**否定だけを外す。(1)引用が `noticePatterns`(「測定値・採点ではありません」「効果を保証するものではありません」等9種)のいずれかを含む (2)引用の位置が**注記**である(`frontmatter charts[].note` / `accordions[].note` / 本文の `%%` 注記) |
| 2つを要る理由 | 位置だけで外すと**注記の中身そのものへの指摘**まで消える。定型文だけで外すと**同じ言い回しが本文の主張として使われている場合**まで外してしまう |
| 一覧は閉じている | `noticePatterns` に無い言い回しの注記は**除外されない**。第3層の指示文が否定を禁じている範囲(執筆規則が求める注記の全体)の方が広いことを承知のうえで、機械の照合は**誤って除外しないこと**を優先する。一覧に無い注記への否定が差し戻し文に残った場合は、その否定を渡したまま**依頼者に報告する**(機械が一覧を自分で広げない) |
| 除外したもの | 差し戻し文に渡さない。判定ログに「**規則との衝突として除外**」として、引用・理由・定型文・規則の全文を残す |
| 否定が0件になったら | **第3層の判定を通過に改める**(差し戻しの理由が残っていないため。差し戻し文が空になる状態を作らない) |
| 禁止 | 除外した否定を「解消済み」として扱わないこと(記事は何も変わっていない)。除外の記録を判定ログから省かないこと |

本文の `%%` 注記は、読者提示テキストでは `%%` が外れるため**引用の文字列からは注記かどうかが分からない**。
そのため逆引き(`reader-view.js`)の側で、その行が `%%` を含むかを位置の情報(`noticeMarkup`)として持たせた。

## 43. 項目11 の解消手段を、差し戻し文と執筆規則に書く

### 直した理由

項目11「出典紐付けのない伝聞表現」は、**伝聞に出典が無いことを禁じている**のであって、伝聞を禁じていない。
出典を紐付けずに**語尾を言い切りに変えて**解消すると(「と説明されています」→「当たりません」/「とされていますが」→「増加しています」/「と言われても」→「と告げられても」)、出所が示されないまま断定だけが強くなる。**§41 が拾う法的断定は、この対応で生まれうる。**

### 決めたこと

| 場所 | 内容 |
|---|---|
| `verify-article.js` の項目11 の `note` | 判定条件の全文に**解消手段を3つ**書く(下記) |
| `judge.js` の第1層 | 項目が `note` を持つ場合、`itemNoteFullText` として差し戻し文まで渡す |
| `cycle.js` の `reworkInstructionFrom` | 「この指摘の解消手段: 」として差し戻し文に出す |
| `.claude/agents/writer.md` | 「差し戻しへの対応時の原則」に、同じ3つの手段と、B5ルールとの関係を足した |

### 解消手段(3つ)

| # | 手段 | 注意 |
|---|---|---|
| 1 | **出典を紐付ける** | その伝聞表現と**同じ文の中**に、丸括弧の出典表記または Markdown リンクを置く(機械の照合が同じ文の中を見るため。別の文に置いた `%%` 注記は数えられない)。**出典を紐付けたうえで言い切る形にしてよい**(2026-09-14 以降は `%%出典:…%%` だけが紐付け。writer.md 規則32 の差し戻し節が正) |
| 2 | **誰が述べたことなのかを本文に書いて、主張の範囲を限定する** | 述べた主体を**文の主語として書く**(「〇〇は…と説明しています」)。このとき**伝聞の語尾をそのまま残すと、項目11 は解消しない**(機械の照合は語尾のパターンで検出するため)(2026-09-18 以降は主体を文に書かない。writer.md 規則32 の差し戻し節が正) |
| 3 | **その記述を削る** | 出典を紐付けられず、誰が述べたことなのかも書けない場合 |

**語尾だけを言い切りに変える対処では解消しない**(出所が示されていない点は変わらず、断定だけが強くなる)。

### B5ルールとの関係

既存の **B5ルール「出典で裏付けられた内容は、伝聞にせず言い切ること」** と、新しい「言い切りへの言い換えはしない」は、
そのままでは正面から衝突する。writer.md に次を明記して優先順位を決めた。

- B5ルールが禁じているのは、**誰の発言か分からないまま主張を弱める伝聞**である
- **出典を紐付けたうえで言い切る**(手段1)か、**誰が述べたことなのかを書く**(手段2)なら、どちらもB5ルールを満たす
- **出典を紐付けないまま語尾だけを言い切りに変えるのは、B5ルールが求めているものではない**
- `type: "secondary"` の出典しか無い法的評価・税務上の評価・リスクの評価は**言い切らない**(手段2 にする)。**伝聞・限定の形で誰が述べたことなのかを示した記述は、§41 の照合の対象にならない**(断定ではないため)

**解消手段を項目の定義の側に置いた理由**: 差し戻し文の組み立て側にだけ書くと、項目が増えるたびに組み立て側に分岐が増える。
項目の `note` に書けば、解消手段を持つ項目はすべて同じ経路で差し戻し文に届く。

## 44. 引き継いだ生成メタ情報を、記事の実態に合わせる

### 直した理由

第4層 `declared` が、`meta.md` の記述(例:「3-1・4-1 は(H3・**アコーディオン**)」「項目23対応として**アコーディオンに退避させて全文を残した**」)と、**記事に `accordions` が0件**であることの食い違いを検出することがある。`meta.md` は引き継ぐ前の実行の時点の記述で、修正で記事からアコーディオンが消えたあとも更新されない。`continuePrepare` は `meta.md` を**そのまま複製する**仕様のため、古い記述が新しい実行に持ち込まれる。

**宣言と実体の食い違いは記事の欠陥ではなく引き継ぎの副作用**であり、これを差し戻しとして執筆側に回すと、
記事を直す必要がないのに修正の工程が1巡分消費される。

### 決めたこと

| 決めたこと | 内容 |
|---|---|
| 工程 | `metaSync`(工程の名前「生成メタ情報の一致」)。**`continuePrepare` の次**に1つ実行し、そのあと第1層へ進む |
| 呼び出し | claude 1回(writer)。時間上限は**5分**(単一定義 `maxMinutesPerArticle` ÷ 12 から導出)。**記事の処理時間に数える** |
| 更新する対象 | `meta.md` だけ。記事が述べられている事実(見出しの構成・視覚要素の種類と位置・約束の回収位置・判定への対応として行った変更の記述) |
| 更新しない対象 | 構成の選定理由・企画意図そのもの(記事の内容と食い違っていない限り) |
| 記事の保護 | 工程の前後で記事の SHA-256 を照合し、**変わっていれば異常として止め、停止記録を置く**。成果物の復元(§31)の対象工程にも入れた |
| 記録 | `meta.md` の末尾に「## 記事との一致(metaSync)」を作り、実行日・書き直した箇所を一覧で残す。食い違いが無ければ「食い違いなし」と書く |
| 禁止 | `meta.md` の記述に合わせて**記事を書き換える**経路を作らないこと(記事は判定の対象であり、引き継いだ内容のまま判定にかける) |


## 45. 主体を明示した記述を、第4層と項目11 の両方で正しく扱う

### 直した理由(設計側の矛盾)

`writer.md` に「`type: "secondary"` の出典しか無い法的評価・税務上の評価・リスクの評価は、**誰が述べたかを主体として書く**」と定めた。
規則どおりに書くと、**規則に従うと落ち、落ちないように直すと別の規則で落ちる**状態になりうる。

| 書き方 | 項目11(第1層) | 第4層 factual |
|---|---|---|
| 受動形「〜と説明されています」 | **発火する** | 候補から外れる |
| 能動形「〜と説明しています」 | 発火しない | **断定の文末として候補に残り、secondary のみとして不合格** |

### 決めたこと(第4層: 主体明示の3条件。2026-09-13 改訂)

法的評価・税務上の評価・リスクの評価であっても、次の**3つをすべて満たす**記述は、出典の `type` を問わず「裏付けあり」として扱う
(`layer4.authorityCheck.subjectAttribution`)。

1. 述べた主体が**同じ文の中に明示**され、その主体が**収集データに出典として記録**されている
2. **同じ文に出典が紐付いている**(`%%出典:…%%`・丸括弧の出典表記・Markdown リンク)。
   前の文を受ける参照(「同じ解説は」等)の文は、その文自体に出典が紐付いていなくても、**参照される側の文に紐付いた出典で主体を特定できればよい**。参照される側の文は、同じ段落の中で参照する文より前にある、主体を明示して出典が紐付いた文に限る(2026-09-13 に明記。「その文」が参照する側か参照される側かで読みが分かれるため)
3. **本文の述語の強さが、収集データにあるその主体の原文を超えていない**。
   原文が「可能性がある」「おそれがある」「〜とされる」のような限定なら本文も限定にとどめ、原文が言い切りなら本文も言い切ってよい

**述語の形では区別しない。** 「〜によると、…です」「〜は、…と説明しています」「〜によれば、…します」は、どれも主体明示として同じに扱う。

| 例 | 扱い |
|---|---|
| 「〇〇協会の解説記事**によると**、…の対象に**なりません**`%%出典:…%%`」/ 原文も言い切り | **裏付けあり**((1)(2)(3)をすべて満たす) |
| 「〇〇協会の解説記事**によると**、…**違法です**`%%出典:…%%`」/ 原文は「違法とみなされる**おそれがある**」 | **不合格**(述語が原文を超えている。(3)を満たさない) |
| 「〇〇事務所の解説**は**、…**と説明しています**」/ 同じ文に出典の紐付けが無い | **不合格**((2)を満たさない) |

述語の形(「〜によると…です／ません」)で区別すると、断定への転化とみなして落とす・前文参照で主体を特定できないとして落とす、という誤りが出る。読者は「〜によると」で始まる文も主体の見解として読むため、述語の形で区別せず、**読者が裏付けをたどれるか(出典の紐付け)と、原文を超えていないか**を見る(VERIFICATION.md「その20」)。

### 決めたこと(候補の振り分け)

機械の候補抽出に**主体明示の標識**(`subjectMarkers` 15種: 「によると」「によれば」「と説明しています」「の解説は」等)を足し、
断定の候補と**主体明示の候補**に分ける。分けた文は黙って落とさず、標識と理由を判定ログに残す。
両方を第4層に渡し、**判定の観点だけを変える**(前者は出典の `type`、後者は上の3条件)。

### 決めたこと(項目11)

紐付けとして数える形に **`%%出典:…%%`** を足した(`verify-article.js` の `RE_HAS_CITATION_MARK`)。
主体を明示し同じ文に紐付けた記述は**能動形・受動形とも発火しない**。
self-test に「**発火しないはず**」の注入を3件足し、毎回確かめる(発火すると板挟みが戻るため)。

## 46. 層の中の独立した呼び出しを並列にする

### 直した理由

第3層(3回実行)と第4層が、判定1巡の時間の大半を占める。
第3層の3回は同じ入力に対する独立した呼び出しであり、直列に待つ必要がない。第4層の3タスクも互いの出力を参照しない。

### 決めたこと

| 対象 | 並列にするもの | 順序を保つもの |
|---|---|---|
| 第3層 | `runs` 回の実行(既定3回) | — |
| 第2層 | タスク実行側 と 枠だけを見た読者役 | 合否判定側(実行側の出力を入力にする) |
| 第4層 | design・declared・factual の3タスク | — |

- 同時に走らせる数の上限は `limits.parallelCalls.maxConcurrent`(既定4)
- **1つでも失敗したら、他の完了を待ってから層全体を異常にする**(成功した分だけで進めない)
- 同時実行の制限に当たった呼び出しは、**失敗した分だけを直列でやり直す**。やり直した事実は層の結果に残す
- **並列に走っている間は、判定ログ・台帳・`runs/` へ書かない**(書き出しは判定の確定後に1回)
- **記事単位の並列(複数記事の同時処理)は行わない**(運用期の設計。判断事項のまま)

### 実装の形

`judge.js` は**同期のまま**保った。非同期にすると、工程を1つずつ実行する仕組み全体に波及するためである。
呼び出しを束ねて待つ処理だけを `call-parallel.js` に置き、`judge.js` からは `spawnSync` で1回だけ起動する。

各層は `callMany` を受け取る。渡されなければ `call` を順に呼ぶ(既存の経路・テストはそのまま動く)。

## 47. 第3層の採用基準

### 直した理由

第3層の和集合には、**3回中1回だけ**に出た指摘が多く含まれる。出た否定をすべて差し戻しに入れると、実行ごとのぶれがそのまま差し戻しの件数になり、執筆側は巡ごとに別の指摘に応じることになる。

### 決めたこと(`layer3.adoption`)

| 出た回数 | 型(kind) | 扱い |
|---|---|---|
| 過半数の実行(3回なら2回以上) | 問わない | 採用 |
| 1回の実行でだけ(過半数に満たない) | 型を問わない(2026-10-11 の決定で、根拠を超えた断定・根拠が無い主張の例外を無くした) | **採用しない**。判定ログに理由(何回中何回・型)つきで残す |
| 判定が自分で「弱い」と書いた否定 | 型・回数を問わない | **採用しない**。判定ログに残す |

- 採用するのは、定義どおりの回数(`runs`)を実行して、過半数の実行に出た否定だけ。実行した回数が `runs` に満たない場合は採用しない(2026-10-11 依頼者の決定。以前は「実行が1回だけの場合は出た否定をすべて採用」だった)
- 第3層を理由とする差し戻しは、1つの記事で1回だけ。1回直したあとは第3層を理由に差し戻さず、最後の判定で第3層をもう一度実行した結果は報告だけにする(`layer3.roundScope`)
- 同じ位置に複数の型が付いた場合は、記録には出た型をすべて残す(採否は出た回数で決める)
- **採用基準は第3層の判定プロセスに渡さない**(型の選び方で採否を動かせないようにする)。渡すのは型の一覧と「複数の型に当たる場合は一覧の先の型を選ぶ」だけ
- 採用しなかった否定は `notAdoptedClaims`。**差し戻し文には入れない**。停止点の報告・記事の報告には出す

## 48. 上限到達の条件文を単一定義から組み立て、典型値を並記する

- `limits.onLimitReached.conditionText` に「5回」「60分」を直書きすると、上限を変えたあとも**古い数値のまま停止記録に入る**
- 条件文は数値を持たず、`{maxReworkPerArticle}` などの差し込み口だけを持つ。判定ログに書き写すときに `limits` の値を差し込む(`judge.js` の `limitConditionFullText`)。値の無い差し込み口は「【値が無い: キー】」として残す
- **典型値を並記する**: 112分は実測の最大値を積み上げた暴走防止の上限である。典型値なら差し戻し2回でも上限よりずっと早く終わる。典型値と最大値の両方を記録し、運用期の値として確定する

## 49. `--continue` は設計期モードでだけ受け付ける

- 判定を経ていない修正版を判定にかけ直すかどうかは、依頼者が停止点で状態を見て決める設計期の操作である
- 運用期に受け付けると、止まった実行の成果物を、人の判断を経ずに判定へ戻す経路になる
- 運用期モードでは `start --continue` を拒否する(`limits.continueDraft.modeConditionText`)。**運用期への切り替え時に確定する(判断事項)**

## 50. 画像依頼

### 直した理由

判定を通過して公開待ちに置かれた記事は、サムネイルが無くても公開される(記事は画像なしで公開してよい。依頼者の決定)。画像テーマ案が本文の HTML コメントにあるだけでは、どこからも取り出されず、依頼者が記事を開いて探す必要がある。

### 決めたこと(`imageRequest`)

- 執筆側は画像テーマ案を **frontmatter の `imageBrief`** に構造化して書く(`thumbnail` / `bodyImages[{afterHeading, theme, reason}]`)。`imageBrief` は読者提示テキストに入らず、サイトも描画に使わない
- 公開待ちへの配置(`place`)で、公開待ちフォルダに **`<記事名>__画像依頼.md`** を置く。中身は、記事タイトル・想定読者・サムネイルのテーマ案(ChatGPT にそのまま渡せる日本語のプロンプト。特定の店舗・ブランド・実在の人物を想起させない構図の指定を含む)・本文画像の候補位置とテーマ案・画像を置くパスと `thumbnail` の書き方・画像を埋めたあとは commit・push(公開待ちの記事は、`publishAt` が入っていれば `npm run queue` は要らない)
- 既存記事の修正版(`replace`)は、`thumbnail` が埋まっていれば `imageBrief.bodyImages` に候補がある場合だけ作る。`thumbnail` が空なら新規記事と同じくサムネイルを含めて作る(置き先はどちらも公開待ち。公開済みには置かない。画像を埋めたあとは commit・push。公開待ちの記事は、`publishAt` が入っていれば `npm run queue` は要らない)
- `imageBrief` が無い記事は、HTML コメントのうち「画像」を含むものを構造化されていない候補として写す
- 公開キュー(`queue-lib.js` の `listQueueFiles`)・`--revise` の対象・記事の実在確認(項目37)は、画像依頼を記事として扱わない。末尾の定義は `queue-lib.js` の `IMAGE_REQUEST_SUFFIX` ただ1つ
- 画像依頼を書けなかった場合は、記事を置いたことと書けなかった理由を残して工程を異常にする(黙って完了にしない)


## 51. 第4層 design の基準を「固有の事実を根拠にしているか」に置き直す

### 直した理由

design が「構成の選定理由が他の記事にもそのまま当てはまる一般論か」を、流用できる別テーマを1つ挙げさせて判定すると、資格・制度・効果の線引きのような同じ型のテーマでは、執筆側が理由を収集データの事例・物質名・濃度基準に置き直しても通らず、不合格が続く。

**「流用できるか」を基準にすると、資格・制度・効果の線引きという型を持つテーマはすべて流用可能と判定され、通る理由が存在しない。基準が到達不能になる。**

### 決めたこと

| | 内容 |
|---|---|
| 合格 | 構成の選定理由が、収集データにある固有の事実(事例・数値・制度・出典の記述)を根拠として挙げ、その事実が見出しの並びのどこを決めたかを述べている |
| 不合格 | (a) 固有の事実を挙げていない(一般的な説得の原則だけ)/ (b) 挙げた事実が収集データに無い / (c) 事実と並びの対応が述べられていない |
| 使わない基準 | 他のテーマに流用できるか。型が同じテーマが他にあることは、この記事の理由が固有の事実に基づいていることと矛盾しない |

- 条件文に合格の例(相談事例の因果の順序を挙げ、見出し3・4を見出し6より先に置く理由にしている)と不合格の例(「制度を知らないと事例を誤読する」だけ)を置く
- design にも収集データを渡す。判定プロセスは挙げた事実ごとに収集データの引用(`sourcesQuote`)と、決めた並び(`decidedOrderFullText`)を出す
- **機械照合**: 合格とされても、事実が0件 / 引用が収集データに実在しない / 並びの対応が空 / 不合格条件を挙げている、のどれかなら不合格に直す(`designMechanicalCheck`)。第4層 factual の `authorityOverride` と同じ考え方
- 生成メタ情報に理由の版が複数あれば最新の版を判定する。一般的な説明が混ざること自体は不合格にしない
- 執筆側(`RATIONALE_RULE`・`writer.md`)も同じ基準にそろえた

## 52. 判定の収束 — ぶれで差し戻しにしない

### 直した理由

差し戻しの上限に達して止まる原因が、記事の欠陥ではなく**判定の非収束**であることがある。

| 層 | 起きること |
|---|---|
| 第3層 | 修正版で採用した指摘の多くが、修正前からあった文への新しい指摘になる。3回では出尽くさず、巡ごとに別の穴が見つかる |
| 第2層 | concrete が、該当箇所を変えていないのに通ったり落ちたりする(1回実行) |
| 第4層 factual | 図表のラベルのような断定を4回中1回しか拾わない。主体も出典も無い評価の文を、前の段落に統合されただけで「実質的に同一段落内の参照とみなせる」として通す(**判定が緩くなる向き**) |

「1回の判定で出た指摘を直せば通る」という前提が成り立たないため、差し戻し回数の上限が意味を持たない。**判定条件は変えず、ぶれを吸収する実行の仕方に直す。**

### 決めたこと

| 対象 | 実行の仕方 | 規則 |
|---|---|---|
| 第3層 | 初回3回を同時に実行し、そのあと1回ずつ追加する。追加した回で**新しい位置の否定が出なければ終える**。合計5回まで。採用基準(実行した回数の過半数。2026-10-11 の決定で、1回でも根拠を超えた断定・根拠が無い主張の例外を無くした)は、実行したすべての回で数える。差し戻し後の再判定でも同じ手順(前回の採用分に限定しない) | `layer3.convergence` |
| 第2層 | 実行側・「この記事で分かること」の読者役・合否判定側を各3回。i 回目の実行結果を i 回目の合否判定に渡す。**タスクごとに、3回中2回以上不合格のときだけ不合格** | `layer2.majority` |
| 第4層 factual | 2回実行し、事実照合・要確認候補の誤り・権威性・主体明示の指摘を**和集合**で採る。同じ位置の指摘は1件にまとめる。1回でも failed なら不合格。design・declared は1回 | `layer4.tasks[factual].runs`・`unionConditionText` |
| 前文参照の例外 | 「同じ解説は」「この通知は」「同ガイドラインは」等の**参照語で始まる文に限る**。同じ段落にあることは例外の理由にならない | `subjectAttribution.conditionText`・factual の `taskText` |
| 第4層 factual の機械照合 | 断定の候補のうち、(1) いずれかの回が法令・税法・約款の解釈、制度・業規制への該当、利益・損失・リスク・税負担の評価と分類し (2) 参照語で始まらず (3) 主体の明示が無く(主体の標識が無く、かつ factual の2回とも「同じ文の中に主体が明示されている」とは分類しなかった) (4) 同じ文に出典の紐付けが無い文があれば、判定プロセスの結論にかかわらず不合格に直す(合格を不合格に直す向きだけ) | factual の `mechanicalCheckText`・`referenceLeadPattern` |
| 判定ログの処理時間 | 累計と上限の判定は、第6層を始めた時点の実行の記録の記事の処理時間(retry の所要を含めない)。retry で実行した層の所要は判定の所要にも足さない | `limits.judgmentLogElapsedText` |

- 評価に当たるかは文の意味によるため、factual に**断定の候補すべての分類**(`candidateAssessments`)を出させ、2回の和集合を使う。
- **主体の明示**(依頼者の判断): 標識(`subjectMarkers`)だけで見ると「金融庁の監督指針(…)では、…定められています。」のように主体を書いた文まで当ててしまい、依頼者が定めた条件より厳しくなる。factual に「同じ文の中に主体が明示されているか」(`subjectExplicitInSameSentence`)も分類させ、**2回とも明示ありとした文だけを外す**(1回でも無し・値の欠落なら当てる)。同じ段落の別の文や前の文に主体があることは明示に当たらない分類が返らなかった候補・記事の行の中の文に対応づけられなかった候補は不合格にせず、件数と行を記録に残す
- 機械照合の条件文そのものは判定プロセスに渡さない(判定条件の側〔`authorityCheck.conditionText`〕には、紐付けの無い評価の文が不合格になることを書く)
- 出典の紐付けの判定(`hasCitationMark`)は、正規化(`stripDecorationAndCitations`)が外す出典の丸括弧と同じ定義を使う(`normalize-text.js` の `CITATION_PAREN_SOURCE`)
- どれか1回でも呼び出しの失敗・JSON が返らない場合は、層全体を判定を経ていない(error)とする(成功した回だけで多数決・和集合を取らない)
- 停止点の報告と差し戻し文に、実行回数と採否の決まり方(第3層: 実行した回数・各回の新しい位置の数・終えた理由 / 第2層: タスクごとの多数決と各回の合否 / 第4層: 各回の件数と和集合・機械照合で当たった文)を出す
- 執筆側(`writer.md`)にも、参照語の範囲と「評価の断定には同じ文の出典・主体の明示・参照語のどれかを持たせる」を書いた

## 53. 判定1巡の時間の是正(緩めずに)と、紐付けの定義の統一

### 直した理由

判定1巡の時間が長くなると、上限の式(固定分 + 2 × 1巡)が上限(112分)と両立しなくなる。

| 原因 | 内容 |
|---|---|
| factual の出力の途中切れ | 1回の応答の出力上限は 64,000 トークン。factual が1回で候補すべての分類と照合を行うと、思考が長くなって上限を使い切ることがある。claude は続きの応答を出すが、`--output-format json` の `result` には**最後の応答の文章だけ**が入り、JSON の途中から始まる文章しか受け取れない。読み取りのやり直しを直列で行うと、時間が増える |
| 同時実行の上限3 | 同時実行の上限が3だと、第4層の4つ目の呼び出しが待つ |
| 回帰判定の経路 | `judge.js` の main は並列の口を持たず直列で呼んでいた |
| 紐付けの定義の食い違い | 主体明示の条件 (2) は %%出典 だけ、factual のタスク文は丸括弧・リンクも、項目11 は中身を問わない丸括弧すべて、機械照合は出典を示す丸括弧(条件文ごとに違う) |
| 候補の抽出 | 本文の語尾のある文だけを候補にすると、図表のラベル(「(ある資格者)のみ扱える」のようなもの)や句点で終わらない箇条書きが候補にならない |
| 機械照合の穴 | 分類が返らない文・行に対応づけられない文は当てない / 主体の標識だけで外す |

**判定条件と上限の値は変えず、実行の仕方と読み取りを直す。上限の値は依頼者が決める。**

### 決めたこと

| 対象 | 変更 | 規則 |
|---|---|---|
| 出力の読み取り | 判定側の claude を `--output-format stream-json --verbose` で起動し、**全応答の文章を出た順に結合**してから JSON を取り出す(続きの応答が開き直した JSON ブロックの行は外す)。読み方は `parseClaudeOutput` ただ1つ(`call-parallel.js` も同じ関数)。文章が応答をまたいだ呼び出しは、生の出力を層の結果の `spanningCalls` に残し、無ければ「実走では未再現」と書く | `logging.judgeCallOutputText`・`logging.spanningCallText` |
| 呼び出しの記録 | 呼び出しごとにトークン数(入力・キャッシュ読み・キャッシュ作成・出力・うち思考)・stop_reason・num_turns・応答の数・api_error_status・rate_limit_event・費用・所要を、層の結果の `callRecords`・`usage`・`rateLimitedCalls` に残す。rate_limit_event の `allowed_warning` は制限に当たったに数えない | 同上 |
| factual の分割 | 1回の呼び出しを「照合」(事実照合・要確認候補・権威性・主体の明示。**出力は JSON だけ、理由は指摘にだけ書く**、指摘に条件の名前 conditionName)と「分類」(候補を **20件ずつ**の別の呼び出し。4項目を真偽値で。項目は減らさない)に分ける。どちらも runs(2)回。思考の上限は設けない(依頼者の判断 2) | factual の `verifyOutputText`・`classification` |
| 無効の回 | 全応答を結合しても JSON を取り出せない回は無効として記録し(何の何回目か・理由・トークン数・stop_reason・応答の数・生の出力)、**有効な回だけで和集合**。照合の有効な回が0回、または分類のどれかの小分けで有効な回が0回なら層全体を error。有効な回が1回分だけなら「和集合が1回分のみ」と残す | factual の `invalidRunText` |
| 条件の名前での分類 | 指摘は conditionName(事実照合 / 権威性 / 主体の明示)の分類に置き、置き場所と名前が違う指摘は移して記録する。権威性には primary の原文で裏付けられない断定だけを入れる | factual の `unionConditionText`・`authorityCheck.conditionText` |
| 同時実行 | 上限を **4** にする(第4層の design・declared・照合×2 が待ちなく始まる数)。制限の応答の回数と時刻を記録する | `limits.parallelCalls.maxConcurrent`・`maxConcurrentRationale` |
| 回帰判定 | `judge.js` の main も `runJudgmentLayers` を通し、工程と同じ呼び出し方(並列の口・位置の逆引き・この記事で分かることの入力)にする | — |
| 紐付けの定義(依頼者の判断 1 = B) | **同じ文(句点の前)の `%%出典:…%%` の注記だけ**。丸括弧の出典表記・Markdown リンクは数えない。定義は `normalize-text.js` の `hasCitationMark` ただ1つで、第1層 項目11 と第4層が同じ定義を使う。frontmatter の図表の文字列は、その図表の出典欄 `charts[i].source` があれば紐付けあり(判断 3 = B)。**緩くなる条件文は無い**(対照表は VERIFICATION その29) | `citationDefinition` |
| 候補の抽出 | 読者提示テキスト全体(本文のすべての行〔見出し・表は欄ごと・箇条書き〕+ frontmatter のタイトル・この記事で分かること・マスコットの一言・図表の文字列〔出典欄を除く〕・折りたたみの見出しと中身)。句点で終わらない文字列は語尾を問わず候補。id(K1…)で分類と機械照合を対応づける。行の範囲では決めない | `candidateExtraction.conditionText`・`scopeRationale` |
| 機械照合 | 断定の候補と主体明示の候補の両方が対象。(1) 有効な回のどれかが評価と分類(**分類の無い文は評価として扱う**) (2) 参照語で始まらない (3) 有効なすべての回が「同じ文の中に主体が明示」と分類した文だけを外す(**主体の標識だけでは外さない**) (4) 同じ文に紐付けが無い(**行に対応づけられない文は紐付け無しとして当て、文の全文を位置に書く**)。判定プロセスの分類(参照語・紐付け)と機械の照合の食い違いは件数を記録 | factual の `mechanicalCheckText` |
| 出力の形式の例 | 照合と分類の出力の例に、実在の候補の id・行番号・真偽値を書かず、山括弧の説明だけにする(例に引っ張られて照合を逃れる向きを作らない) | `layer4.outputExampleRule` |

- 執筆側(`writer.md`)・`nevora-pipeline-verifier.md`・項目11 の解消手段の文・`docs/CONTRIBUTING.md` §16 を、紐付けは同じ文の `%%出典:…%%` だけに揃えた。frontmatter の文字列も判定の対象で、図表は出典欄があれば紐付けありと書いた

- 既存記事は、判定が厳しくなるため、運用期切り替え後の `--revise` で書き換える

## 56. 修正工程の変更範囲を、差し戻し文の指摘の位置の中に限る

## 57. 修正工程の位置の照合を文ごとにし、修正で足した出典名・主体名を照合し、差し戻し回数の上限を3回にする

### 決めたこと(依頼者の判断1〜3)

| 対象 | 変更 | 規則 |
|---|---|---|
| 位置の照合(直し1) | 引用を行ごとに加えて文ごとにも分け、4字以上の文を含む行・項目をすべて指摘の位置にする | `fix-scope.js` の `quoteParts`・`locateText`(規則の文「引用が複数行にわたる場合は、各行が現れる行・項目」の実装を直した) |

## 58. 第1層の指摘の位置を判定時の行番号にし、記事が変わらないときの再度の受け渡しと、修正後・判定前の第1層の事前実行を足す

- 第1層の指摘が行番号を持たず、修正工程の位置を該当テキストから逆引きすると、逆引きの正規化(読者提示テキストの表記「【リンク】文言 → 遷移先」で生の行をそろえる)の都合で、内部リンクの行が指摘の位置に入らないことがある

## 61. source の無い図表の書き換えを修正差分の事実照合の対象にする

### 直した理由

source の無い図表の行を修正工程が書き換えた場合の扱い。文字を足した書き換え(記号「△」→「◎」、折れ線の値 8→9、prosCons の文の書き換え)は差分の事実照合の対象に入るが、**文字を削っただけで別の値になる書き換え(価格帯「1,500〜2,500円」→「500〜2,500円」、使用タイミング「週2〜3回・〇〇の後」→「週2回・〇〇の後」)は「削っただけの変更」として対象に入らない**(対象外を免れるのは source のある図表の中の変更だけ)。また、source の無い図表の中の変更には図表の行が付かず(§60 の PHASE 8)、照合に渡るのは「△ → ◎」だけで、どの項目・どの対応タイプの記号かが分からない。

### 決めたこと

| 対象 | 変更 | 規則 |
|---|---|---|
| 照合の対象 | 図表の中の変更は、削っただけでも照合の対象にする(図表の値は1つの値が1つの主張で、文字を削るだけで別の値になる)。中身を全部削った変更は、これまでどおり対象にしない | `fixScope.diffFactCheck.conditionText` |
| source の無い図表の文脈 | 変えた値がどの行・どの欄の値かを示すために、読者に見える図表のすべての行(読者提示テキストと同じ描画)を `chartContext` として付ける。行ごとの裏付けは判定せず(`chartRows` に入れない)、変えた後の値を行・欄の意味とともに(例「年会費無料カードの基本還元率は0.5〜1.0%」)言い足し(additions)として判定する | `fixScope.diffFactCheck.conditionText`・`taskText` |

- source のある図表の中の変更は変えない(source と行ごとの判定の行を付ける)
- 本文の帰属の無い語句の削除は、これまでどおり対象にしない(依頼者の問いの範囲外)
- テスト: source の無い図表の価格帯・使用タイミング・記号・折れ線・prosCons の書き換え(対象・文脈つき)、中身を全部削った変更と本文の削除(対象外)、source のある stat(従来どおり)、判定側の指示文の `chartContext`、修正の工程から照合に渡ること。破壊テストは行わない(依頼者の方針)

## 64. 判定の流れ(指摘の分け方・やり直す範囲・差し戻しの上限・公開・時刻の記録)(2026-10-11 依頼者の決定)

- 指摘の分け方: 判定する担当は、指摘ごとに、ア(差し戻す=内容が変わる指摘。事実・条件・手順・結論・読者への約束が変わるもの)・イ(まとめて直す=形と書き方の指摘。字数・文の数・語尾・強調の数・部品の並び・`sectionAlternate`・表記など)・ウ(差し戻さない=出典の印の欠け・企画書と原稿の食い違い)のどれかを付けて返す。イは差し戻しに数えず、仕上げで1回にまとめて直し、直していない担当が内容が変わっていないことを1回確かめる。残った形の指摘はもう1回だけ直し、それでも残れば報告に書いて先へ進む。ウはその場で直す(食い違いは企画書の側を直す)か、報告だけにする
- 差し戻したあとは、直した所に関係する判定だけをやり直す(すべての判定をやり直さない)
- 差し戻しの上限: 1つの記事で合計5回。第3層はそのうち1回まで。上限に達して通らないときは、公開せずに止めて報告する(`limits.maxReworkPerArticle`。以前の値〔1回・2回・3回〕を改めた。範囲の照合・第1層の事前実行の差し戻し〔`fixScope.maxSendBacks` など〕は判定の差し戻しに数えず、値は変えていない)
- 第3層の採用と差し戻し・直し方は §63 のとおり(採用は過半数の実行に出た否定だけ、第3層の差し戻しは1記事1回、足す文は行き先や手順を示すだけ)
- 公開の仕方(2026-10-12 依頼者の決定。2026-10-11 の「公開は待たない」を改めた): 依頼者が「すぐ公開」と指定した記事は、公開の時刻(`publishAt`)を今の時刻以前にして公開待ちに置き、push のあと手元(`サイト運営/サイト本体`)で `npm run queue:release` を実行し、移ったファイルをファイル名を指定して commit・push する。それ以外の記事(複数をまとめて作る場合を含む)は予約投稿にし、`npm run queue` で時刻を割り振って公開待ちに置き、commit・push して終わる(公開は自動処理に任せ、待たない・手動で実行しない)。デプロイの反映を確かめる待ちは、記事の公開を待つことではない
- 判定の段階ごとに、始めた時刻と終えた時刻を記録し、報告に書く
- 手順の正は `.claude/skills/run-article-production/SKILL.md` の「判定の流れ」と `docs/pipeline/JUDGE-ITEMS.md`。記事の公開の手順は `.claude/agents/publisher.md`
