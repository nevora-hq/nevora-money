### 1-3. 傾向とばらつき

**全記事に共通(傾向 → 上流に原因)**

- `charts`・`summaryPoints`・`sources` はほぼ全記事に存在する → 指示由来・機械判定由来
- 最終H2が「まとめ」系の記事が大半
- 機械判定34項目: ほぼ全記事が全項目Pass
- **本文のみでは2000字未満の記事が相当数ある**。frontmatter(図表・アコーディオンのテキスト)を含めると量は足りており、文字量の相当部分が本文からfrontmatterの視覚要素へ移動している

**記事によって出たり出なかったり(ばらつき → 生成裁量。判定要件が欠けている)**

- H2セクション(本文100字以上)のうち「具体的場面 / 数量 / 読者の行動」が2種未満のものが半数超ある
- 記事ごとの「2種未満セクション率」は0%〜100%に散る
- 締めの一文: 「〜の記事もあわせてご覧ください」「〜テーマもあわせてご覧ください」の定型に偏る

## PHASE 3. 症状の構造化

### 3-1. 症状の列挙(原因は語らない)

- S1: H2セクションの多くに、具体的場面・数量・読者の行動のいずれも2種そろっていない
- S2: 本文のみでは2000字未満の記事がある
- S3: 締めの一文が同一定型に偏る
- S4: セクションが「出典の要約1〜2文 + コールアウトボックス」の反復で構成される記事がある
- S5: 商品名の実在未確認、主語省略の体験談疑い、チャート数値と本文数値の不整合が、検出されたまま処理されていない
- S6: 編集長の合格ラインが2つの文書で食い違っている(90点上限で差し戻し / 80〜99点は公開可)
- S7: 判定の記録が残らない(機械判定JSONは一部の記事分、AI判定は記録なし)
- S8: ルール定義が大量の文書に分散し、「食い違ったら◯◯が正」という宣言が複数箇所ある

### 3-2. 症状を工程に紐づける

| 症状 | 発生工程 | 分類 | 根拠 |
|---|---|---|---|
| S1 | 執筆(writer) | 生成裁量 | writer.md「具体例・具体的な場面を各見出しに入れる」は指示として存在するが、`verify-article.js`の34項目に対応する検査が無い。記事ごとの充足率が0〜100%に散る |
| S2 | 執筆(writer) | 混在(指示由来の枠 + 裁量の中身) | 300字ルール・H2ごと視覚要素必須・chart2件以上により、説明が本文からfrontmatterの視覚要素へ移動する。枠は指示由来、移動量は裁量 |
| S3 | 執筆(writer) | 生成裁量 | writer.md「締めの一文が同型にならないよう横断チェック」は複数記事一括制作時のみの指示で、単記事生成では発動しない。機械検査も無い |
| S4 | 執筆(writer) | 混在 | 各セクションが「業界団体は〜と説明しています」+ボックスで完結する形が起こりうる |
| S5 | 検証(nevora-pipeline-verifier) | 固定枠 | `verify-article.js` が項目18・19・20を`result: "N/A"`(非ブロッキング・要目視確認)として出力し、verifier定義が「判定に含めず参考情報として報告するのみ」と規定 |
| S6 | 編集長(editor-in-chief) | 固定枠(2文書の並存) | `editor-in-chief.md`「1つでも欠ける場合は90点を上限として差し戻し」 vs `final-review-scoring/SKILL.md`「80〜99点: 軽微な修正推奨、公開可」 |
| S7 | 全工程 | 固定枠 | verifier定義のみが保存先を規定(`docs/pipeline/verify/{slug}_{日付}.json`)。reviewer・legal-checker・editor-in-chiefの定義に判定結果の保存規定が無い |
| S8 | 全工程 | 固定枠 | CONTRIBUTING.md・writer.md・SKILL.md・editor-in-chief.md・verifier・SPEC-EXTRACT |

### 3-3. 上流・下流の切り分け

```
上流原因 U1: 判定系の重心が形式に100%寄っており、内容を判定する層が存在しない
  ├ 下流症状 S1(具体性の欠如)        : U1を直せば解消する → 個別要件を作らない
  ├ 下流症状 S3(締めの定型化)        : U1を直せば解消する → 個別要件を作らない
  └ 下流症状 S4(出典要約の反復)      : U1を直せば解消する → 個別要件を作らない
     根拠: 機械34項目はすべて形式・装飾・表現規制・データ整合の検査であり、
           内容を判定するのは編集長の単層AI判定のみ。その編集長は確定稿の保存も
           担当しており、差し戻すと自分の作業が増える(判定者と実行者が同一)。
           結果、内容要件は自己申告で通過する。S1がその帰結。

上流原因 U2: 形式要件が本文の内容量を圧迫する方向に働いている
  └ 下流症状 S2(本文2000字未満)   : U2を直せば解消する
     根拠: 300字ごとに視覚要素を要求する規則(項目23)+ H2ごと視覚要素必須(項目8)
           + chart2件以上(項目3)+ 装飾6箇所以上(項目4)が同時に働き、
           H2を細分化して各セクションを100〜200字に縮める圧力になる。
           frontmatter込みの総量は足りているため、
           「量が足りない」のではなく「本文から視覚要素へ移動している」。

上流原因 U3: 合格判定が点数化され、かつ合格ラインが二重定義されている
  └ 下流症状 S6                      : U3を直せば解消する

独立原因 I1: 虚偽・誤情報に直結する検査が非ブロッキングのまま(S5)
     U1〜U3を直しても解消しない。項目18・19・20の扱いを変える単独対処が必要。
     ただし単純なブロッキング化は不可(項目20は本文中の任意の数値を
     チャート値と照合するため過検出が支配的)。判定方法の再定義が必要。

独立原因 I2: 判定ログが存在しない(S7)
     自動改修サイクルの母数が無いため、I2を直さない限り§6-5は成立しない。

独立原因 I3: ルール定義の多重化(S8)
     §6-1(ルールは常に1つ)に直接抵触。判定基準の記述が複数文書にあり、
     片方だけ更新される事故が起こりうる(例: 300字ルールの
     改訂がeditor-in-chief.md・verifier定義に反映されない)。
```

**要件の数を増やすのではなく、U1〜U3・I1〜I3の6点に集約して対処する。** S1・S3・S4に個別の要件は作らない。
