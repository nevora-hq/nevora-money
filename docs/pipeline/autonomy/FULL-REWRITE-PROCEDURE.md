# 全記事見直し(企画からの全面書き直し)の手順

- 本ファイルを、全記事見直し(企画からの全面書き直し)の手順の正本とする。
- **多層判定(`run-local.js`の第1〜6層・self-test)は経ない。** 最終判定は依頼者の目視。理由: run-local.jsのself-testは意図的に停止している(`docs/pipeline/autonomy/SELFTEST-PAUSE.md`参照)。全記事見直し・ルール改修の期間は、この経路を使わない運用にしている。

## 手順

1. **対象の選定**: 書き直す記事の一覧を `作成中/_対象_第N回_YYYY-MM-DD.md` に作る(選定理由・件数を明記)。
2. **書き直し**: 対象記事を企画から書き直す(タイトル・見出し・本文・図表・出典等)。ファイル名・`date`・`skinType`・URLは元のまま変えない。お金の記事の書き直しでは、税率・金利・手数料・還元率・上限額・制度の要件を書き直し時点の公式の情報で確かめ直し、時点(年月か年度)と `updatedDate` を残す。数値を直すときは本文・図表・`summaryPoints` など同じ値の出現箇所をすべて直す。
3. **push前の項目35確認(2026-09-28追加)**: 書き直した記事のうち、図解(`charts`)を新規作成・変更した記事、またはfrontmatter(`heroImage`・`thumbnail`等)を書き換えた記事は、pushする前に必ず対象記事へ `node scripts/verify-rendered-layout.js --strict <slug>` を実行し、検出0件を確認する。0件でない記事は、その記事だけ差し戻して直すか、依頼者に報告して指示を仰ぐ(検出が残ったままpushしない)。
   - この確認が手順に無いと、書き直しで失われた既存の項目35対応(座標調整済み図解・短いラベル・heroImage分離)が週次実行(item35-weekly)まで気づかれない。
4. **依頼者の目視確認**: 書き直した記事を依頼者が目視し、可否を判断する。
5. **台帳への記録**: 4の目視確認で可となった記事について、`node scripts/ledger-add-visual-check.js --slug <slug> [--slug <slug> ...] --reason "<理由>" --commit <対象コミットのハッシュ>` を**依頼者本人が**実行し、台帳(`publish-ledger.json`)へ`kind: "requester-visual-check"`のエントリを追記する(`docs/CONTRIBUTING.md` 40節参照。このスクリプトは内部でも項目35 --strictの0件を確認するため、3の確認が漏れていた場合はここで検知される)。
6. **commit・push**: 記事データ・台帳の変更をcommitし、pushする。(`ledger-add-visual-check.js` が使えない間は、5の台帳の追記を依頼者の指示による代行記録として、`.claude/agents/publisher.md` の「台帳の代行記録」の手順で行い、4の依頼者の目視は公開のあとにする。2026-10-03)
7. **push後の確認**: push から最低5分待ち、Vercelのデプロイ成功(トップページ・記事ページHTTP 200、sitemapの記事URL件数の整合)を確認する(CLAUDE.mdのデプロイ運用ルール)。

## まとめて直す回(組ごと)

多くの記事をまとめて直す回の進め方。上の「手順」の4(依頼者の目視)は、依頼者が不在の回は、本文を直していない担当の判定に置き換える(CLAUDE.md の「依頼者が不在の回」)。公開・台帳の手順の正は `.claude/agents/publisher.md`(「台帳の代行記録」)で、ここには書き写さない。

1. **20本ずつの組に分ける**。組の中の担当の並べ方は CLAUDE.md の作業方針(基本は20体)。
2. **組ごとに、次の順で行う**: 担当が直す → 検査(`verify-article.js` など。走らせ方は writer.md の「検査の走らせ方」)→ 本文を直していない担当の判定(No がなくなるまで。`docs/pipeline/JUDGE-ITEMS.md`)→ 公開(`publisher.md` の「台帳の代行記録」。pushは組ごとに1回)→ 本番の確認(push から5分待ち、トップ・記事数・その組の記事を確かめる。記事数が減っていたら、次の組へ進まず原因を直す)。
3. **指示の写しと再開の手順**: 依頼者の1通の全文を `サイト運営/記事データ/作成中/_指示_<回>_<日付>.md` に写す。進捗ファイル `サイト運営/記事データ/作成中/_進捗_<回>_<日付>.md` を作り、先頭に再開の手順(「コンパクトのあと、または再開のときは、_指示_<回>_<日付>.md とこのファイルを読み直し、git status で commit していない変更が無いかを確かめ、下の『次の手順』から、止まらずに続ける。」。依頼者が不在の回は「依頼者は不在。質問しない。」を足す)を置いて消さない。その下に「次の手順」を1行で書き、手順が1つ進むたびに書き直す。
4. **個別の小さな直し**は、組の作業に混ぜず、先に1つの commit で出す。
5. **変えていない記事**は、公開・台帳の対象にしない(`publisher.md`「台帳の代行記録」の1)。
