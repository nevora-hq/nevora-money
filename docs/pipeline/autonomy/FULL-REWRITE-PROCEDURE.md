# 全記事見直し(企画からの全面書き直し)の手順

- 本ファイルを、全記事見直し(企画からの全面書き直し)の手順の正本とする。
- **多層判定(`run-local.js`の第1〜6層・self-test)は経ない。** 最終判定は依頼者の目視。理由: run-local.jsのself-testは意図的に停止している(`docs/pipeline/autonomy/SELFTEST-PAUSE.md`参照)。全記事見直し・ルール改修の期間は、この経路を使わない運用にしている。

## 手順

1. **対象の選定**: 書き直す記事の一覧を `作成中/_対象_第N回_YYYY-MM-DD.md` に作る(選定理由・件数を明記)。
2. **書き直し**: 対象記事を企画から書き直す(タイトル・見出し・本文・図表・出典等)。ファイル名・`date`・`skinType`・URLは元のまま変えない。お金の記事の書き直しでは、税率・金利・手数料・還元率・上限額・制度の要件を書き直し時点の公式の情報で確かめ直し、時点(年月か年度)と `updatedDate` を残す。数値を直すときは本文・図表・`summaryPoints` など同じ値の出現箇所をすべて直す。1記事は1体の担当が書く(1記事1体)。書いた担当は、自分の記事の通読・判定をしない。1記事の流れは次の順(下の「1記事の流れ」)。
3. **push前の項目35確認(2026-09-28追加)**: 書き直した記事のうち、図解(`charts`)を新規作成・変更した記事、またはfrontmatter(`heroImage`・`thumbnail`等)を書き換えた記事は、pushする前に必ず対象記事へ `node scripts/verify-rendered-layout.js --strict <slug>` を実行し、検出0件を確認する。0件でない記事は、その記事だけ差し戻して直すか、依頼者に報告して指示を仰ぐ(検出が残ったままpushしない)。
   - この確認が手順に無いと、書き直しで失われた既存の項目35対応(座標調整済み図解・短いラベル・heroImage分離)が週次実行(item35-weekly)まで気づかれない。
4. **依頼者の目視確認**: 書き直した記事を依頼者が目視し、可否を判断する。
5. **台帳への記録は無い**: サイト本体に公開ゲート・台帳(`publish-ledger.json`)・`ledger-add-visual-check.js` は無い(`.claude/agents/publisher.md`「公開前の確認」。2026-11-19 に実在を確認して手順を直した)。4の目視の可否は、回のフォルダの進捗ファイルに記録する。3の `--strict` の0件確認が、公開前の最後の機械の関門になる。
6. **commit・push**: 記事データの変更をcommitし、pushする(`.claude/agents/publisher.md` の公開の手順。4の依頼者の目視は、依頼者がいる回は push の前、不在の回は本文を直していない担当の判定で置き換える)。
7. **push後の確認**: push から最低5分待ち(Vercelのデプロイの反映を確かめる待ち。記事の公開を待つことではない)、Vercelのデプロイ成功(トップページ・記事ページHTTP 200、sitemapの記事URL件数の整合)を確認する(CLAUDE.mdのデプロイ運用ルール)。

## まとめて直す回(組ごと)

多くの記事をまとめて直す回の進め方。上の「手順」の4(依頼者の目視)は、依頼者が不在の回は、本文を直していない担当の判定に置き換える(CLAUDE.md の「依頼者が不在の回」)。公開の手順の正は `.claude/agents/publisher.md` で、ここには書き写さない。

1. **20本ずつの組に分ける**。組の中の担当の並べ方は CLAUDE.md の作業方針(基本は20体)。
2. **組ごとに、次の順で行う**: 担当が直す → 検査(`verify-article.js` など。走らせ方は writer.md の「検査の走らせ方」)→ 本文を直していない担当の判定(`docs/pipeline/JUDGE-ITEMS.md`。指摘にア・イ・ウを付けて返し、ア〔内容が変わる指摘〕がなくなるまで直す。差し戻したあとは、直した所に関係する判定だけをやり直す。イ〔形の指摘〕は差し戻しに数えず、仕上げで1回にまとめて直し、直していない担当が内容が変わっていないことを1回確かめる。ウ〔出典の印の欠け・企画書と原稿の食い違い〕は差し戻さない。差し戻しの上限は1つの記事で合計5回〔第3層は1回まで〕。2026-10-11 依頼者の決定)→ 公開(`publisher.md` の公開の手順。pushは組ごとに1回)→ 本番の確認(push から5分待ち〔デプロイの反映を確かめる待ち〕、トップ・記事数・その組の記事を確かめる。記事数が減っていたら、次の組へ進まず原因を直す)。
3. **指示の写しと再開の手順**: 依頼者の1通の全文を `サイト運営/記事データ/作成中/_指示_<回>_<日付>.md` に写す。進捗ファイル `サイト運営/記事データ/作成中/_進捗_<回>_<日付>.md` を作り、先頭に再開の手順(「コンパクトのあと、または再開のときは、_指示_<回>_<日付>.md とこのファイルを読み直し、git status で commit していない変更が無いかを確かめ、下の『次の手順』から、止まらずに続ける。」。依頼者が不在の回は「依頼者は不在。質問しない。」を足す)を置いて消さない。その下に「次の手順」を1行で書き、手順が1つ進むたびに書き直す。
4. **個別の小さな直し**は、組の作業に混ぜず、先に1つの commit で出す。
5. **変えていない記事**は、公開の対象にしない(commit・push に含めない)。

## 1記事の流れ(書き直し・新規制作に共通。2026-11-19 追加。他サイトで確定した手順を、お金サイト向けに読み替えて置いた)

規則の本文は `.claude/agents/writer.md` が正で、ここは手順の順番だけを置く(規則を言い換えて再定義しない)。記事の作業フォルダは `サイト運営/記事データ/作成中/<日付>_<記事名>/`(中身は git に入れない)。

1. **企画書(`meta.md`)**: 読者の悩み・②の問い・**問いの根拠**(声を使った記事は声の番号だけ。使わない記事は、検索語・読者が知りたいこと・一次情報で確かめた事実のずれなど。規則34)・③の答え・構成と理由を書く(writer.md 規則11(0))。既存記事の書き直しでは、まず「落とさない中身」(注意書き・免責・リスク/手数料/元本割れの併記・時点・適用条件・窓口の例外の案内・依頼者の方針)を、書き直す前の記事から企画書へ書き写す。
2. **声の作業記録(`voices.md`。任意。依頼者の決定 2026-11-20)**: **声は任意**である。**探して使う場合だけ、writer.md 規則34に従う**(本文は規則34が正。ここには書き写さない)。声を使う記事は、記事ごとに `voices.md` を作業フォルダへ置く(声の探し先は X・Yahoo!知恵袋・Reddit・投資系の掲示板・家計相談の質問サイトなど、読者が悩みを書く公開の場。原文は匿名で保存し、区分「悩み/悩みではない」と理由1行を付ける。取れなかったソースは取れなかったと書く。探す担当は `.claude/agents/voice-researcher.md`で、依頼があったときにだけ使う)。声は問いの見つけ直し・見出しと導入の言い回し・導入の共感にだけ使い、出典・根拠・数字の裏付けにしない。**声を使わない記事は、問いの根拠を企画書に書く**(キーワード調査の検索語・読者が知りたいこと・一次情報で確かめた事実のずれなど)。**想像で悩みを作らない・声を作文しないことは、声を使うか使わないかにかかわらず変わらない。**「悩み不要」の宣言(制度改正・数値改定の速報解説、統計の読み解き、用語・仕組みの解説で、規則34・規則11(0)の条件を満たすもの)は、導入に読者の悩みを前提にした文を書かないための宣言であり、声の免除のためだけには使わない(②の問いと一次情報の出典は従来どおり必須)。
   - 他人の投稿の原文・アカウント名・URL・投稿IDは、報告にも、原文なしのファイル(企画書・まとめ・一覧)にも出さない。声は番号だけで呼ぶ。原文は `voices.md` だけに置く(作成中は git の追跡外)。機微な財務・家族・勤務先の情報(借金の詳細・病気や家族構成の詳細・勤務先が分かる記述など)は保存せず、番号と型だけを残す。
   - 声を探したが1件も取れなかった記事は、悩みを想像で作らない。声を使わずに、問いの根拠を企画書に書いて進めてよい(止める理由にしない。依頼者の決定 2026-11-20)。取れなかったことは報告に書く。
3. **本文を書く**(1記事1体)。
4. **部品を整える**(図解・要点ボックス・診断・mascotComment など。型と本数は writer.md 規則28・規則35が正)。
5. **画像を置く見出しを決める**(`imageBrief`。writer.md の「画像テーマ案」と、image-placer.md の「画像の採否」が正)。
6. **通読**(本文を書いていない新しい担当が全文を読む。直した文は直す前と並べ、別の新しい担当が前後の文とセットで「文脈読み」する)。
7. **指摘を文脈で1つずつ見て直し、別の新しい担当が同じ文を再確認する**。直す回数の上限は、1つの記事で最大2巡・再確認1巡を目安に、回の最初に決める(決めないと終わらない)。
8. **検査**(`verify-article.js`。地の文400字連続の確認を含む。走らせ方は writer.md の「検査の走らせ方」)。**地の文の字数(下限3,500字。依頼者の決定 2026-11-20。数え方は規則33(c))と、画像の枚数(サムネイル込みで3枚以上。同じく 2026-11-20。writer.md「画像テーマ案(imageBrief)」)は、`verify-article.js` に機械検査が無い**ので、判定役が数えて報告に書く(作業用の数え方は scratchpad に置き、リポジトリに置かない)。3,500字に届かない記事は、水増しせず、規則35(h)の深掘り(やり方の具体)で足す。画像が3枚に足りないときは、公開を止めず、確保できた枚数・理由・足りない画像の依頼を報告する(画像は依頼者が用意するため)。
9. **回帰チェック**(企画書の「落とさない中身」が本文に残っているか。新しい担当が全文を読む)。
10. 組ごとの終わりに、writer.md の規則35の確認(文末・フック・図の本数・文単位の監査など)を行う。機械検査が実装されていない項目は、判定役が文脈で読む。数は参考表示で、止めるのは規則に決まった項目だけ。

## 共通の指示(担当を起動するとき。2026-11-19 追加)

担当の起動プロンプトは「共通の指示ファイルを最初に全文読め」と「割り当て1つ」だけにする。共通の指示は `作成中/_共通の守ること_<回>.md` に置き、次を必ず書く。規則の本文は写さず参照だけにする(規則の本文は writer.md の1か所だけ)。

1. 日付と、使うフルパス(「作成中/」「公開待ち/」「公開済み/」は `サイト運営/記事データ/` の下、画像は `サイト運営/サイト本体/public/images/articles/`)。
2. 今回が何をする回か(下書きを作る回・確認する回)と、してはいけないこと: commit・push・公開・置き換え・消去・リンク付け替え・サイトのコードや規則本文の変更をしない。git は読み取り(status・diff・log・show)だけ。
3. 触ってよいもの(自分の担当フォルダの新規ファイル、または指定の下書き1本だけ)と、触らないもの(他の下書き、公開済み・公開待ち、規則本文、検査スクリプト、サイトのコード、スキル)。
4. 変えないもの(悩み=記事の問い、題・slug・date、リスク・注意・免責の記述、窓口の例外の案内、大見出しの数と順、`%%出典:…%%` の記法)と、新しい数字・出典・事実を足さないこと。税率・金利・手数料などは公式の情報で確かめ、時点を残す。
5. 最優先の原則: 悩みをずらさない。リスクや注意の記述を弱めない。出典を新しく探しに行かない(確かめは本文を書き終えたあとに公式の資料で行う。規則11・規則28)。儲かる・得する額を断定しない。検査を通すためだけの移動・水増しをしない(検査が通らない原因が悩みや解決法のずれなら、直さずブロッカーとして報告する)。
6. 直す前の写しを `<元の名前>_第N回前.md` で同じフォルダに残し、直し前後を `直し前後_第N回.md` に書く(前後の全文・字数・理由)。
7. 検査は、公開名(`<slug>.md`)の写しを自分専用の一時フォルダに作って走らせ、リポジトリに何も書かない形で行う。他の担当の結果を上書きしない。書き込みのおそれがあれば「未実行」と書く。
8. 書き込みはLFのまま(CRLFにしない)。
9. 依頼者の在席・不在にかかわらず質問しない。最も妥当な読みで進め、読みの内容を報告に書く。決められない点は直さず一覧にして報告する。
10. 出力と報告: 内容はファイルに書き、完了報告は要点だけ(3行以内)。パスはフルパス。他人の投稿の原文・URLを出さない。事実(読んで確かめた)・推測・未確認を分ける。工程ごとに作業フォルダへ保存する(途中で止まっても再開できるように)。
11. 確認担当には、書き手の報告を読ませない(説明に引きずられないため)。読んでよいのは、旧版の題とフック・新しい版・企画書など指定の数ファイルだけで、1ファイルに出力させる。

確認担当の観点: (A)悩みのずれ(旧版の題とフックから読者の悩みを1文で書き、新しい版でも書いて「同じ/ずれた/迷う」を判定)、(B)規則違反(違反の文を引用)、(C)文脈読み(前後2文つきで1文ずつ読み、不自然な文だけを、場所・分類・理由・優先度・直し案1文で出す)、(D)回帰チェック。

## 並列の起動数と上限(2026-11-19 追加)

- 同時に動かす担当は、対象の記事の数だけ。基本は20体(10体×2組。CLAUDE.md の作業方針)。これは同時に起動する数の目安で、実際に同時に走る数は実行環境の上限で頭打ちになる。
- 依頼者が「並列」と書いたときは実際に並列で起動する(「未確認だから直列」にしない)。段階を踏むなら、最初の3〜4体で型を確かめ、問題なければ20体にする。
- 声を探す担当(依頼があったときだけ使う任意の担当。ブラウザ操作・検索)は、同じサイトへの連続読み込みに数秒あける。大量に収集せず、人のペースで読む。ブラウザを使う担当が多いと他の担当の検索結果が混ざる乱れが出るため、ブラウザを使う担当は同時に5体までを目安にする(ブラウザを使わない担当は20体まで)。
- 1回の作業で1つの規則(または1つの観点)を全記事に当てる。複数の規則を一度に当てると、どの直しが改善か分からなくなる。

## 終わり方の定義(2026-11-19 追加)

組の記事ごとに、次を満たしたものを「完了」にする。(i)悩みが新しい2体の独立判定で「同じ」(ii)規則違反0(新しい2体)(iii)文脈読みで「高(読者が意味を取り違える・つまずく)」と直せる「中」が0(iv)題・URL・dateが旧版と一致(v)検査(verify-article.js)が悪化していない(vi)ページが開く(HTTP 200)・画像欠け0・直した文が入っている(vii)判断が要る点は判断の表に載っている。上限まで直しても高・中が残る記事は「指摘付き」として報告し、悪化が戻せない記事は中止して元の版に戻す。直したあとに別の確認を入れていない記事は完了にしない(未完)。確認の回数が定義より少なかったときは、弱めた点として報告に正直に書く。

## 既存記事の洗い出し・集約(似た記事を1本にする。2026-11-19 追加)

同じ検索意図の記事が複数あると、検索エンジンに似た記事と見なされてインデックスが落ちる。集約は、依頼者が決めた回に行う(調べの回は実行しない)。

動機: 集約は、検索エンジンのインデックス登録が落ちている実測(Search Console の「クロール済み - インデックス未登録」の件数など)への対応として行う。記事数を減らすこと自体が目的ではなく、質の高い記事だけが残った結果として数が減る。依頼者の1通にその動機が書かれていなければ、報告に書く。

1. **洗い出し**: 公開済み・公開待ち・直し中の記事どうしを、いまの題・見出し・本文で比べ、「同じ主要な悩み(検索意図)に答えるか」で組にする(話題が同じだけでは組にしない。履歴に頼らない)。判定は、前の判定を見ていない新しい2体が、互いの結果を見ずに独立に行い、2体が一致した組だけをグループにする。割れたものは新規扱い(グループにしない)とし、迷うものは「要判断」にまとめる。本文を読んで確かめた組と、題・見出しだけで読んだ組を分けて書く。結果は回のフォルダに保存する。記事数が少ないときは、1人の目視で置き換えてよい。
   - **質の見る点**(集約・削除を決めるとき。質の定義の本文は writer.md 規則35(i-9)が正で、ここには書き写さない): 判定役は、(1)題の悩みが読者の実在の悩みか (2)本文がその悩みを実際に解決しているか (3)読者が求める内容か、の3点で見る。字数・語の数・出典の数のような表面の指標で質を決めない。金融の記事は、リスク・手数料・元本割れ・時点が落ちていないことも質に含める。
2. **集約するか、問いを分けるか、削除するか**: グループごとに、(a)集約(1本にする)・(b)問いを分ける(各記事の悩みを別の悩みにする。分けた問いも、実在の声か、企画書に書いた問いの根拠〔検索語・読者が知りたいこと・一次情報のずれ〕から出す。想像でずらさない)・(c)削除(薄い・重複する・独自性のない記事で、残す価値がないもの)から依頼者が決め、(a)なら残す1本(吸収先)も依頼者が決める。**悩みが別の記事を、無理に1本に混ぜない**(悩みが別なら統合しない。質が高ければ残し、低ければ(c)を検討する)。評価は、独自性・具体性・統合したときの読みやすさを、高・中・低で記録し、字数だけで決めない。(c)は、依頼者が不在の回は実行せず保留にする(`publisher.md`「保留にしてよい範囲」)。懸念が少しでも残るなら集約する。3本を3本に直しただけの、重複の多いほとんど同じ記事は作らない。依頼者が不在の回は、依頼者の1通と規則の考え方で自分で決め、決めた内容と理由を報告に書く。
3. **吸収の手順**: 吸収先に加えるのは、吸収される記事が答えていて、吸収先がまだ答えていない分に限る(同じ悩みの分は足さない)。吸収先は規則(11・30・31・35)で作り直す。URL・slug・dateは変えず、`updatedDate` だけ直前に当日にする。吸収先が何本を吸収したかの数は本文に残さない。統合後の本文は、読者の悩みの答えを渡しきる長さにする(字数を満たすために書き足さない)。
   - 取り込みのルール: 吸収先の本文を先に読み、同じ内容が既にあれば取り込まない。出典は frontmatter の `sources` だけを扱い(取り込む文に出典の注記があれば、吸収元の該当の出典を足す。同じURLは足さない)、新しく探しに行かない。**リスク・手数料・元本割れ・適用条件・時点の併記、免責、窓口の例外の案内は残す**(吸収元にあって吸収先に無いときは取り込む)。既存の見出し(H2/H3)の文言は変えない(`charts`・`accordions`・`imageBrief` が見出し文で位置を指す。変えるときは指す側も同じに直す)。吸収元の図・画像は持ち込まない。吸収元を指すリンクは書かない(あとで付け替える)。
   - 統合後の本文も、既存の規則・検査にすべて通す(規則35・B5・400字ルール)。「〜と思います」の強引な決めつけ(「〜人も多いと思います」を含む)を新しく書かない(依頼者の決定 2026-11-20。扱いは writer.md 規則35(d)・35(i-9)が正)。読者の状況は規則16の確かめる語りで書く。読点だけでだらだら列挙せず、並列は箇条書きか表にする。同じ文面を別の節で使い回さない。
   - 吸収先の題・description・tags・summaryPoints・targetReader・worry を、取り込んだ悩みが入る形に更新する(題は writer.md の題の規則に従う)。
4. **吸収された記事の扱い**(依頼者の決定を待つ。不在の回は、実行せず該当の記事だけ保留にする。CLAUDE.md の「依頼者が不在の回」と publisher.md の「保留にしてよい範囲」):
   - 吸収元の記事ファイルを `サイト運営/記事データ/公開済み/` から `サイト運営/記事データ/非公開アーカイブ/` へ移す(移動=サイトから消す。履歴は git に残る)。移すのは公開の手順を実行する者(束ねる側)だけで、担当は移さない。
   - 吸収元を指していた他の記事の内部リンクを、吸収先へ付け替える(消す前に、slug〔日付なし・URLエンコード形〕で全記事を検索する。付け替えたあと、「実在しない /posts/…」を全記事から列挙して0件を確かめる)。題を変えた記事を指すリンク文は、新しい題に直す。公開待ち同士にリンクを張るときは、リンク先が先に公開される順になっているかを確かめる。
   - 旧URLの転送は、依頼者が回ごとに決める。転送するなら `vercel.json` の `redirects` に書く(CLAUDE.md)。
   - 吸収元の専用画像は、他の記事と共有されていないこと(`git grep` で `pages`・`lib`・`components`・`styles` から参照が無いこと)を確かめてから消す。画像の扱いは回ごとに依頼者が決める(消さずに残してもサイトの画面には出ない)。
   - コード内の slug 直書きは、消す前に `git grep -n "<slug>" -- pages lib components` で確かめ、当たれば消す前に報告する。
   - 記事として使われなくなる悩みの記録を、回のフォルダに残す(元の記事・扱っていた切り口・使われなくなった理由・吸収先)。
   - push のあとの本番の確認は、CLAUDE.md のデプロイ運用ルールのとおり(トップ200・sitemap の記事URL件数が消した本数だけ減る・吸収先の記事ページ200・消した記事のURLが開けない・サイト内検索と一覧に出ない)。記事数が想定より減っていたら、次の組へ進まず原因を直す。
5. 集約を実行する担当への指示(共通の指示のほかに): 編集してよいのは、吸収先の記事ファイル1本と自分の報告ファイルだけ。吸収元・他の記事・サイト本体は変えない。作業前に吸収先と吸収元の全文を最後まで読む。報告の型は、(1)吸収先・吸収元 (2)題・description・tags・summaryPoints・targetReader の前後 (3)字数 (4)取り込んだ内容・取り込まなかった内容と理由 (5)語の数え(リスク・元本割れ・手数料・適用条件・時点・窓口の例外・免責の件数の前→後。減っていないこと) (6)検査結果 (7)出典欄の変更 (8)吸収元を指すリンク (9)迷い。

## 図(絵図)の確かめ方(2026-11-19 追加)

図の型と本数は writer.md 規則28・規則35が正。ここは、図を新しく作る・直すときの確かめ方だけを置く。

- 記事ごとに専用の図を作る。他の記事と同じ構図に文字だけ変えた図、記事の悩みの答えと関係の薄い飾りの図は使わない(同じ制度・同じ種類の明らかに似た記事どうしだけ共用してよい)。1つの記事に複数の図を置くときは、役割(状態の対比・手順・見分ける位置)を変える。
- ラベル隠しテスト: 文字を隠しても、何を見せる図かが形と配置で伝わること。丸・四角・矢印を並べただけで何の図か分からないものは使わない。商品名・ブランド名・出典のない数値は図に入れない。口座・税・手数料・手続きの構造を描く図は、金融庁・国税庁・日本銀行など一次資料で突き合わせる(似た制度だから同じ、という推測で描かない)。
- 文字の読みやすさ: 幅320・375・768pxのどれでも、文字が線・図形・矢印・他の文字に重ならず、枠からはみ出さないこと(`node scripts/verify-rendered-layout.js --strict <slug>` が0件。「手順」の3のとおり push 前に必ず行う)。
- 作った担当が、画面で自分の目で確かめる(図を1つずつ画面で開き、文字のはみ出し・重なり・小さい文字・何の図か分からない・手抜きに見える所があれば直して、もう一度見る)。確認担当は別の担当が、同じ方法で手抜き感の有無を記録する。
- 公開前に、図を含むページを依頼者が見る回は、図に指摘があればその図は公開しない。公開の直前に `--strict` を通す。
- 絵柄・図の描画コードを新しく足すときは、実装の前に案(推奨+代替)を依頼者に示して決めてもらう(不在の回は規則の考え方で自分で決め、理由を報告する)。

## 作業フォルダの運用(2026-11-19 追加)

- 依頼者の1通は、始める前に `サイト運営/記事データ/作成中/_指示_<回>_<日付>.md` へ全文を写す。進捗ファイルの先頭の再開の手順は上の「まとめて直す回」の3のとおり。
- 着手前に `git log` の直近を見て、同じファイル・機能に別の作業者の変更が入っていないかを確かめる。`git status` で未commitの変更を確かめ、報告に書く。同じ値・同じ変更を複数ファイルへ機械的に当てる前に、対象リストの根拠を明示し、サンプルを確認する(updatedDate を実質でない記事に付けない。誤字・表記ゆれだけの空更新はしない)。
- 依頼者が見る資料(目視用の一覧・案内)は、記事を題か短縮形で呼び、内部の記号(A1・案a・第◯回)を使わない。専門用語は言い換えるか、初出で1文の説明を付ける。
- 「確認済み」と書くのは、取得して確かめた項目だけ。読んでいない記事・範囲について書かない。件数は足して合うことを確かめてから書く。
