# NEVORA 記事制作パイプライン 実行仕様書 v1.0

本書は、サブエージェントに工程単位で配布する**実行指示書**である。
記述されていないことは実行してはならない。判断に迷った時点で作業を停止し、停止理由を報告すること（§2.6 停止ルール）。

---

## 0. 使い方（依頼者向け・サブエージェントには配布不要）

1. §1 の表の ⬜ をすべて埋める。**1つでも空欄のままパイプラインを起動しない。**
2. 工程ごとに新規セッションを立て、そのセッションに貼る文書は
   **「§1」+「§2 共通規約」+「担当工程の章」+「前工程のハンドオフファイル」の4点のみ**とする。
3. 工程は必ず 0 → 1 → 2 → 3 → 4 の順。工程4が「合格」を出すまで公開しない。

## 2. 共通規約（全工程が遵守）

### 2.1 作業ディレクトリと成果物

| 工程 | 入力 | 出力 |
|------|------|------|
| 0 仕様棚卸し | 既存リポジトリ | `docs/pipeline/SPEC-EXTRACT.md` |
| 1 本文執筆 | §1, `SPEC-EXTRACT.md` | 記事ファイル（プレースホルダー入り）, `docs/pipeline/HANDOFF-01.md` |
| 2 アコーディオン実装 | 上記 + `SPEC-EXTRACT.md` | 記事ファイル（更新）, `HANDOFF-02.md` |
| 3 ビジュアル実装 | 上記 | 記事ファイル（更新）, 画像アセット, `HANDOFF-03.md` |
| 4 検証 | 上記すべて | `docs/pipeline/VERIFY-REPORT.md` |

- 各工程は**着手前に `git switch -c <作業ブランチ>` または既存作業ブランチへ切替**、
  **完了時に1コミット**を作る。コミットメッセージ: `pipeline(step-N): <工程名>`。
- 工程4（検証）は**記事ファイルを一切編集しない**。編集した時点でその工程は失敗とみなす。

### 2.2 プレースホルダー文法（唯一の正）

プレースホルダーは**ブロック形式のみ**。インライン記法・独自の亜種を作ってはならない。

```
[[TYPE:ID
intent: <この要素が読者に何をさせたいか。1文>
content: <実装対象の中身。TYPEごとの必須キーは各工程章で定義>
]]
```

規則:

| 規則 | 内容 |
|------|------|
| R-1 | 開始行 `[[TYPE:ID` は行頭から始め、その行に他の文字を書かない |
| R-2 | 終了行は `]]` のみの行 |
| R-3 | ブロックの前後は空行1行で区切る |
| R-4 | ネスト禁止。プレースホルダーの中に別のプレースホルダーを書かない |
| R-5 | `intent` と `content` は必須。省略したブロックは不正として工程4で不合格 |
| R-6 | 本文中に文字列 `[[` を通常表記として使わない（使う必要が生じたら停止・報告） |

**TYPE は以下の3種のみ。新設禁止。**

| TYPE | 用途 | 担当工程 |
|------|------|----------|
| `ACC` | アコーディオン（開閉パネル） | 工程2 |
| `VIS` | 図解・グラフ・イラスト等の視覚要素 | 工程3 |
| `TBL` | 表 | 工程3 |

### 2.3 ID 採番規則（重複防止）

- 形式: `<TYPE>-<2桁連番>`（例: `ACC-01`, `VIS-03`, `TBL-01`）
- 連番は TYPE ごとに 01 から、記事内での**出現順**に振る。欠番・飛び番禁止。
- 工程1は本文確定後に次のコマンドを実行し、**重複0・欠番0を自分で確認してから**引き渡す。

```bash
# ID一覧（重複行が出力されたら不合格）
grep -oE '\[\[(ACC|VIS|TBL)-?[A-Z]*:[A-Z]+-[0-9]{2}' <記事ファイル> | sort | uniq -d
```

### 2.4 消費マーカー（実装済みの機械判定を可能にする）

工程2・3 は、プレースホルダーブロックを**完全に削除**し、実装コードに置換する。
そのうえで、置換した実装の**直前行**に消費マーカーを1行残す。

```
{/* impl:VIS-01 */}
```

（`.mdx` 以外の形式の場合、その形式で有効なコメント構文を工程0で確定し `SPEC-EXTRACT.md` に記録すること）

これにより工程4は次を機械判定できる:

- 未実装 = 記事内に `[[` が残っている
- 実装漏れ = `HANDOFF-01.md` のIDリストに対し `impl:<ID>` が存在しない

### 2.5 「新規に発明しない」の運用定義

- **禁止**: 既存リポジトリに存在しない記法・コンポーネント・CSSクラス・画像生成手段を新たに定義すること。
- **必須**: 実装に使う記法/コンポーネントは、すべて `SPEC-EXTRACT.md` に列挙された項目の中から選ぶ。
- **例外時の唯一の許可動作**: `SPEC-EXTRACT.md` に該当する既存手段が無い場合、
  **代替実装を考えてはならない。** 次を記事内のその位置に残し、報告して次へ進む。

```
[[UNRESOLVED:<元のID>
reason: <既存仕様に該当が無い理由。参照した SPEC-EXTRACT.md の節番号を明記>
]]
```

> 前回の失敗（「無難な実装に逃げる」）は、例外時の逃げ道が定義されていなかったことによる。
> **手を抜くより停止する方が正しい**、というのが本パイプラインの原則である。

### 2.6 停止ルール（全工程共通）

以下に該当したら**その場で作業を停止し、実施済み内容と停止理由を報告**する。推測で進めない。

1. §1 の必要項目が空欄
2. 前工程のハンドオフファイルが存在しない／必須項目が欠けている
3. `SPEC-EXTRACT.md` に該当する既存仕様が無い（§2.5 の例外処理を実施して報告）
4. プレースホルダーの `content` が実装に必要な情報を欠いている（例: 項目数が指定と不一致）
5. 記事ファイルが想定形式と異なる
6. ビルドが通らない状態を自力で解消できない

### 2.7 ハンドオフファイルの必須項目

`docs/pipeline/HANDOFF-0N.md` に以下を必ず書く（これが後工程の唯一の文脈源）。

```markdown
# HANDOFF-0N
- 工程: <番号と名称>
- 対象ファイル: <パス>
- コミット: <ハッシュ>
- 記事の狙い（1〜3行）: <後工程が意図を外さないための要約>
- 本工程で確定したIDと状態:
  | ID | TYPE | 状態(placed/implemented/unresolved) | 配置位置(直前のH2/H3見出し) |
- 参照した SPEC-EXTRACT.md の節: <節番号の列挙>
- 未解決・申し送り事項: <無ければ「なし」>
```

## 4. 工程1：本文執筆＋プレースホルダー配置

**この工程ではコンポーネントを実装しない。** 出力は文章とプレースホルダーのみ。

### 4.1 実行手順

1. `SPEC-EXTRACT.md` を読む。§1（記法）§5（マスコット）§7（構成実測値）を必ず参照する。
2. 見出し構成（H2/H3）を先に作り、`HANDOFF-01.md` の下書きに記載する。
3. 本文を書く。§1-9/-10 のUI制約を守る。
4. プレースホルダーを配置する（§4.3）。
5. §2.3 の重複チェックコマンドを実行し、結果を `HANDOFF-01.md` に貼る。
6. §4.5 の完了条件をセルフチェックし、全項目 Yes になってからコミット。

### 4.2 執筆制約

- 文字数: §1-7 の範囲内。
- 1段落: §1-9 の定義を超えない。
- テキスト段落の連続: §1-10 の定義を超えない。超えそうな箇所には `VIS` / `TBL` / `ACC` のいずれかを挟む。
- 使ってよい装飾記法は `SPEC-EXTRACT.md` §1 に列挙されたものだけ。
- 薬機法: 効能効果の断定表現を使わない（付録A のNGワードを含めない）。
- 断定的な数値・研究引用を書く場合は出典を frontmatter または本文脚注に残す。

### 4.3 プレースホルダーの必須フィールド（TYPE別）

#### ACC（アコーディオン）

**重要: アコーディオンの中身の文章は工程1がすべて書く。** 工程2に文章を書かせない。
**重要: アコーディオンに入れる内容と同じ文章を、本文側に重複して書かない**（前回の二重表示の再発防止）。
導入として1文だけリード文を置く場合は、`lead` フィールドに書き、本文側には書かない。

```
[[ACC:ACC-01
intent: 自己流ケアの読者に、当てはまるNG行動を自己診断させる
lead: 心当たりがあるものを開いて確認してみてください。
title: やりがちなNGケア5選
items:
  - label: 洗顔は1日3回以上している
    body: 皮脂を落としすぎると…（2〜4文。ここが唯一の本文）
  - label: 化粧水をコットンで強くパッティングしている
    body: …
]]
```

- `items` は2件以上。件数は `title` の記述と一致させる（「5選」なら5件）。
- `label` は40字以内、`body` は §1-9 の1段落上限以内。

#### VIS（図解・グラフ・イラスト）

```
[[VIS:VIS-01
intent: 乾燥肌と健康な肌の違いを、読者が構造として理解できるようにする
kind: 断面比較図
content: 左に健康な肌、右に乾燥肌の断面。角層・皮脂膜・水分の3層を色分けし、乾燥肌側は角層の乱れと水分減少を表現
labels: 角層 / 皮脂膜 / 水分量
caption: 乾燥肌では角層のバリア機能が低下している
alt: 健康な肌と乾燥肌の断面を並べた比較図
]]
```

- `kind` は「何の図か」の分類（比較図／フロー図／棒グラフ／円グラフ／イラスト 等）。
- `labels` は図中に入れる文言。工程3は**ここに無い文言を図中に足さない**。
- `alt` は必須。

#### TBL（表）

```
[[TBL:TBL-01
intent: 読者が自分の肌質を1分で判別できるようにする
content: 肌質4タイプ判別表
rows: 乾燥肌 / 脂性肌 / 混合肌 / 敏感肌
cols: 洗顔後のつっぱり / 日中のテカリ / 刺激への反応 / 向いているケア
cells: 全マスの内容を工程1が記述する（下記）
  - 乾燥肌: 強い / ほぼなし / 弱い赤みが出やすい / 高保湿クリーム
  - 脂性肌: なし / Tゾーン以外も / 出にくい / さっぱり保湿
  - 混合肌: 部分的 / Tゾーンのみ / 部位差あり / 部位別ケア
  - 敏感肌: 強い / 少ない / 赤み・かゆみ / 低刺激処方
]]
```

- **表のセル内容は工程1がすべて埋める。** 工程3に内容を考えさせない。

### 4.4 配置ルール

## 5. 工程2：アコーディオン実装

**扱うのは `ACC` のみ。`VIS`/`TBL` には一切触れない。文章を書き足さない・削らない。**

### 5.1 実行手順

1. `SPEC-EXTRACT.md` §3（アコーディオン仕様）と §2（コンポーネント）を読む。
2. `HANDOFF-01.md` の ID リストから `ACC-*` を抽出し、対象一覧を作る。
3. 各 `ACC` ブロックを、既存コンポーネントを用いた実装に置換する。
   - `title` → コンポーネントの見出しprop
   - `items[].label` → 各パネルの見出し
   - `items[].body` → 各パネルの本文（**文言を改変しない**）
   - `lead` → `SPEC-EXTRACT.md` §3 の既存記事の作法に従って配置。作法が確認できない場合はアコーディオン直前の通常段落として1文だけ置く。
4. ブロックを**削除**し、実装の直前行に `{/* impl:ACC-01 */}` を残す（§2.4）。
5. `SPEC-EXTRACT.md` §9 のビルド／Lintコマンドを実行し、成功を確認。
6. §5.3 をセルフチェックしてコミット、`HANDOFF-02.md` を作成。

### 5.2 禁止事項

- 新しいアコーディオンコンポーネント／CSSクラス／記法の作成
- `body` の要約・書き換え・削除、および**本文への再掲**（二重表示の禁止）
- `VIS` / `TBL` プレースホルダーの削除・移動・改変
- 既存コンポーネントに存在しない props の追加

## 6. 工程3：ビジュアル・表の実装

## 8. 工程5：差し戻しループ

1. 差し戻し先の工程を**新規セッション**で起動する。渡すのは
   §1 + §2 + 該当工程章 + `VERIFY-REPORT.md` の該当行 + 直前のハンドオフ。
2. 修正担当は、**指摘された箇所のみ**を修正する。指摘外の改変は禁止。
3. 修正後は工程4を**全項目**再実行する（部分検証は不可。修正が別項目を壊すため）。
4. ループ上限は**2周**。3周目に入る場合は自動修正を止め、依頼者にエスカレーションする。
   （同じ項目が2回連続で不合格になる = 指示か仕様定義に欠陥がある、と判断する）
